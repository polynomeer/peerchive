# 공개 사례 초안: ProofU — 졸업작품을 버리지 않고 Peerchive로 잇기

> **상태:** 초안 · **공개 수준(예정):** 🌐 전체 공개 · **작성 방식:** `사후 작성` (2026-10 작성, 과거 시점은 자기 기입)
> Peerchive의 첫 공개 사례이자 [사후 작성 모드](../../PROOFU_EVOLUTION_PLAN.md#67-사후-작성-모드)의 첫 실전 시험입니다. 앱이 생기면 이 문서를 그대로 옮겨 넣고, 마일스톤 스냅샷은 실제 파일로 대체합니다.

## 한 줄 요약

선배에게 알음알음 받던 족보를 공개 이력으로 바꾸고, 그 이력을 포트폴리오로 만들겠다는 2019년 졸업작품의 아이디어를, 7년 뒤 “칸반이 남기지 못한 것”을 반성하며 학기 중에 쓸모 있는 빌드 로그 중심 서비스로 다시 설계한 과정.

## 빌드 로그 (중요한 전환점)

### ⚖️ 결정 — 2019: 과정을 보여 주는 형식으로 칸반을 택함 `사후 작성`
- **선택지:** 칸반 보드 / 일지 / 깃허브 커밋 연동
- **판단 기준:** 팀 과제의 진행 상태를 한눈에 보여 줄 것, 당시 익숙한 도구(Trello)와 비슷할 것, 졸업작품 기간 안에 구현 가능할 것
- **선택:** Trello형 칸반(Todo/Doing/Done) + 카드 첨부파일 + 팀 채팅
- **지나고 보니:** 칸반은 *상태*만 남겼습니다. 카드가 Done으로 가면 왜·어떻게·무엇이 어려웠는지가 사라져, 후배에게도 채용자에게도 정보가 되지 않았습니다. 또 학기 중에 Trello·카톡 대신 이 서비스를 쓸 이유가 약했습니다.

### 🔨 진행 — 2019: 팀·보드·카드·파일·채팅·일정·학교 공지·마이페이지 구현 `사후 작성`
- 근거: `backend/models.js`(User·Team·Member·Join·Board·List·Card·Message·BoardFile·CardFile), `frontend/src/router/index.js`, MyPage의 언어·분야 차트
- (작성자 기입: 이 중 직접 구현한 부분)

### 🧱 막힘 — 2026-10: 보존된 원본이 그대로는 실행되지 않음
- **증상:** `backend/app.js`가 불러오는 `backend/api/user.js`가 저장소에 없음. Vue 2/Webpack 3/Babel 6, sqlite3 네이티브 모듈 등 구버전 체인.
- **시도한 것:** 원본 분석과 실행 제약 문서화([프로젝트 분석](../../PROJECT_ANALYSIS.md))
- **해결·우회:** 원본은 수정하지 않고 기록 보존 대상으로 둠. 실행 복원 대신 새 앱을 옆에 만들기로 결정(아래 결정). 원본 화면 시연이 필요하면 별도 overlay로 2~3일 시간 상자 안에서 시도.
- **걸린 시간:** 반나절 이상 (분석·문서화 포함)
- 상태: 우회(원본 실행 자체는 미해결)

### ⚖️ 결정 — 2026-10: 이력을 지우지 않고 재구성·검증 가능한 아카이브로
- **선택지:** 저장소를 새로 시작 / 기존 이력 위에 그대로 이어 쓰기 / 이력을 기능별로 재구성하되 원본을 백업하고 검증 스크립트로 보존 확인
- **선택:** 세 번째. 재구성 커밋마다 retrospective reconstruction임을 명시하고, `scripts/check_archive.py`로 원본 blob·이력 보존을 검증
- **지나고 보니:** (작성 예정)

### ⚖️ 결정 — 2026-10: 원본을 업그레이드하지 않고 새 앱을 옆에
- **선택지:** Vue 2 → 3 점진 업그레이드 / 새 앱을 `apps/`에 추가
- **판단 기준:** 실행 복원 비용, 보안 구조(평문 비밀번호·하드코딩된 키) 수정 비용, 새 핵심 도메인(빌드 로그·기여 장부·공개 스냅샷)이 원본에 없음
- **선택:** 새 앱. 원본의 개념(팀·보드·카드·파일)은 [계승 매핑](../../planning/SYSTEM_DESIGN.md#22-개념-계승-매핑)으로 이어 감
- **지나고 보니:** (작성 예정)

### ⚖️ 결정 — 2026-10: 칸반 대신 빌드 로그 + 마일스톤, 학기 중 동기는 기여 장부
- **선택지:** 칸반 유지 / 자유 일지 / 커밋 자동 수집 / 빌드 로그 + 마일스톤 + 주간 체크인
- **판단 기준:** 후배가 재사용할 수 있는가, 채용자가 판단 근거로 읽을 수 있는가, 작성 부담이 낮은가, 학기 중에 쓸 이유가 있는가
- **선택:** 빌드 로그 + 마일스톤. 칸반은 ‘할 일’ 보기로 남기고, 카드 완료 시 막힘·결정 기록으로 전환
- **지나고 보니:** (단계 0 E0 결과 후 작성)

### 🔁 회고 (중간)
- 2019년의 핵심 아이디어(족보의 공개, 과정의 아카이브, 포트폴리오화)는 지금도 유효했고, 바뀌어야 했던 것은 *기록의 형식*과 *쓰는 동기*였다.
- “나중에 포트폴리오가 된다”는 보상만으로는 기록이 쌓이지 않는다. 학기 중의 이득(조별과제 기여 증명)이 먼저다.
- 정답을 빼도 족보 가치의 대부분이 남는다는 점을 깨닫고, 공개의 단위를 ‘답’에서 ‘지도’로 바꿨다.
