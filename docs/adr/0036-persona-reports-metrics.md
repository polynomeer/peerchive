# 0036. 페르소나 신고·조치와 공개 프로필 계측: 페르소나 하나만 가리키는 신고·조치 + 사유를 남겨야 열리는 주인 확인 + 프로필에만 고르는 표시명 사칭 사유 + 사용자 키·시 단위 시각만 담는 §6.2 이벤트

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

S-07은 DELIVERY_PLAN §4.2 공개 프로필·팔로우 백로그의 마지막 항목입니다: "신고 대상에 페르소나·프로필 글·소셜 링크 추가, 표시명 사칭 신고 사유, §6.2 이벤트(0~1단계 글은 사용자 키 없이)". §7 GP 게이트의 필수 확인 중 "신고 대상에 페르소나·프로필 글 포함, 표시명 사칭 처리 기준 공지"가 이 항목입니다. 관련 설계와 앞선 결정:

- SYSTEM_DESIGN §8.3 표 "표시명 ↔ 실명 연결 보기 — 운영자: 신고 처리 시 감사 기록과 함께", §6.7.1 ProfilePost(`hidden`)·SocialLink, §8.1 작성자 확인("사유·범위·감사 기록을 남긴 경우만").
- ADR 0015(신고·조치·이의제기: 지금 공개인 것만 신고, 대상 단위 처리, 내부 메모·당사자 사유 분리, 감사는 id·종류만, 조치마다 이의제기 한 번), 0016(분석: 허용 목록 props·HMAC 사용자 키·수집 거부·지표 5 미만 가림), 0023(커뮤니티 작성자 확인: 사유 기록 + id만 감사 + 응답에만 결과), 0027(키 없는 이벤트 = `actor_hash` null, 운영 기록은 개수로만, 모든 칸 5 미만 가림).
- ADR 0028: 신고·조치·운영 화면 이름표가 사용자 단위(`profile_user_id`)라 표시명 프로필을 신고하면 운영 화면에 실명 handle이 붙고 숨김도 실명 프로필에 걸립니다. 그래서 표시명 프로필에는 신고 버튼을 두지 않고 S-07로 미뤘습니다. 숨김(`profiles.hidden_at`)은 페르소나마다입니다.
- ADR 0034: 제3자가 남의 페이지에 내 프로필 링크를 넣어 "확인됨"이 될 수 있음 — 신고 대상에 소셜 링크를 더할 때 다시 봄. ADR 0035: 프로필 글 `hidden` 상태와 거두기·되살리기 트리거는 이미 있고 API만 S-07.
- DELIVERY_PLAN §6.2 분석 이벤트(P1): `persona_created`(kind), `identity_link_toggled`, `visibility_changed`(item_kind·audience), `project_listed`, `follow_requested`, `follow_approved`, `follower_removed`, `block_created`(scope), `mute_created`, `feed_item_opened`(source_type), `social_link_verified`. "0~1단계 글 이벤트에는 사용자 키를 붙이지 않고, 차단·뮤트·팔로워 삭제 이벤트에는 상대방 키를 담지 않습니다. 팔로워 수·피드 노출 수를 개인 지표나 순위로 쓰지 않습니다." 지표: 정체성 누출(필수)·팔로우 → 기록 활용(핵심)·피드 구성·표시명 사용·표시명 사칭·팔로워 수 표시 선택·소셜 링크 유입·차단·뮤트·팔로워 삭제.

## 결정

### 1. 신고 대상: 페르소나 하나만 가리킴 (migration `0032_persona_reports_metrics`)

| targetType | targetRef(공개 화면에 보이는 값) | 지금 공개 판정 | 포인터 |
|---|---|---|---|
| `persona` | `{handle}`(실명·표시명 어느 쪽이든) | `resolvePublicPersona`(페르소나·계정 active, 프로필 있음, 숨김 아님) + 신고자에게 차단으로 숨겨지지 않음 | `persona_id` |
| `profile_post` | `{activityId}`(활동 목록·피드의 활동 id — 글 id는 공개되지 않음) | 거두지 않은 활동 + 게시 중인 글 + 페르소나 공개 상태 + 차단 아님 + `posts` 공개 범위(`canViewActivityKind`, 활동 목록과 같은 판정) | `profile_post_id` |
| `social_link` | `{handle, url}` | 위 페르소나 판정 + 그 페르소나의 숨기지 않은 같은 주소 링크 | `social_link_id` |

- `reports`·`moderation_actions`에 세 열을 더했고 **외래 키가 없습니다**: 탈퇴 정리가 그 사람만의 자료(페르소나·글·링크)를 지워도 신고·조치 기록은 남아야 합니다(운영 화면은 "찾을 수 없음"). **주인 사용자 id는 어느 행에도 두지 않습니다** — 프로필 글·링크 신고에도 그 페르소나 id조차 함께 두지 않고 대상 하나만 가리킵니다.
- 대상 키 `persona:<id>`·`profile_post:<id>`·`social_link:<id>`. 같은 사람의 실명·표시명 프로필은 서로 다른 묶음입니다(대기열에서 합쳐지지 않음 — 합쳐지면 운영자 화면이 연결을 알려 줌).
- 이름표(신고자 `내 신고`, 운영자 대기열, 당사자 안내)는 **그 페르소나 자신의 handle**뿐입니다: `공개 프로필 @d-… (표시명)`, `프로필 글 · @…`, `소셜 링크 · @…`. 신고자 응답(접수 영수증·내 신고)에 주인 사용자·다른 페르소나는 없습니다(테스트).
- 기존 `profile`(사용자 단위, 실명 프로필만)은 이전 신고·API 호환으로 남기고 화면은 `persona`를 씁니다. 같은 실명 프로필이 두 묶음이 될 수 있는 것은 감수했습니다(새 화면은 `profile`을 보내지 않음).
- 순서·중복·한도는 ADR 0015 그대로(검증 422 → 대상 404 → 중복 200 → 한도 429 → 201).

### 2. 운영 조치: 그 페르소나·글·링크 하나만

| 조치 | 효과 | 되돌림(이의제기·해제) |
|---|---|---|
| `hide_persona` | 그 페르소나의 `profiles.hidden_at`. 공개 프로필·README 카드·활동·피드·팔로우 목록에서 다음 요청부터 빠짐. **같은 사람의 다른 페르소나는 그대로**(함께 사라지면 같은 사람임이 드러남, ADR 0028) | `hidden_at = null` |
| `hide_profile_post` | 글 published → hidden. 같은 트랜잭션의 트리거(0031)가 활동을 거둠 → 활동 목록·피드에서 다음 요청부터 빠짐. 숨긴 글은 본인이 지울 수 없음(409 `hidden`, 근거 보존) | hidden → published, 트리거가 원천을 다시 확인해 활동을 되살림 |
| `hide_social_link` | `social_links.hidden_at`(새 열). 공개 DTO에서 빠지고 본인 화면에는 "운영 조치로 숨김". 숨긴 동안 지울 수 없음(409 `hidden` — 지우고 같은 주소로 다시 붙여 조치를 피하지 못하게) | `hidden_at = null` |

- 모든 조치 행에 내부 메모(필수)·당사자 사유(선택, 알림이면 필수)가 있고, 감사 `moderation.apply`·`moderation.reverse`는 대상(페르소나·글·링크 id)과 `actionId`·`kind`·`notifyOwner` 플래그뿐입니다(메모·사유·handle·주소 없음, 테스트).
- 당사자 = 그 페르소나·글·링크의 주인(`personas.user_id` 등으로 그때 찾음). 안내 경로 `/settings/personas`. 이의제기는 ADR 0015 그대로(조치마다 한 번, 당사자만).
- **계정 단위 조치는 이 API에 없습니다.** 두 페르소나를 함께 숨겨야 하면 각 프로필의 신고로 따로 처리하고, 계정 정지는 운영 절차(RUNBOOK §4.5, 아래 주인 확인 뒤)로 합니다.

### 3. 운영자 화면과 주인 확인

- 신고 상세의 내용은 **신고된 페르소나 자신만**: 페르소나면 handle·이름·종류·숨김 여부·한 줄 소개·관심 직무·학교(본인 입력)·졸업 시기·그 페르소나의 소셜 링크(숨긴 것 포함), 글이면 그 글 본문·상태, 링크면 그 링크. 연결(identity_links)·다른 페르소나·계정 id·이메일은 읽지도 싣지도 않습니다(테스트: 표시명 신고의 대기열·상세 JSON에 실명 handle·계정 id·계정 이름 0건).
- **주인 확인** `POST /api/v1/operator/persona-owner-lookups {reportId, reason}`(커뮤니티 작성자 확인 ADR 0023과 같은 모양): 페르소나·프로필 글·소셜 링크 신고에만(아니면 422 `reportId: not_persona_target`), 사유 1~1000자 필수, 운영자 시간당 20건(429), 대상이 지워졌으면 409 `target_unavailable`. 한 트랜잭션에 `persona_owner_lookups`(운영자·신고·페르소나·확인된 주인·사유) + 감사 `persona.owner_lookup`(대상 페르소나, metadata `lookupId`·`reportId`뿐) 뒤 201로 주인 계정 id·상태·그 사람의 페르소나 전부(숨김 표시)·연결 공개 여부·걸린 숨김 조치 수를 줍니다. **결과는 이 응답에만** 있고 신고 상세·목록에 다시 나오지 않습니다. 탈퇴 정리는 확인 기록의 주인 칸만 비웁니다(접근 기록은 남음).
- **감사 조회로 우회하지 못하게**: 운영자가 조치 id → 감사의 대상 페르소나·링크 id → 그 id의 감사로 따라가면, 주인이 자기 페르소나에 남긴 행(`persona.create`·`persona.update`·`persona.identity_link_update`·`persona.visibility_update`·`persona.project_listing_update`·`social_link.*`·`social.block`·`social.unblock`)의 행위자로 주인 계정을 알 수 있었습니다. `GET /operator/audit`은 이 행들의 `actorId`를 비워 돌려줍니다(행 자체·DB는 그대로, 테스트). 커뮤니티 글 쓰기에 감사를 남기지 않은 ADR 0022와 같은 이유입니다.

### 4. 표시명 사칭 사유와 처리 기준

- 사유 `impersonation`(표시명 사칭)은 **프로필 신고(`persona`·이전 `profile`)에만** 고를 수 있습니다(@peerchive/domain `reasonApplicable`, 아니면 422 `reason: not_applicable`, DB check `reports_impersonation_check`). 신고 대화상자는 대상마다 고를 수 있는 사유만 보이고 짧은 기준을 함께 보입니다.
- 처리 기준(RUNBOOK §4.5에 공지 문구와 함께): 다른 **실존 인물**(교수·조교·다른 학생·졸업생·공인)이나 **학교·학과·기업·단체**로 오인하게 하는 이름·handle·소개·링크면 사칭. 이름이 비슷한 것만으로는 아님, 패러디·팬 계정은 프로필에 그 사실이 분명하면 아님, 실명 프로필의 본명은 사칭 판단 대상이 아님(신원 확인을 하지 않음). 확인되면 **그 프로필만 `hide_persona` + 당사자 사유**. 당사자가 이름·handle·소개를 고친 뒤 이의제기하면 운영자가 확인하고 되돌립니다(테스트: 고친 이름으로 다시 열림).
- handle 예약·강제 변경은 만들지 않았습니다(최소 범위). 숨김이 공개를 막고, 고치는 것은 당사자, 다시 여는 것은 이의제기입니다. 반복되면 §6.2의 판단(표시명 프로필에 기관 인증 배지 필수화)을 지표로 봅니다.
- 소셜 링크의 "확인됨"(ADR 0034)을 남의 페이지에 링크를 넣어 얻은 경우도 `social_link` 신고 → `hide_social_link`로 다룹니다.

### 5. §6.2 분석 이벤트: 사용자 키 + 시 단위 시각, 페르소나 id 없음

| 이벤트 | 어디서 | props |
|---|---|---|
| `persona_created` | 실명 프로필을 처음 만들 때(`upsertProfile`)·표시명 페르소나 | `kind: real/display` |
| `identity_link_toggled` | `PUT /me/identity-link`(바뀔 때만) | `visible` |
| `visibility_changed` | 공개 범위 저장(바뀐 항목마다) | `itemKind`, `audience` |
| `project_listed` | 과제 수행 목록 올림·내림(바뀔 때만) | `listed` |
| `follow_requested` | 새 팔로우 행 | `targetKind`(대상 페르소나 종류), `pending`, `origin: profile/suggestion`(추천 목록에서 온 팔로우) |
| `follow_approved` | 요청 승인(하나·한꺼번에) | `bulk` |
| `follower_removed` | 승인된 팔로워 삭제 | — |
| `block_created` | 차단 | `scope` |
| `mute_created` | 새 뮤트 | — |
| `feed_item_opened` | 피드 항목 링크를 열 때 화면이 `POST /api/v1/feed/opened {activityId}`(서버가 활동 행의 원천 종류만 읽음, 없는·거둔 활동은 조용히 넘김, 시간당 300) | `sourceType` |
| `social_link_verified` | worker 수집기가 unverified·lost → verified로 바꾼 순간(재확인 유지는 세지 않음) | `provider` |

- **키 결정**: 모두 사용자 키(`actor_hash`)로 기록하고, **페르소나 id·handle·상대 페르소나·상대방 사용자 키는 허용 목록에 자리가 없습니다**(테스트: 페르소나 id·handle·키를 넣으면 이벤트 전체 거부, 실제 흐름의 이벤트 JSON에 0건). 사람 단위 핵심 지표("피드 사용자 중 도움됐어요·포크를 남긴 비율", "공개 프로필 보유자 중 표시명을 만든 비율")가 사용자 키를 요구하기 때문입니다.
  - 고려한 대안 "페르소나 이벤트는 페르소나별 pepper 키": 같은 사람의 두 페르소나 행동을 분석가가 잇지 못하는 장점은 있지만, 사용자 키 이벤트(기록 활용·포크)와 페르소나 키 이벤트(피드 열기)를 잇지 못해 핵심 지표를 잴 수 없고, 두 키를 함께 남기면 그 자체가 연결표가 됩니다.
  - 그래서 **이벤트만으로는 "이 사용자 키 = 이 표시명 페르소나"를 알 수 없습니다**: 페르소나를 가리키는 값이 없고, 알 수 있는 것은 "이 키의 사람이 표시명 페르소나를 만들었다"(종류)뿐입니다. 팔로우 이벤트에는 내가 어느 페르소나로 팔로우했는지(행위 페르소나 종류)도 넣지 않았습니다.
  - 남는 위험은 **시각으로 운영 테이블과 잇는 것**(예: `follows.created_at`과 같은 순간의 `follow_requested`)입니다. 분석 접근권한은 `analytics_events`만이라는 전제(ADR 0016) 위에, 이 11개 이벤트는 **시각을 시 단위로 내립니다**(`socialEventTime`, web `emitSocialAnalytics`·worker `emitWorkerAnalytics({social: true})`). 지표는 모두 기간 단위라 손실이 없습니다.
- **0~1단계(익명) 글**: 피드·활동에는 익명 글이 투영 경로부터 없으므로(S-02) `feed_item_opened`가 익명 글을 가리킬 수 없습니다. 익명 글·댓글·공감·신고 이벤트의 키 없음(`unlinked`, ADR 0027)은 그대로입니다. 이번 신고 대상(페르소나·글·링크)은 모두 2~3단계라 신고 분석 이벤트를 새로 두지 않았고, 사칭 신고 수 등은 운영 기록에서 셉니다.
- 수집 거부·탈퇴 정리·pepper 교체 규칙은 ADR 0016 그대로입니다(거부하면 지난 이벤트도 지우고 이후 0건, 테스트).

### 6. 운영자 지표: 공개 프로필·팔로우 칸

`GET /api/v1/operator/metrics`에 `profile`(@peerchive/domain `computeProfileMetrics`)을 더했습니다. 사람 행동은 이벤트(키 있는 것만 사람으로 셈), 운영 기록(페르소나·글·링크·실명 프로필 신고와 그 처리, 주인 확인 수)과 지금 상태(활성 팔로우 수, 공개 페르소나의 종류·팔로워 수 표시 설정)는 개수로만 셉니다. **모든 칸 5 미만 null**, 비율은 분자·분모 중 하나라도 가려지면 null.

| 지표(§6.2) | 정의 |
|---|---|
| 팔로우 → 기록 활용(핵심) | 기간 안에 피드 항목을 연 사람 중 같은 기간에 도움됐어요·포크를 남긴 사람(이벤트끼리 잇지 않은 기간 근사) |
| 피드 구성 | 연 항목 중 기록(공개 사례·선배 노트·스터디 기록) 비율(노출 수는 재지 않아 연 항목으로 근사) |
| 표시명 사용 | 기간 안에 실명 프로필을 만든 사람 대비 표시명 페르소나를 만든 사람, 연결 켜기·끄기 수 |
| 표시명 사칭 | 표시명 페르소나 대상 사칭 신고 수와 그중 숨김으로 확정(되돌리지 않음)된 수 |
| 팔로워 수 표시 | 지금 공개 페르소나 중 팔로워 수 표시를 켠 비율 |
| 소셜 링크 유입 | 확인 이벤트 수와 확인을 얻은 사람 수(외부 링크 경유 방문은 재지 않음) |
| 차단·뮤트·팔로워 삭제 | 개수와 지금 활성 팔로우 1,000건당 |
| 그 밖 | 대상별 신고 수, 팔로우 요청(대기·추천 출처)·승인 수, 공개 범위·과제 수행 목록 변경 수, 주인 확인 수 |
| 정체성 누출(필수) | 이벤트로 재지 않음 — S-02 속성 테스트와 사고·신고 기록(RUNBOOK GP) |

화면 `/operator/metrics`에 표와 목록으로 보입니다. 사람·페르소나 id는 응답에 없습니다.

### 7. 화면

- `/u/:handle`(실명·표시명 모두): 바닥글 "신고하기" — 대상은 이 프로필(`persona`)과 이 프로필의 소셜 링크 하나하나, 실명 프로필이면 대표 케이스. 활동 목록·피드의 남의 프로필 글마다 "이 글 신고"(같은 대화상자). 피드 항목 링크를 열면 `feed_item_opened`, 추천 목록 링크는 `?from=suggestion`을 붙여 팔로우 출처만 알립니다.
- `/settings/personas` 소셜 링크 편집: 숨긴 링크 안내·지우기 비활성. `/operator/reports/:id`: 페르소나 내용과 "주인 확인(계정 단위 조치가 필요할 때만)"(`OperatorPersonaLookup`). `/operator/metrics`: 공개 프로필·팔로우 칸.

## 결과

- 표시명 프로필을 신고·숨길 수 있게 되었고, 그 과정의 어느 화면(신고자·운영자 대기열·상세·공개 경로)도 실명 페르소나와 잇지 않습니다. 잇는 길은 사유를 남기는 주인 확인 하나이고 감사에 남습니다.
- 숨김은 페르소나·글·링크 하나에만 걸리고 이의제기로 되돌아옵니다. 프로필 글은 0031 트리거 덕분에 상태 한 줄로 활동·피드에서 빠지고 되살아납니다.
- §6.2 P1 이벤트 11개와 운영자 지표 칸이 생겼습니다. 이벤트에는 페르소나를 가리키는 값이 없고 시각은 시 단위입니다.
- S-02 경계: 새 소셜 라우트(`POST /feed/opened`)는 이름으로 경계 검사에 자동 포함되고 커뮤니티 코드에 닿지 않습니다. moderation 모듈이 social 모듈의 공개 판정(`resolvePublicPersona`·`reportableProfilePost`·`reportableSocialLink`·`isHiddenFrom`)을 import합니다(반대 방향은 없음). social DB 역할 권한은 바꿀 필요가 없었습니다(`social_links`·`profile_posts`는 테이블 단위 SELECT라 새 열도 읽히고, 새 표는 운영 기록). 신고·지표는 새 공개 출력을 만들지 않아 S-02 속성 테스트는 넓히지 않았습니다.
- 테스트: 도메인 `profile-metrics.test.ts`(대상·사유 규칙, 이벤트 허용 목록에 id·handle 자리 없음, 시 단위 시각, 지표 계산·가림), `analytics.test.ts`(이벤트 46개), web `persona-reports.integration.test.ts`(대상별 신고·숨김·되돌림, 다른 페르소나 영향 없음, 신고자·운영자 응답에 연결 0건, 주인 확인 사유·감사, 감사 조회 행위자 비움, 차단당한 신고자 404, 이벤트 키·props·시각·수집 거부, 지표 가림), 기존 S-04 테스트의 "다른 표에 행 없음"에 분석 이벤트 한 줄을 더함·S-06 테스트의 본인 링크 DTO에 `hidden`, worker `social-links.test.ts`(verified 전환 이벤트 한 번, 수집 거부)·`ops-purge.test.ts`(주인 확인 기록의 주인 칸 비움), E2E `s07-persona-reports`.
- 한계·후속:
  - **이전 `profile` 대상**이 남아 같은 실명 프로필이 두 묶음이 될 수 있습니다. 화면은 보내지 않으므로 파일럿 뒤 API에서 받지 않게 할 수 있습니다.
  - **계정 단위 조치**(정지)는 API가 없고 운영 절차입니다. 두 페르소나를 함께 숨기는 조치도 없습니다(각 신고로).
  - 숨긴 페르소나·글·링크의 신고 때 내용은 따로 보관하지 않습니다(최소 저장, ADR 0015와 같음). 본인이 그 사이 고치면 운영자는 지금 내용을 봅니다.
  - 감사 조회의 행위자 비움은 API 응답에서만입니다. DB에 직접 접근하는 운영자는 감사 행으로 잇습니다(운영 DB 접근은 RUNBOOK의 별도 권한).
  - 시 단위 시각은 시간 상관을 줄일 뿐 없애지 못합니다(팔로우가 드문 시간대). 분석 접근권한을 이벤트 표로 한정하는 운영 규칙이 함께 필요합니다.
  - 피드 노출 수·외부 링크 경유 방문은 재지 않습니다(페이지 조회 추적 없음, ADR 0027과 같은 원칙).

## 대안

- **표시명 신고도 사용자 단위로 받고 운영 화면에서만 가리기**: 저장은 단순하지만 조치가 사용자 단위라 숨김이 실명 프로필에 걸리고, 조회 하나만 빠뜨려도 실명 handle이 붙습니다. 페르소나 열을 따로 둡니다.
- **신고·조치 행에 주인 사용자 id도 함께 저장**: 당사자 찾기·지표가 쉽지만 운영 기록 자체가 페르소나 ↔ 계정 연결표가 됩니다. 당사자는 그때 페르소나 행으로 찾습니다.
- **주인 확인 없이 운영자에게 연결을 늘 보여 줌**: 처리가 빠르지만 §8.3의 "신고 처리 시 감사 기록과 함께"를 어기고 운영자 수만큼 연결이 새는 길이 됩니다.
- **페르소나 신고 시 계정 전체(두 페르소나) 숨김**: 사칭 대응은 강하지만 함께 사라지는 것이 연결 단서가 되고(ADR 0028), 한쪽 프로필의 문제로 다른 쪽 공개를 막습니다.
- **handle 예약·강제 변경 조치**: 사칭 handle을 다른 사람이 다시 쓰지 못하게 하지만, 예약어 관리·당사자 handle 강제 변경 화면·되돌림이 필요합니다. 파일럿은 숨김 + 사유 + 고친 뒤 이의제기로 충분하다고 봤습니다.
- **페르소나 pepper 키로 이벤트 기록**: 위 5절. 핵심 지표를 잴 수 없고, 두 키를 함께 두면 연결표가 됩니다.
- **피드 열기를 서버 쪽 리다이렉트로 계측**: 클라이언트 호출이 필요 없지만 피드 링크가 사이트 안 경로라 리다이렉트 경로·캐시·접근성 처리가 늘어납니다. 활동 id만 보내는 작은 POST로 충분합니다.
