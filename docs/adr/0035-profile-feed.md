# 0035. 프로필 글·활동 목록·팔로우 피드·추천: 같은 트랜잭션에서 투영하는 프로필 글 + outbox로 투영하고 원본 트리거로 거두는 페르소나 활동 + 원본을 다시 보는 SECURITY DEFINER 카드 함수 + social DB 역할로 읽는 피드 + 하루 단위 기록 우선 순서 + 교집합만 세는 추천

- 상태: 채택
- 날짜: 2026-10-28

## 맥락

S-05는 DELIVERY_PLAN §4.2의 다섯째 항목입니다: "읽기 시점 권한·원본 상태 재검사, 철회·숨김·차단·공개 범위 축소가 다음 요청부터 반영. 인기 순위·팔로워 수 정렬 없음, 추천은 과목·기관·관심 직무 교집합. 피드는 기록(사례·노트·스터디) 우선". 수용 시나리오는 §5.2 Q(익명 글이 활동 목록·피드·추천 어디에도 없음, 방이 실명으로 바뀐 뒤에도 이전 익명 글은 없음, 아카이브로 옮기며 표시명을 고르면 복사본만), S 마지막 문장(공개 사례를 철회하면 다음 요청부터 프로필 목록과 팔로워 피드에서 빠짐), T(승인 전에는 기본 정보만, 승인 뒤 `승인한 팔로워` 범위의 글). 관련 설계:

- SYSTEM_DESIGN §6.7.1 `ProfilePost(id, persona_id, body, media_version_ids[], status, created_at)` — "미디어는 §10 파일 검사를 거친 버전만, 노출은 `posts` 공개 범위". `PersonaActivity` — "공개 프로필의 활동 목록과 팔로우 피드가 읽는 유일한 원천, 원본 모듈이 outbox로 투영, 숨김·삭제·철회·이름 표시 재선택 시 같은 트랜잭션의 outbox로 `withdrawn_at`을 채움". "추천은 같은 과목·기관·관심 직무의 교집합으로만, 팔로워 수·활동량으로 정렬하지 않음".
- §8.3 불변조건 1: "공개 프로필·팔로우 목록·팔로우 피드·팔로우 추천·알림은 모두 `PersonaActivity`·`Persona`·`Follow`와 공개 release 뷰만 읽음", social DB 역할에 커뮤니티 글 SELECT 권한 없음. "커뮤니티 글은 listed 공간의 글이라도 열람자가 `canReadSpace`를 통과할 때만 프로필에 보임". §8.3 표: 공개 사례 목록은 "공개 release만(비공개 계정이면 불가)", 글·노트·스터디는 공개 범위.
- §11.3: 피드는 쓰기 시점 fan-out 없이 읽기 시점에 `Follow` × `PersonaActivity`를 조인하고 항목마다 `canViewPersonaItem`과 원본 상태를 다시 확인. worker가 늦어도 읽기 경로의 원본 재확인이 먼저 막음.
- ADR 0029(S-02): `persona_activities`·도메인 규칙 `decidePersonaActivityProjection`·투영 트리거·social 역할·쓰기 도우미. 후속으로 S-05에 남긴 것: 원본 모듈 투영·철회 연결, 읽기 시점 재확인, 앱이 social 역할로 읽기. ADR 0031(공개 범위)·0033(팔로우·차단·뮤트: 뮤트는 피드·알림에서만, 거절·삭제·차단·뮤트는 알리지 않음, 팔로우 요청 알림은 S-05로 미룸).
- 지금 코드: 앱 안 알림 장치는 커뮤니티 알림(`community_notices`, 커뮤니티 구역 테이블)과 운영 조치 안내(조치 행에서 계산)뿐이고 소셜용 알림 표는 없습니다. 파일 검사 파이프라인은 과제 산출물(프로젝트 소속) 전용입니다.

## 결정

### 1. 프로필 글(`profile_posts`, migration `0031_profile_feed`)

- 열: `id`, `persona_id`·`user_id`(복합 외래 키로 주인 사본), `body`(1~500자, 지우면 빈 문자열), `media_version_ids uuid[]`(**빈 배열만** — check), `status`(published/deleted/hidden), `created_at`, `deleted_at`. 실명·표시명 어느 페르소나에도 씁니다(공개 프로필이 있어야, 없으면 409 `profile_required`).
- API: `POST /personas/:id/posts {body}`(201, 남의 페르소나 404, 422 `body: required|too_long`, `mediaVersionIds`에 무엇이든 넣으면 422 `not_supported`, 사용자당 시간당 20건 429), `DELETE /personas/:id/posts/:postId`(204, 본문 비움·멱등, 운영 숨김 글은 409 `hidden`). 감사·알림 없음(일상 글쓰기, 팔로우와 같은 기준).
- **투영은 같은 트랜잭션에서**: 프로필 글은 social이 소유한 원천이라 outbox를 거치지 않고 `projectPersonaActivity`로 바로 넣습니다(규칙 `profile_post`는 이제 "자기 페르소나 + 게시 중"). 쓰자마자 내 프로필·팔로워 피드에 보이고 E2E가 worker를 기다리지 않습니다.
- 운영 숨김(hidden)의 API는 S-07(신고 대상 추가)입니다. 상태만 바꾸면 아래 트리거가 활동을 거둡니다.
- **미디어는 이번 범위에서 뺐습니다**(아래 결과·후속): 지금 파일 검사·저장소는 과제 공간 산출물에 묶여 있어(업로드 의도·권한·공개 판정이 프로젝트 단위) 프로필용 업로드 경로와 공개 서빙 규칙을 새로 세워야 합니다.

### 2. 투영: 원본 모듈이 outbox, worker가 지금 원본 행으로 판정

- 새 outbox 주제 `persona_activity.project`(payload는 `{sourceType, sourceId}`, 커뮤니티 글만 `personaId`·`occurredAt`를 더함 — id·시각뿐). 원본을 처음 공개하는 트랜잭션에서 원본 모듈이 남깁니다.
  - 커뮤니티 글(`community/posts.ts` `createPost`): 커뮤니티 모듈이 **자기 행으로 `decidePersonaActivityProjection`을 판정**해(real·display + 작성 시점 페르소나 + listed + 게시 중) 통과할 때만, 그 페르소나와 작성 시각을 넣습니다. **익명 글은 이벤트 자체가 없습니다**(§8.3 "0~1단계는 투영 경로 자체가 없음"). worker는 커뮤니티 테이블을 읽지 않습니다(C-05 경계 "worker 파생 처리기는 커뮤니티 코드·테이블에 닿지 않음"을 그대로 지킴).
  - 선배 노트(`publishSeniorNote`): 익명이 아닐 때만. 아카이브로 옮겨 온 초안도 여기서 게시되므로 **복사본 노트만** 투영됩니다(시나리오 Q).
  - 공개 사례·스터디 release(`publishCandidate`): 스냅샷이 익명 스터디 방이 아닐 때, 종류에 따라 `publication_release`/`study_release`.
- worker 처리기(`apps/worker/src/persona-activities.ts`): 선배 노트·release는 원본 행을 FOR SHARE로 다시 읽고(노트 작성자의 같은 종류 페르소나, release의 granted 동의 당사자마다 실명 페르소나) `decidePersonaActivityProjection`, 커뮤니티 글은 넘겨받은 페르소나로. INSERT는 어느 쪽이든 `persona_activity_source_ok`를 통과할 때만 하므로(그 사이 원본이 지워졌으면 0행, 재시도로 실패를 되풀이하지 않음) DB 트리거와 함께 원본 행으로 두 번 확인됩니다. 이미 있고 거둔 행은 원천이 다시 공개 상태일 때만 되살립니다. 이벤트 내용은 id뿐이라 늦거나 중복돼도 결과가 같습니다. social 모듈과 같은 일을 하지만 worker는 웹 모듈을 import할 수 없어 도메인 규칙과 DB 트리거를 공유합니다.
- 기존 투영 트리거(0027)의 원천 판정을 `persona_activity_source_ok(persona, type, source)`(SECURITY DEFINER) 한 함수로 옮기고 프로필 글 규칙을 더했습니다. 투영 INSERT, **거둔 행 되살리기(withdrawn_at → null)**, 읽기 시점 재확인이 모두 이 함수를 거칩니다(되살리기도 원천을 다시 확인 — 지운 글을 SQL로 되살릴 수 없음).

### 3. 거두기: 원본 상태가 바뀌는 같은 트랜잭션의 DB 트리거

- 설계 문구 "같은 트랜잭션의 outbox로 `withdrawn_at`을 채움"의 목적(원본 변경과 거두기가 갈라지지 않음)을 **outbox 대신 원본 테이블의 AFTER UPDATE 트리거**로 이룹니다: `community_posts.status`(작성자 삭제·운영 숨김·임시 숨김), `community_spaces.discovery`(listed를 떠남), `senior_notes.status`(철회·고쳐서 draft·운영 숨김), `publication_candidates.status`(철회·대체·공개 제한), `consents.status`(granted → 철회: 그 당사자 페르소나의 활동만), `profile_posts.status`. 공개 상태로 돌아오면(운영 숨김 해제, 고친 노트 다시 게시, listed로 되돌림) 원천을 다시 확인해 통과하는 행만 되살립니다.
- 이유: 거두기 경로는 웹·worker(이름 표시 방식 적용·탈퇴 정리)·운영 조치·운영 SQL에 흩어져 있어 코드마다 연결하면 하나만 빠져도 철회된 항목이 남습니다. 트리거는 경로와 무관하고 worker 지연이 없습니다. outbox 이벤트를 따로 두면 같은 일을 늦게 한 번 더 할 뿐이라 두지 않았습니다.
- 이 트리거는 DB에 있고 social 모듈 코드가 아닙니다(경계 테스트는 TS 소스의 import·이름을 봄). 새 함수 셋(`persona_activity_source_ok`·`persona_activity_cards`·`persona_activities_sync`)은 PUBLIC 실행 권한을 거뒀습니다. 웹·worker는 migration과 같은 `DATABASE_URL` 계정(= 테이블·함수 주인)으로 붙으므로 그대로 부르고, social 역할에는 카드 함수만 줍니다. 앱 계정을 주인과 다른 계정으로 나누는 날에는 그 계정에 이 함수들의 EXECUTE를 줘야 합니다(RUNBOOK §1).

### 4. 읽기 시점 재확인: SECURITY DEFINER 카드 함수 하나

- social 모듈은 커뮤니티 글·선배 노트·공개 후보 테이블을 읽을 수 없으므로(§8.3, import 경계 + DB 역할), 원본 상태와 카드 내용은 **`persona_activity_cards(viewer uuid, ids uuid[])`** 하나로만 얻습니다(SECURITY DEFINER, search_path 고정, social 역할에만 EXECUTE). 넘긴 활동 중 **지금 보여도 되는 것만** 한 줄씩 돌려줍니다:
  - 모든 원천: 거두지 않음 + `persona_activity_source_ok`(게시 상태·동의·익명 아님·작성 시점 페르소나·listed) + 페르소나·계정 active + 프로필 운영 숨김 아님. **worker가 늦어 withdrawn_at이 비어 있어도 원본이 숨김·삭제·철회면 빠집니다**(트리거를 끈 채 원본만 숨겨 확인하는 테스트).
  - 커뮤니티 글: 보는 사람이 그 공간을 읽을 수 있을 때만 — @peerchive/domain `canReadSpace`와 같은 규칙(active 계정, 공식 페이지는 운영자 또는 그 정본 학교 인증, 사용자·스터디 방은 active 멤버 + 학교 자격). 비로그인은 0건.
  - 공개 사례·스터디 release: 지금 그 공개의 게시 중 release일 때만.
  - 카드 내용: 프로필 글 본문 / 커뮤니티 글 제목·공간 이름·`/community/p/:id` / 선배 노트의 과목 이름·학기·`/c/:courseId`(**노트 본문·원 글 연결 없음**) / release 제목·요약 앞 200자·학기·`/p/:slug`. 작성자 계정 id·원 글 id·이메일 없음.
- 고른 대안 "활동 행에 원본 상태 열을 두고 같은 트랜잭션에서 갱신"보다 함수가 나은 점: 커뮤니티 글의 열람 판정은 보는 사람마다 달라 열로 미리 둘 수 없고, 카드 내용을 social이 따로 읽을 길도 필요합니다. 함수는 결과를 활동 id로만 묶고, 투영 규칙과 같은 판정 함수를 씁니다.
- 함수 안의 `canReadSpace` 복제는 도메인 함수와 어긋날 수 있습니다(한계). 지금은 S-02 속성 테스트(본인 눈의 활동 API가 정확히 "작성 시점 페르소나·같은 방식·listed 글"과 같음)와 통합 테스트가 덮고, `canReadSpace`를 바꾸면 이 함수도 고쳐야 합니다(아래 후속).

### 5. 활동 목록 `GET /profiles/:handle/activity?kind=&cursor=`

- 세션을 읽는 경로입니다(공개 화면 `/u/:handle`은 SSR 뒤 브라우저에서만 부름 — 보는 사람에 따라 달라지는 목록이 SSR HTML·payload에 없음). 차단당한 사용자·없는 handle 404, 모르는 kind·cursor 422.
- 종류별 열람은 @peerchive/domain **`canViewActivityKind`**: `posts`(프로필 글·커뮤니티 글)·`notes_and_studies`(선배 노트·스터디 기록)는 그 공개 범위(`canViewPersonaItem`), `cases`(공개 사례)는 공개 범위 설정의 대상이 아니라 공개 절차만 — 단 §8.3 표대로 **비공개 계정이면 승인된 팔로워·본인에게만** 목록에 나옵니다(공개 URL은 그대로). 응답 `kinds`는 보는 사람이 볼 수 있는 종류뿐(이유를 밝히지 않음). 뮤트는 활동 목록에 영향이 없습니다.
- 최근 순, 20개씩, cursor는 (시각, 활동 id). 재확인에서 빠지는 행이 있어도 페이지를 채우도록 최대 5번 더 읽고, 마지막으로 **본** 행을 cursor 기준으로 씁니다.
- 본인에게만 프로필 글의 `profilePostId`(지우기용)를 싣습니다.

### 6. 팔로우 피드 `GET /feed?cursor=`

- **사용자 단위 피드**: 내 모든 페르소나의 active 팔로우를 합칩니다. 응답은 나에게만 보이므로 내 두 페르소나가 이어져 드러날 상대가 없습니다(페르소나별 피드로 나누면 화면만 복잡해짐). 
- 팔로우 대상마다: 공개 상태(페르소나·계정 active, 프로필 숨김 아님), **차단** — 주인이 나를 차단해 그 페르소나가 숨겨졌거나, 내가 **바로 그 페르소나**를 차단했으면 제외(같은 사람의 다른 페르소나 차단으로 거르면 두 페르소나가 같은 사람임을 알려 주게 됨, ADR 0033과 같은 원칙), **뮤트한 페르소나 제외(피드만)**. 보는 사람은 그 페르소나의 승인된 팔로워이고(active 팔로우), 같은 기관은 두 사람의 active 학교 인증으로 계산합니다. 종류마다 `canViewActivityKind`.
- 순서(@peerchive/domain `compareFeedKeys`, SQL도 같은 식): **한국 시간 하루 단위로 최근 날 먼저 → 같은 날 안에서 기록(공개 사례·선배 노트·스터디 기록)이 글(프로필 글·커뮤니티 글)보다 먼저 → 최근 시각 → 활동 id**. "기록 우선"을 전체에 걸면 글이 영원히 기록 뒤로 밀리고 cursor 페이지가 시간과 어긋나므로 하루 창 안에서만 적용했습니다. **팔로워 수·공감 수·활동량은 쿼리에 없습니다**(테스트: 팔로워를 잔뜩 붙여도 순서 같음). cursor는 (날, 묶음, 시각, id).
- 쓰기 시점 fan-out·캐시가 없습니다. 철회·숨김·차단·공개 범위 축소·뮤트는 다음 요청부터 반영됩니다(설계의 `access_epoch` 캐시 무효화는 캐시를 두지 않아 필요 없음).
- 응답의 `following`은 팔로우 중인 수(뮤트 포함, 빈 피드 안내용).

### 7. 팔로우 추천 `GET /feed/suggestions`

- 신호 세 가지의 교집합 개수만: **같은 과목**(내가 active 멤버인 과제의 정본 과목 ∩ 상대의 과제 수행 목록 — 내가 그 목록을 볼 수 있을 때만, 익명·표시명 스터디 과제 제외), **같은 학교**(두 사람 모두 같은 정본 학교의 active 인증 + **상대가 실명 페르소나이고 학교 배지를 공개함** — 표시명 페르소나를 소속으로 추천하면 열람 성공 여부로 소속이 추정되고, 배지를 끈 사람을 같은 학교라는 이유로 추천하면 숨긴 소속을 알려 주게 됨), **관심 직무**(공개 프로필의 값, 대소문자·앞뒤 공백 무시, 실명·표시명 모두).
- 점수 `3×min(과목,3) + 2×학교 + min(직무,3)`(@peerchive/domain `suggestionScore`), 0이면 빼고, 동점은 `sha256(보는 사람, 페르소나)` — 보는 사람마다 고정, handle 알파벳·팔로워 수 편향 없음. 최대 10개.
- 제외: 나, 이미 팔로우(요청 포함, 내 어느 페르소나로든), 내가 차단·뮤트한 바로 그 페르소나, 나에게 차단으로 숨겨진 페르소나, 공개 상태가 아닌 페르소나. **한 사람의 페르소나는 하나만**(두 프로필을 나란히 추천하면 같은 사람임을 짐작할 수 있음). 비공개 계정도 기본 정보는 공개라 추천에 나오고(`accountPrivacy`로 표시), 응답은 handle·이름·종류·공개 여부·이유뿐입니다.

### 8. social DB 역할로 읽기(ADR 0029 후속)

- 활동 목록·피드·추천은 `withSocialRole`(`social/db-role.ts`)로 트랜잭션을 열고 `SET LOCAL ROLE peerchive_social`로 바꾼 뒤 읽습니다(끝나면 `RESET ROLE` — 테스트의 바깥 트랜잭션 안에서도 역할이 새지 않게). 역할에는 커뮤니티·원천 테이블 권한이 없으므로 코드가 실수로 그 표를 읽으면 42501입니다(import 검사와 별개의 두 번째 겹, 테스트).
- `PEERCHIVE_SOCIAL_DB_ROLE`(기본 `peerchive_social`). `off`는 개발·테스트에서만 전환을 끄고, **production은 무시하고 늘 전환합니다 — 역할이 없거나 앱 계정이 멤버가 아니면 요청이 실패(fail closed)**. 운영은 `GRANT peerchive_social TO <앱 계정>`(RUNBOOK §1). 로컬 docker의 앱 계정은 슈퍼유저라 그대로 됩니다.
- 공개 포트폴리오 경로(`portfolio/public-profile.ts`)는 여전히 테이블 주인 권한으로 읽습니다(판·케이스·release를 읽어 역할에 원천 테이블을 줘야 함, ADR 0029 §2). 이번에는 새 읽기 경로만 역할로 돌렸습니다.
- 권한: `peerchive_apply_social_grants()`를 다시 정의해 `profile_posts` SELECT와 `persona_activity_cards` EXECUTE를 더하고 다시 불렀습니다. `persona_activity_source_ok`·`persona_activities_sync`는 실행 권한이 없습니다(테스트).

### 9. 알림은 미룸

- "팔로우 요청 받음"·"팔로우한 사람의 새 글" 알림은 만들지 않았습니다. 앱 안 알림 장치가 커뮤니티 알림(커뮤니티 구역 테이블 — social이 쓸 수도 읽을 수도 없음)뿐이라 소셜용 알림 표·화면·읽음 처리·탈퇴 정리를 새로 세워야 하고, §8.3의 "알림도 PersonaActivity만 읽음"과 차단·뮤트 규칙을 함께 정해야 합니다. 대기 중인 팔로우 요청 수는 이미 `/me/personas`(`pendingFollowRequests`)와 팔로우 관리 화면에 보입니다. 거절·삭제·차단·뮤트에 알림이 없다는 ADR 0033의 약속은 그대로입니다.

### 10. 탈퇴 정리·화면

- worker purge: 페르소나 활동 삭제 뒤 그 사람의 프로필 글(지운 글 포함)을 지우고(장부 `profile_posts`), 그다음 페르소나를 지웁니다.
- 화면: `/u/:handle`의 "활동"(브라우저에서만, 볼 수 있는 종류만 탭, 더 보기, 본인이면 글쓰기·지우기, 404면 "찾을 수 없음"), `/feed`(피드 + 추천과 이유, 로그인 필요), 머리 메뉴 "피드".

## 결과

- 페르소나 활동의 원천 다섯 가지가 모두 연결됐습니다: 프로필 글(같은 트랜잭션), 커뮤니티 글·선배 노트·공개 사례·스터디 release(outbox → worker). 거두기는 원본 상태가 바뀌는 같은 트랜잭션의 트리거이고, 읽기는 그와 별개로 원본을 다시 봅니다 — 둘 중 하나가 빠져도 철회·숨김 항목이 보이지 않습니다.
- S-02 속성 테스트를 넓혔습니다: 원본 모듈의 outbox를 worker 처리기로도 처리하고(익명 글 이벤트 0건), 모든 페르소나의 활동 API(비로그인·본인·다른 모든 사람의 눈), 모든 사람의 피드·추천에 익명 글의 id·본문·해시·시각 0건, 피드 작성자는 내가 팔로우한 페르소나뿐, 추천에 내 페르소나·한 사람의 두 페르소나 없음, 본인 눈의 활동 API = 기대 글 집합.
- 테스트: 도메인 `feed.test.ts`(본문 정규화·종류별 열람·피드 순서·cursor·추천 점수), `persona-activities.test.ts`(프로필 글 게시 상태), web `feed.integration.test.ts`(원천별 투영·거두기·되살리기, worker 지연 재확인, 시나리오 Q·S, 차단·뮤트·공개 범위 축소, 비공개 계정, 인기 정렬 없음, cursor, 추천 규칙, 역할 설정), 경계 테스트(새 라우트·모듈 자동 포함, 역할 권한·함수 실행 권한, 역할 안에서 커뮤니티·원천 테이블 42501), worker `persona-activities.test.ts`·`ops-purge`(프로필 글), E2E `s05-feed`.
- 한계·후속:
  - **프로필 글 미디어**: 빈 배열만 받습니다. 프로필용 업로드(검사를 통과한 버전만, 공개 서빙·EXIF 제거·탈퇴 정리)를 따로 정해야 합니다.
  - **알림**(§9): 소셜 알림 표·화면은 후속입니다.
  - **운영 숨김 API·신고 대상**: 프로필 글 신고·숨김은 S-07. 상태만 바꾸면 거두기는 이미 됩니다.
  - **카드 함수의 `canReadSpace` 복제**: 도메인 함수를 바꾸면 SQL도 고쳐야 합니다. 커뮤니티 C-05 계열 테스트에 대조 테스트를 두는 것이 다음 단계입니다.
  - **추천의 과목 신호**는 과제 수행 목록(기본 비공개)만 봅니다. 공개 release의 과목을 쓰려면 social 역할에 공개 release 뷰가 필요합니다(공개 포트폴리오 경로를 역할로 옮길 때 함께).
  - 공개 사례 활동은 게시 이후의 release만입니다(이 migration 전에 게시된 release는 다음 게시 때부터 투영 — 빈 파일럿 DB에서는 없음). 필요하면 운영 명령으로 기존 release에 outbox 행을 넣으면 됩니다.
  - listed가 아닌 공간에서 쓴 글은 나중에 공간이 listed가 되어도 투영하지 않습니다(작성자가 목록에 없는 공간이라 여기고 쓴 글을 프로필로 끌어올리지 않음). listed → unlisted → listed는 되살립니다.

## 대안

- **거두기도 outbox → worker**: 설계 문구에 가깝지만 worker가 늦는 동안 행이 남고(읽기 재확인이 막긴 함), 거두기 경로마다 이벤트를 넣어야 해 하나가 빠지기 쉽습니다. 트리거는 경로와 무관하게 같은 트랜잭션입니다.
- **원본 상태 열을 활동 행에 미러링**: 읽기가 단순하지만 커뮤니티 글의 열람 판정(보는 사람마다)과 카드 내용은 여전히 다른 길이 필요합니다.
- **social 역할에 원천 테이블 SELECT**: 가장 단순하지만 익명 노트 작성자·커뮤니티 글 전체를 읽을 수 있게 되어 §8.3의 역할 분리가 무너집니다.
- **프로필 글도 outbox로 투영**: 원천이 하나로 같아지지만 쓴 글이 worker가 돌 때까지 내 프로필에 없고, social이 소유한 원천이라 얻는 것이 없습니다.
- **페르소나별 피드**: 표시명으로 팔로우한 것과 실명으로 팔로우한 것을 나눠 보여 줄 수 있지만, 피드는 나에게만 보여 분리로 막을 누출이 없고 화면이 복잡해집니다.
- **전체 기록 우선(기록 전부 → 글 전부)**: 계획 문구를 글자 그대로 따르지만 글이 끝없이 밀리고 페이지가 시간과 어긋납니다. 시간 창 끼워 넣기(예: 기록 2개마다 글 1개)는 규칙이 설명하기 어렵습니다.
- **추천에 표시명 페르소나도 같은 학교로**: 후보가 늘지만 소속 추정 경로가 생깁니다. 배지를 끈 실명 페르소나도 같은 학교로 추천하면 숨긴 소속이 드러납니다.
- **역할 전환이 실패하면 주인 권한으로 물러서기**: 운영 설정 실수에도 화면이 돌지만, 권한 경계가 조용히 사라집니다. production은 실패로 둡니다.
