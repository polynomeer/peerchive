# 0047. 과목 허브 단계적 개방: 기본 꺼짐 P1 플래그 + 공개 사례·선배 노트 합계 기준(설정, 기본 3)을 요청마다 계산 + 허브 모음만 "준비 중"(내용 목록 없음) + 등록한 학생의 열림 알림(본인만, 읽을 때 한 번 기록) + 마친 학생의 선배 노트 요청 + 운영자 과목별 진행(공개 항목 수만)

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

E-02는 DELIVERY_PLAN §4.4 P1 보완 백로그의 두 번째 항목입니다: "공개 사례 + 선배 노트 합계가 기준(설정값, 초기 3) 미만이면 허브 비공개, 등록 학생에게 “준비 중”과 개방 알림 신청, 해당 과목을 마친 학생에게 선배 노트 요청, 기준 도달 시 다음 요청부터 공개". §4.4 머리말은 "pilot 근거가 필요한 개방은 기본 꺼짐 플래그 뒤"에 두라고 합니다. 관련 설계와 앞선 결정:

- PROOFU_EVOLUTION_PLAN §8.6(과목 허브 단계적 개방: 공개 사례·선배 노트가 기준 개수에 이르면 공개, 그 전에는 등록한 학생에게 준비 중·알림 신청, 마친 학생에게 선배 노트 요청), §8.7(이번 학기 과목 등록).
- ADR 0012(공개 읽기는 요청마다 DB 상태 확인), 0013(과목 허브·선배 노트·검색, `servableReleaseSql`·`courseScopeSql`), 0025(막힘 Q&A), 0029(S-02 경계 lint·social DB 역할), 0037(기능 플래그 helper), 0046(과목 등록: 본인만, 학기 종료 알림, 허브 수강 인원은 5명 이상만).

## 결정

### 1. 플래그: P1 영역 `hubStagedOpening`, 기본 꺼짐

- 기존 플래그 helper(ADR 0037)에 영역 하나를 더합니다: `PEERCHIVE_FEATURE_HUB_STAGED_OPENING`(`@peerchive/domain` `features.ts`, web `server/modules/features.ts`). 값 해석(`on`·`1`·`true`·`yes`)과 요청마다 읽기, `GET /api/v1/features`·`useFeatures()`는 그대로입니다.
- **P2 묶음 변수 `PEERCHIVE_FEATURE_P2`를 따르지 않습니다.** P2 영역(alumni·topics·institutions)과 P1 영역(`P1_FEATURE_AREAS`)을 나누고, P1 영역은 자기 변수만 봅니다. P2 GA 게이트와 단계적 개방은 서로 다른 운영 결정이기 때문입니다.
- 꺼져 있으면 **지금과 똑같습니다**: 모든 허브가 열려 있고 개수를 세지 않으며, 새 본인 API는 404, 홈 알림 영역은 그리지 않습니다. 기존 허브 테스트는 플래그 없이 그대로 통과합니다.
- 기준값 `PEERCHIVE_HUB_OPEN_THRESHOLD`: 1~100의 정수, 그 밖(빈 값·0·소수·글자)은 기본 3(§8.6 초기안, pilot에서 확정). 같은 helper가 요청마다 읽습니다.

### 2. 무엇을 세는가: 공개 사례 + 게시된 선배 노트(정본 과목)

- **공개 사례**: 허브 목록과 같은 조건(`servableReleaseSql`) — 공개·release가 published, 지금 release, 엠바고 없음. 초안·준비·철회·대체·엠바고 중인 release는 세지 않습니다. 운영 조치로 가린 항목(`hidden_items`)은 스냅샷 일부를 가릴 뿐 사례는 공개 중이므로 셉니다.
- **선배 노트**: `status = 'published'`만. 초안·철회·숨김(운영 조치 `hidden`)은 세지 않습니다.
- **정본 기준**: 행의 과목 id를 `coalesce(courses.merged_into, courses.id)`로 정본에 모읍니다. 병합은 하위 병합까지 새 정본을 가리키게 바꾸므로(ADR 0010) 한 단계면 충분하고, 병합 뒤 원본 id를 가리키는 행이 남아 있어도 정본으로 셉니다.
- **세지 않는 것**: 막힘 Q&A(C-09)·체크인 통계·개념 태그. §8.6 기준이 사례·노트이고, Q&A는 커뮤니티에서 옮겨 온 복사본이라 "이 과목을 해 본 사람의 기록"과 성격이 다릅니다. 필요하면 pilot 뒤에 기준을 바꿉니다.

### 3. 언제 여는가: 요청마다 계산, 저장·캐시 없음

- 허브 요청마다 두 개의 집계 쿼리(사례·노트 수)로 판정합니다(`course-hub/staged-opening.ts`). 열림 상태를 저장하지 않으므로 세 번째 항목이 게시되면 **다음 요청부터** 열리고 운영자 조작·worker가 필요 없습니다.
- 철회·숨김으로 기준 밑으로 내려가면 다시 "준비 중"입니다(한 번 열리면 고정하는 방식은 쓰지 않음, 대안 참고). 허브가 보여 주는 내용 자체가 그만큼 줄었기 때문에 판정을 내용과 같은 순간의 값에 맞춥니다.
- 비용: 허브 요청마다 정본 과목 하나에 대한 `count` 두 번(`publication_candidates.course_id`, `senior_notes.course_id` 조건). 플래그가 꺼져 있으면 세지 않습니다.

### 4. 무엇을 가리는가: 허브 모음 페이지만

- `GET /api/v1/public/courses/:id`는 열린 허브(기존 응답 + `status: 'open'`) 또는 `{status: 'preparing', course, opening: {count, threshold}}`를 돌려줍니다. "준비 중"에는 사례·막힘·노트·Q&A·워크로드·다른 학교·수강 인원·개념 태그를 **싣지 않고**, 허브 조회 함수 자체를 부르지 않습니다. `count`는 이미 공개된 항목의 수라 그대로 보여 줍니다(진행이 보여야 노트를 쓰게 됨).
- 익명 방문자에게도 404 대신 최소한의 "과목 페이지 준비 중"을 보여 줍니다. 과목 자체는 카탈로그에서 누구나 찾을 수 있고, 404면 등록한 학생·선배가 "열리면 알려 주세요"·"선배 노트 쓰기"로 갈 길이 없습니다. 화면은 항상 noindex(준비 중 페이지가 검색 엔진에 쌓이지 않게)이고, 공개 API의 기존 헤더(no-store·noindex·쿠키 없음)는 그대로입니다. 없는 과목은 여전히 404입니다.
- **공개 사례(`/p/:slug`)는 그대로 열립니다.** 이미 작성자·팀 동의로 공개된 것이고, 단계적 개방의 목적은 내용이 얇은 "과목 페이지"가 먼저 퍼지지 않게 하는 것입니다. 검색의 사례·막힘 결과(경로 `/p/…`)도 그대로입니다.
- **검색의 노트·막힘 Q&A 결과는 뺍니다.** 이 둘은 허브 안에서만 읽을 수 있어(경로 `/c/:id#…`) 준비 중 과목이면 내용 없는 페이지로 보내게 됩니다. 결과 상한(20)을 채운 뒤 거르므로 준비 중 과목이 많으면 결과가 20보다 적을 수 있습니다(pilot 규모에서 허용).
- 선배 노트 쓰기(`/senior-notes?course=`)는 허브가 준비 중이어도 그대로 됩니다(허브를 여는 길이므로). 이 화면은 공개 허브 응답에서 과목 이름만 읽습니다.

### 5. 등록한 학생: "준비 중" + 열리면 알려 주세요

- 허브 화면은 SSR에서 로그인 상태를 읽지 않으므로, 준비 중일 때 화면이 뜬 뒤 로그인한 경우에만 `GET /api/v1/me/course-hubs/:id/opening`으로 본인 상태(등록했는지·마쳤는지·신청했는지·내 노트가 있는지)를 묻습니다. 다른 사람의 정보·신청 수는 없습니다.
- `POST /api/v1/me/course-hubs/:id/notify`: 이 과목(정본 + 병합된 과목)을 **어느 학기든 등록한 학생만**(아니면 403 `not_registered`), 이미 열렸으면 409 `already_open`, 같은 신청은 하나(다시 눌러도 200). `DELETE …/notify`는 행을 지웁니다. 사용자별 시간당 60회(429).
- **알림 = 홈이 읽을 때 한 번 기록.** `GET /api/v1/me/course-hub-notices`가 닫지 않은 내 신청의 과목을 판정해, 열렸으면 `opened_at = now`를 **조건부 갱신(`opened_at is null`)**으로 채웁니다. 동시에 여러 번 읽어도 시각은 한 번만 기록되고 다시 읽으면 같은 값입니다. 홈 "과목 허브 소식"이 "과목 페이지가 열렸습니다"와 닫기를 보여 주고, 닫으면(`POST /api/v1/me/course-hub-notices/:id/dismiss`, 멱등, 아직 열리지 않았으면 409 `not_opened`) 다시 보이지 않습니다. 허브가 다시 기준 밑으로 내려가면 열림 알림은 그동안 숨깁니다.
- worker 작업을 두지 않았습니다. 열림은 요청마다 계산하는 값이라 worker가 같은 계산을 주기적으로 반복해야 하고, 화면 안 알림뿐이라(메일·푸시 없음) 사용자가 홈을 열 때 판정해도 보는 시점은 같습니다. 나중에 메일을 붙이면 같은 조건부 갱신을 worker로 옮깁니다.
- E-01 학기 종료 알림(등록 행의 시각)과 달리 별도 테이블을 둡니다. 신청은 과목 단위(학기와 무관)이고, 등록을 지워도 신청은 남을 수 있으며, 마친 학생의 요청 닫기도 같은 곳에 둡니다.

### 6. 마친 학생: 선배 노트 요청

- **마침** = 학기가 끝난(정본 개설 학기의 `ends_at ≤ now`, 운영자가 고친 값 포함) 등록이 있거나, 끝난 학기에 연결된 과제 공간(스터디 기록 제외)의 active 멤버. 과제 공간 기준을 함께 쓰는 이유는 E-01 이전에 과목을 마친 학생(등록 기록 없음)이 대부분이기 때문입니다.
- 준비 중 허브 화면(로그인 시)과 홈 "과목 허브 소식"에 "선배 노트를 남겨 주세요"(최대 10개 과목, 과목 이름순)를 보여 줍니다. **이미 내 노트(초안·게시·숨김, 철회 제외)가 있거나, 닫았거나, 같은 과목의 E-01 학기 종료 알림이 아직 떠 있으면**(같은 요청이 겹치지 않게) 보이지 않습니다. 허브가 열리면 사라집니다(열린 허브는 노트 쓰기 진입점이 이미 있음).
- 닫기 `POST /api/v1/me/course-hubs/:id/dismiss-note-request`(멱등)는 `note_request` 행을 닫힘 시각과 함께 만듭니다.

### 7. 데이터: `course_hub_notices`

- 열: `user_id`, `course_id`(정본 과목), `kind`(`open_notify`·`note_request`, 새 enum `course_hub_notice_kind`), `opened_at`(`open_notify`만, check), `dismissed_at`(`note_request`는 필수, check), `created_at`. (사용자, 과목, 종류) unique, `course_id` 인덱스.
- **본인만**: 이 테이블을 부르는 서버 파일은 본인 화면 모듈(`course-registrations/hub-opening.ts`)과 과목 병합뿐입니다(S-02 lint 확장). 등록 테이블을 읽는 본인 모듈과 그 `/me` 라우트 6개는 E-01 허용 목록에 더했고, 운영자 라우트는 여전히 하나도 닿지 않습니다. social DB 역할에는 권한이 없습니다(S-02 DB 테스트 확장). 감사 기록·분석 이벤트를 남기지 않고, **신청 수는 공개·운영자 화면 어디에도 내보내지 않습니다**(5명 이상 집계도 만들지 않음 — 쓸 곳이 없음).
- 과목 병합 때 같은 트랜잭션에서 정본으로 옮기고, 같은 사람·종류가 정본에 이미 있으면 원본 쪽 행을 지웁니다. 감사 metadata에 옮긴 수를 남기지 않습니다(신청 수가 운영자 기록에 드러나지 않게).
- 탈퇴 정리(`account-purge`)가 그 사람의 행을 지우고 삭제 장부에 `course_hub_notices` 개수를 남깁니다(재적용 idempotent).

### 8. 운영자: 과목별 진행(공개 항목 수만)

- `GET /api/v1/operator/course-hubs/opening`(운영자만, 403 `operator_only`)·화면 `/operator/hub-opening`: 공개 사례·선배 노트가 하나라도 있는 정본 과목별 사례 수·노트 수·합계/기준·상태(합계 많은 순, 최대 200개)와 요약(내용 있는 과목·열림·준비 중 수). 사람·알림 신청·등록 정보는 없습니다(이 모듈은 등록 모듈을 import하지 않음).
- 플래그가 꺼져 있어도 "켰을 때의 상태"를 보여 줍니다. 켜기 전에 이미 사례·노트가 있는 허브 중 몇 개가 준비 중으로 바뀌는지 확인하라고 runbook에 적었습니다.

## 결과

- 플래그를 켜면 내용이 얇은 과목 페이지가 먼저 퍼지지 않고, 등록한 학생은 열릴 때 홈에서 알고, 마친 학생은 선배 노트 요청을 받습니다. 기준에 이르면 다음 요청부터 열립니다.
- 꺼져 있으면 기존 동작과 같습니다(E2E는 꺼진 상태만, 켜진 규칙은 web 통합 테스트 `course-hub-opening.integration.test.ts`).
- migration `0044_course_hub_notices`(새 테이블 하나, enum 하나, 빈 DB 처음부터 migrate 확인).
- 한계: 허브 요청마다 개수를 셉니다. 검색의 노트·Q&A는 상한을 채운 뒤 걸러 결과가 줄 수 있습니다. 열림 알림은 홈을 열어야 기록되므로 "열린 시각"이 아니라 "본인이 처음 확인한 시각"입니다. 기준을 낮추거나 플래그를 끄면 바로 열리고, 그때 신청한 학생은 다음 홈 방문에서 알림을 봅니다.

## 대안

- **한 번 열리면 고정(`course_hub_openings` 저장)**: 철회로 페이지가 다시 닫히는 깜빡임이 없지만, 저장 상태와 병합(두 과목 중 하나만 열린 경우)·기준 변경을 따로 맞춰야 하고 "지금 보이는 내용"과 판정이 어긋납니다. pilot에서 깜빡임이 문제면 이 방식으로 바꿉니다.
- **준비 중이면 404**: 가장 단순하지만 등록·마친 학생이 알림 신청·노트 쓰기로 갈 길이 없고, 과목이 없는 것과 구분되지 않습니다.
- **공개 사례 페이지·사례 검색도 가리기**: 이미 공개 동의를 받은 기록을 허브 조건으로 다시 숨기면 작성자 기대와 어긋나고, 단계적 개방의 목적(얇은 과목 페이지가 먼저 퍼지지 않기)과도 맞지 않습니다.
- **worker가 열림을 감지해 알림 시각을 채움**: 메일을 보낼 때는 필요하지만 지금은 화면 안 알림뿐이라 같은 계산을 주기적으로 반복하는 비용만 듭니다.
- **누구나 알림 신청**: 등록하지 않은 사람도 받을 수 있지만 §8.6은 등록한 학생을 대상으로 하고, 등록이 곧 "이 과목을 듣는다"는 본인 신호라 신청을 그쪽으로 모읍니다.
- **신청 수를 5명 이상이면 운영자에게 공개**: 수요를 보는 데 쓸 수 있지만 등록 수(E-01)와 마찬가지로 운영자에게 사람별·과목별 관심을 보여 줄 이유가 아직 없어 만들지 않았습니다.
- **P2 플래그 묶음에 넣기**: 기존 변수 하나로 켤 수 있지만 P2 GA 게이트와 무관한 P1 개방이 함께 켜지게 됩니다.
