# 0051. 제한 공유 링크: 지금 판 하나를 가리키는 256비트 bearer 토큰(SHA-256 해시만 저장, `portfolio_share_links`) + 만료 1~90일(기본 30)·철회·열람 횟수만 + `/s/<token>`은 요청마다 다시 판정해 그 판의 공개 보기보다 좁게(프로필 기본 필드 + 포트폴리오 보기만) + 늘 noindex·no-referrer·no-store, robots 차단, IP마다 분당 60회 + 철회·만료·새 판·프로필 숨김은 다음 요청부터 404 + 탈퇴 때 삭제, 플래그 없음

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

E-07은 DELIVERY_PLAN §4.4 P1 보완 백로그 항목입니다: "포트폴리오 판 단위 토큰(해시 저장)·만료·철회·열람 횟수만 기록, 토큰 링크는 noindex·검색 제외, 철회 다음 요청부터 404, 공개 범위를 넓히지 않고 판의 공개 사례만 보여 줌". 관련 설계와 앞선 결정:

- SYSTEM_DESIGN §6.5 `ShareGrant (P1) | edition_id, token_hash, expires_at, revoked_at | 원문 토큰 저장 안 함`, 공개 범위 절의 P1 `restricted-share`(만료·철회 가능한 토큰 링크, 링크만 알면 누구나 보는 `unlisted`와 다름).
- ADR 0014(T-14: 판은 만들 때마다 새 version이고 바꾸지 않음, 이전 판은 남지만 공개하지 않음, 공개 읽기는 요청마다 release 제공 가능 여부 확인. 한계에 "공유 토큰(ShareGrant, P1) 없음"), 0012(공개 조회 공통 handler: no-store·nosniff·no-referrer·noindex 기본·운영 스위치), 0021(C-05 robots.txt), 0028(S-01 페르소나·연결 플래그, 표시명 판에는 대표 케이스 없음), 0031(S-03 공개 범위), 0033(S-04 차단), 0050(E-06 실명 대표 케이스의 "물어보면 좋은 질문").
- 토큰 규칙은 매직링크·초대와 같습니다(`security/tokens`: CSPRNG 32바이트 base64url, DB에는 SHA-256 hex, 해시로 직접 조회).
- 변경: D-09: 철회·만료·판 교체로 끝난 링크 행은 90일 뒤 worker가 지웁니다 ([ADR 0060](0060-open-question-decisions.md)).

## 결정

### 1. 저장: 판 하나에 링크 여럿, 해시만

- `portfolio_share_links`(user_id, edition_id, `token_hash` unique·hex 64자 check, `label` 1~60자 또는 null, `expires_at`(> created_at), `revoked_at`, `view_count` ≥ 0, created_at). 원문 토큰은 만든 응답(`token`, `path: /s/<token>`)에서 한 번만 돌려주고 목록·감사·로그 어디에도 다시 나오지 않습니다. 잃어버리면 철회하고 새로 만듭니다.
- 조회는 `sha256(token)`으로 unique 인덱스를 직접 찾습니다. 공격자가 해시 값을 고를 수 없으므로 조회가 타이밍 오라클이 되지 않고, 따로 상수 시간 비교를 하지 않습니다(세션·매직링크와 같은 판단). 형식(base64url 20~128자)이 틀리면 DB를 읽지 않습니다.
- **HMAC 대신 SHA-256인 이유**: 토큰이 256비트 무작위라 해시 사전 공격이 의미 없고, 기존 토큰 테이블과 같은 규칙이면 키 관리가 필요 없습니다.
- 만료는 `expiresInDays` 1~90(정수, 기본 30). 사용자마다 지금 열 수 있는 링크 20개(409 `limit_reached`), 만들기 시간당 30회(429).

### 2. 공유 페이지: 요청마다 다시 판정, 공개 프로필보다 좁게

- 경로 `/s/<token>`(페이지), `GET /api/v1/public/share/:token`(JSON). `/s`는 기존 페이지·API와 겹치지 않고 공개 페이지 접두어에 넣어 SSR이 보는 사람의 로그인 상태(`/api/v1/me`)를 싣지 않습니다.
- 열리는 조건(하나라도 아니면 같은 404, 어느 경우인지 밝히지 않음): 링크가 있음 → 철회 안 됨 → 만료 전 → 판이 **지금 판** → 그 페르소나·계정 active, 프로필 운영 조치 숨김 아님(공개 프로필과 같은 조건, `resolvePublicPersonaById`) → 링크 주인 = 페르소나 주인.
- 내용은 공개 프로필과 같은 `buildPortfolioView`(대표 케이스는 게시 중 + 고정 release 제공 가능 + 숨김 아님 + 익명 스터디 아님, 엠바고·철회·대체는 release 판정에서 닫힘)에 프로필 기본 필드(이름·handle·한 줄 소개·관심 직무·학교/졸업(본인 입력)·연락 안내·구직 여부)만 더합니다. 표시명 판은 읽을 때도 대표 케이스를 비우고, "물어보면 좋은 질문"은 실명 판만(ADR 0050과 같음).
- **넣지 않는 것**: 타임라인·후배 기여·과제 수행 목록(S-03)·팔로우 수(S-04)·소셜 링크·학교 인증 배지·상대 페르소나 링크(S-01)·`contactPolicy` 코드. 그래서 공유 DTO는 그 판의 익명 공개 보기와 같거나 더 좁고, 공개 범위 설정으로도 넓어지지 않습니다. 상대 페르소나 필드 자체가 없으므로 연결 플래그와 무관하게 실명 판 링크에 표시명 정보가, 표시명 판 링크에 실명 정보가 나오지 않습니다.
- **지난 판**: 새 판을 만들면 이전 판의 링크는 다음 요청부터 404이고 목록에 `superseded`로 보입니다. 이전 판은 공개하지 않는다는 T-14 규칙을 링크가 깨지 않게 하려는 것입니다. 이전 판에는 새 링크를 만들 수 없습니다(409 `edition_superseded`).
- **차단(S-04)**: 토큰은 bearer입니다. 공유 경로는 세션을 읽지 않으므로(공개 GET) 차단당한 사람이라도 링크를 받으면 로그아웃한 방문자와 같은 응답을 봅니다. 주인이 막고 싶으면 링크를 철회합니다. 공개 프로필 SSR과 같은 판단입니다.

### 3. 헤더·색인·누출

- 공유 API: 공개 조회 공통 handler(no-store·nosniff·`Referrer-Policy: no-referrer`·운영 스위치 503·404 정규화) 위에 **설정과 무관하게 늘** `X-Robots-Tag: noindex, nofollow`. 쿠키를 읽거나 쓰지 않습니다.
- 공유 페이지: 서버 미들웨어(`04.share-page`)가 모든 응답(오류 포함)에 `noindex, nofollow, noarchive`·no-store·no-referrer를 붙이고, 페이지도 `<meta name="robots">`·`<meta name="referrer" content="no-referrer">`를 넣습니다. 출처 칩(`/p/...`)을 눌러도 토큰이 Referer로 새지 않습니다. 제목·OG에는 이름만 쓰고 토큰·글을 싣지 않습니다.
- robots.txt: 공개 색인을 켜도 `/s/`·`/api/v1/public/share/`를 Disallow(더 긴 규칙이 `/api/v1/public/` Allow보다 우선). 사이트맵은 없고, 검색 문서(T-13)는 공개 사례만 읽으므로 공유 링크 내용이 들어갈 길이 없습니다.
- 토큰은 URL 경로에 있으므로 리버스 프록시 접근 로그에 남을 수 있습니다. 운영 로그 보존 정책(RUNBOOK)을 따르고, 로그에서 토큰을 봤다면 그 링크를 철회합니다.

### 4. 열람 한도·횟수

- IP마다 분당 60회(`share_link_view` 버킷, 형식이 틀린 토큰도 셈). 페이지 요청은 미들웨어가 바깥 요청의 IP로 세고, SSR이 같은 프로세스에서 부르는 공개 API(nitro 로컬 fetch, `__unenv__` 요청 객체 — 바깥 요청은 만들 수 없음)는 다시 세지 않습니다. 브라우저·외부에서 API를 직접 부르면 API가 셉니다.
- 열람 기록은 `view_count`(열릴 때마다 1, 404·429는 세지 않음)뿐입니다. 보는 사람의 IP·브라우저·시각·마지막 열람 시각은 저장하지 않고 감사·분석 이벤트도 없습니다. "누가 봤는지"를 알려 주면 받는 사람의 동의 없는 추적이 되기 때문입니다.

### 5. 관리·감사·탈퇴

- 본인만: `POST /portfolio-editions/:id/share-links`, `GET /me/share-links`(최근 100개, 상태 active·revoked·expired·superseded, 열람 횟수), `POST /me/share-links/:id/revoke`(이미 철회했으면 그대로 200), `DELETE /me/share-links/:id`(열 수 없는 링크만 행 삭제, 열린 링크는 409 `share_link_active`). 남의 판·링크는 404.
- 감사: `share_link.create`(판 id·페르소나 종류·만료 일수·이름 유무), `share_link.revoke`(판 id·열람 횟수), `share_link.delete`(판 id). 대상은 링크 id. 토큰·해시·이름 글은 넣지 않습니다.
- 탈퇴 정리(worker): 그 사람의 링크를 판보다 먼저 지웁니다(장부 개수 `portfolio_share_links`). 계정이 비활성이 되는 순간부터는 2절 조건으로 이미 404입니다.
- 플래그 없음: 기본은 링크 0개이고, 링크가 보여 주는 것은 이미 공개된 판의 공개 보기보다 좁아 플래그가 지킬 위험이 없습니다.

## 결과

- 학생은 포트폴리오 화면의 "제한 공유 링크"에서 지금 판의 링크를 이름·만료와 함께 만들고, 주소를 한 번 복사해 보내며, 열람 횟수를 보고 언제든 철회합니다. 받는 사람은 로그인 없이 그 판의 대표 케이스·역량 × 근거를 봅니다.
- migration `0048_portfolio_share_links`(테이블 1개, enum 없음, 빈 DB 처음부터 migrate 확인).
- 테스트: web 통합 `share-links.integration.test.ts`(해시만 저장·감사에 비밀 없음, 만료 경계·입력 검증·한도·남의 링크 404, 헤더 noindex·no-referrer·no-store·쿠키 없음, 열람 횟수, 철회 다음 요청 404, 지난 판·프로필 숨김·계정 정지 404, 게시 취소·숨김·엠바고·철회한 케이스 닫힘, 공개 프로필 전용 항목 없음, S-01 양방향, IP 한도·robots), worker `ops-purge.test.ts`(탈퇴 정리), e2e `e07-share-links.spec.ts`(만들기 → 익명으로 열기 → 철회 → 404).
- 한계: 판마다가 아니라 사용자마다 열린 링크 20개입니다. 링크는 지금 판에만 묶여 새 판을 만들면 다시 보내야 합니다. 철회·만료된 행은 주인이 지우거나 탈퇴할 때까지 남습니다(자동 정리 작업 없음, 해시·이름·횟수뿐). 인쇄 보기·README 카드는 공유 링크용으로 따로 만들지 않았습니다. 이미 열어 둔 화면·저장한 사본은 철회해도 회수되지 않습니다.

## 대안

- **페르소나의 지금 판을 따라가는 링크**: 새 판을 만들어도 링크가 이어지지만, 학생이 보낸 판과 받는 사람이 보는 판이 달라지고 "판 단위 토큰"이라는 백로그 정의와 어긋납니다.
- **지난 판도 링크로는 보여 줌**: 판은 바꾸지 않으므로 보낸 그대로 보이지만, 공개하지 않기로 한 이전 판을 링크가 다시 공개하게 됩니다(공개 범위를 넓힘).
- **공개 프로필 전체를 링크로**: 이미 `/u/:handle`로 누구나 보므로 링크의 의미가 없고, 공개 범위 설정·차단과 얽힙니다.
- **마지막 열람 시각·열람 로그 저장**: 학생에게 유용할 수 있지만 받는 사람 추적이 되고 백로그의 "열람 횟수만"을 넘습니다.
- **HMAC(서버 비밀) 해시**: DB만 유출됐을 때 더 안전하지만 256비트 무작위 토큰에서는 이득이 작고 키 회전·관리가 늘어납니다.
- **SSR 없이 브라우저에서만 불러오기**: IP 한도가 단순해지지만 철회된 링크의 페이지가 200으로 응답합니다.
