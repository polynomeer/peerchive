# 0058. AI 회의 요약: 서버 AI 설정(ADR 0057 `features.ai`)이 있을 때만 + owner가 연결된 디스코드 채널을 회의 채널로 제안하고 **지금 active 멤버 전원**이 웹에서 동의해야 요약(누구든 철회하면 즉시 중단, 새 멤버는 동의할 때까지 중단) + 봇 `/summarize [범위] [개수]` → 메시지를 읽기 전에 서버 확인 → 최근 메시지를 메모리에서만 읽어 HMAC 내부 API(이 경로만 본문 256KB)로 한 번 보냄 → 서버가 조건 재확인 뒤 **동의한 팀원이 쓴 메시지만**(팀 밖 참여자 메시지는 봇이 빼고 서버가 다시 걸러 개수만) 멘션을 표지(`[M1]`·번호 없는 `[외부]`)로 바꿔 Claude 구조화 출력(요약·결정·후속 할 일·열린 질문) → **원문은 DB·로그·outbox 어디에도 저장하지 않고** 초안만 저장 + 초안은 멤버가 보고 owner/editor가 고쳐 승인(요청자 본인은 다른 owner/editor가 없을 때만)하면 🗣️ 회의 로그 source `ai`(`AI 초안`) + 고른 후속 할 일은 할 일로 + 거절·철회·제안 거둠·채널 해제는 초안 삭제, 7일 상한 + 과제마다 하루 5번·승인 대기 3개·메시지 200개·본문 40,000자 + `@peerchive/ai` 상한·사용량 그대로

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

E-13은 DELIVERY_PLAN §4.4 P1 보완 백로그의 열세 번째 항목입니다: "팀이 동의한 회의 채널 대화만, 🗣️ 회의 로그 초안(결정·후속 할 일)은 팀원 승인 후 저장, 원문 대화는 저장하지 않음". 의존 항목은 T-08(디스코드 봇)과 E-12(공용 AI 클라이언트)입니다. 관련 설계와 앞선 결정:

- PROOFU_EVOLUTION_PLAN §6.5 입력 경로 표("회의 요약 — 팀이 동의한 회의 채널 대화를 AI가 요약해 🗣️ 회의 로그 초안 생성", P1), §6.2 회의 로그(참석자·결정·후속 할 일, "봇·AI가 초안, 팀원 승인"), §15 AI 정책(생성물 표시·승인 필수, 비공개 데이터는 해당 팀 작업에만, 학습 미사용 API 조건, AI 없이도 핵심 기능 사용).
- ADR 0009(디스코드 봇·내부 API: HMAC 서명·nonce 재사용 거부·본문 64KB, 채널 연결 `discord_channel_bindings`, 📌 승인 요청은 결정 즉시 내용 삭제), T-04 회의 로그 payload(`attendees`·`decisions`·`followUps`, 각 20개·500자), T-07 할 일(`createTask`), ADR 0016(감사는 id·개수만, 분석 수집 거부, 탈퇴 정리), ADR 0057(공용 `@peerchive/ai`·웹 `callAi`, `PEERCHIVE_AI_ENABLED`, 승인 전 초안은 별도 테이블, `AI 초안` = 로그 source `ai`, 프롬프트·출력 로그 없음).

## 결정

### 1. 켜짐: 서버 설정 + 회의 채널 제안 + 팀 전원 동의

- **서버**: E-12와 같은 `aiConfigured()`(`PEERCHIVE_AI_ENABLED=on` + `ANTHROPIC_API_KEY`). 꺼져 있으면 새 웹 경로 모두 404·화면 칸 없음, 봇 명령은 `ai_disabled` 안내(메시지를 읽지도 보내지도 않음). 새 플래그는 없습니다.
- **제안**: 과제 owner가 이미 연결된 채널(ADR 0009)을 "회의 채널"로 제안합니다(`ai_meeting_channels`, 채널 연결마다 하나). 제안한 owner는 동의한 것으로 봅니다. 스터디 기록(kind study)은 쓰지 않습니다(웹 경로 모두 404, 봇은 `not_meeting_channel` — 동의 목록·초안이 멤버 실명·id를 싣는데 익명 스터디 기록은 가명 규칙(ADR 0026 부록)을 따라야 함).
- **동의 의미**: `ai_meeting_consents`의 행은 "이 사람이 동의함"뿐이고, 요약 가능 여부는 **요청 때마다 지금 active 멤버(계정도 active) 전원에게 동의 행이 있는가**로 계산합니다(domain `meetingConsentState`). 그래서
  - 역할과 무관하게 모든 active 멤버(reviewer·viewer 포함, 대화 당사자이므로)가 동의해야 합니다.
  - 누구든 철회하면 다음 요청부터 바로 요약할 수 없습니다. 철회는 그 채널의 승인 전 초안도 지웁니다(철회한 사람이 그 요약에 반대할 수 있으므로).
  - **나중에 들어온 멤버**는 동의 행이 없으므로 그 사람이 동의할 때까지 요약할 수 없습니다(따로 "재동의 요청"을 만들지 않아도 됨). 나가거나 내보내진 멤버의 동의 행은 그때 지워 다시 들어오면 새로 동의해야 합니다.
  - owner가 제안을 거두면 동의·승인 전 초안을 지웁니다. 채널 연결을 해제해도 같습니다.
- 요청자(봇 명령을 실행한 디스코드 사용자)는 연결된 계정이고 그 과제의 active owner/editor여야 합니다(`not_linked`·`not_writer`).

### 2. 흐름(봇 → 내부 API → AI)

- 봇 `/summarize [window: 최근 1·2·3·6·12·24시간, 기본 2] [count: 1~200, 기본 100]`(서버 채널 전용, 응답은 본인에게만).
- **확인 먼저**(`POST /api/internal/discord/meeting-summaries/check`, 메시지 없음): AI 설정 → 채널 연결 → 계정 연결 → 쓰기 권한 → 회의 채널 → 전원 동의 → 승인 대기 초안 3개 미만. 하나라도 아니면 봇은 이유를 안내하고 **채널 메시지를 읽지 않습니다**.
- 봇이 디스코드 REST로 최근 메시지를 읽습니다(`Read Message History` 권한, 100개씩 최신순, 범위 밖이면 멈춤). 봇·시스템 메시지는 빼고(수만 셈), 첨부는 보내지 않고 개수만, 본문은 2000자로 자릅니다. 본문 합계 40,000자와 요청 크기 상한에 맞게 **오래된 메시지부터** 덜어 최근 대화를 남깁니다(`meetingPayload`). 읽은 메시지는 그 함수의 메모리에만 있습니다.
- **요약**(`POST /api/internal/discord/meeting-summaries`): 서버가 확인 단계를 **다시** 하고(봇을 믿지 않음) interaction id로 중복을 막은 뒤(같은 id면 `duplicate`, AI 다시 안 부름), 과제마다 하루 한도를 셉니다. 남은 메시지가 없으면(첨부만) `empty`로 AI를 부르지 않습니다.
- AI 호출은 트랜잭션 밖(`callAi`: 사용자·전체 하루 상한 → 공급자 → 사용량 기록). **저장 직전에 동의를 다시 확인**해, AI를 부르는 동안 철회·제안 거둠이 있었으면 결과를 버립니다(`no_consent`·`not_meeting_channel`).
- 봇은 이 요청을 재시도하지 않습니다(AI 비용이 두 번 들지 않게; 다른 내부 API는 5xx면 1회 재시도). 디스코드 3초 응답 제한은 기존 어댑터의 "생각 중" 지연 응답(2초 뒤 defer)이 처리합니다.

### 3. 초안 승인·거절과 `AI 초안` 표시

- 초안(`ai_meeting_drafts`)은 그 과제 멤버가 모두 봅니다(과제 화면 "AI 회의 요약 (선택)", 비멤버 404). 거절·승인 화면은 같은 초안을 보여 줍니다.
- **승인 규칙**: active owner/editor 한 명이 고쳐서 승인합니다. 단 **요약을 요청한 사람 본인은 다른 active owner/editor가 있으면 승인할 수 없습니다**(403 `second_approver_required`) — DELIVERY_PLAN의 "팀원 승인"을 "요청자 말고 한 사람 더 본다"로 해석하되, 쓰기 멤버가 요청자 혼자인 과제가 영원히 막히지 않게 그때는 본인 승인을 허용합니다. 과반수 투표는 팀 규모(2~6명)에 비해 무겁고 승인이 늦어 초안이 7일 안에 사라지기 쉬워 택하지 않았습니다.
- 승인(`POST …/ai-meetings/drafts/:draftId/approve`)은 빌드 로그 작성과 **같은** `parseLogInput`·`insertLog`(태그는 🗣️ 회의 고정, 재전송은 초안 id를 `clientId`로 묶음)를 써서 source **`ai`**(`AI 초안` 배지, 공개 스냅샷까지 그대로)·첫 revision `ai_generated`·`approved_at`인 회의 로그를 만듭니다. 작성자는 승인한 사람입니다(최종 글에 책임지는 사람). 기본값은 domain `meetingDraftToLogInput`: 본문 = 요약 + 열린 질문 + "팀 밖 참여자 메시지 N개 제외" + "첨부 N개 생략", payload = 참석 멤버 id·결정·후속 할 일 줄("할 일 — 담당 이름, 기한 YYYY-MM-DD").
- **할 일**: 승인 요청의 `tasks: [{title(≤120), assigneeId?, dueAt?}]`(최대 20, 화면은 후속 할 일마다 체크박스)를 같은 트랜잭션에서 T-07 `createTask`로 만듭니다. 할 일 하나라도 실패하면(한도·담당자 검증) 로그도 남지 않습니다(422/409, 초안 그대로).
- 거절(`DELETE …/ai-meetings/drafts/:draftId`, owner/editor 누구나 — 요청자 포함)은 로그·할 일을 쓰지 않고 초안만 지웁니다.

### 4. AI에 보내는 것(이것뿐)

| 보냄 | 안 보냄 |
|---|---|
| 고정 system 프롬프트(상수, 캐시 대상) | 디스코드 사용자 id·이름·별명, 메시지 id·시각 |
| 회의 날짜(서울, `2026-10-20(화)` — "금요일까지"를 기한으로 바꾸는 데만) | Peerchive 사용자 id·이메일·표시 이름, 과제 id·이름 |
| 팀원 표지 목록(`[M1]…`)·팀원 메시지 수·생략한 첨부 수 | **팀 밖 참여자(연결 안 함·이 과제 active 멤버 아님·나간 멤버)가 쓴 메시지 전부**(개수만 셈) |
| 동의한 팀원이 쓴 메시지 본문(멘션은 표지로) | 첨부 파일·링크 미리보기·봇 메시지·시스템 메시지 |
| 메시지 본문(멘션은 표지로, 역할·채널 멘션은 `@역할`·`#채널`, 이모지·시각 태그 정리, 2000자) | 다른 채널·다른 과제·빌드 로그·체크인 |

- **팀 밖 참여자 메시지는 보내지 않습니다**: 작성자의 디스코드 id가 연결 계정(active)으로 이 과제의 **동의한 active 멤버**에 맞지 않으면 그 메시지는 본문을 보지 않고 버리고 개수만 셉니다. 봇은 확인 응답의 `memberDiscordIds`(동의한 active 멤버의 연결 디스코드 id) 밖의 작성자 메시지를 보내지 않고 `excludedMessages`로 개수만 보내며, 서버는 봇이 보낸 메시지라도 같은 규칙으로 **다시 걸러** 냅니다(봇을 믿지 않음). 초안에는 "팀 밖 참여자 메시지 N개 제외"(봇이 뺀 수 + 서버가 거른 수)만 남습니다. 연결하지 않은 팀원도 팀 밖 참여자로 취급되므로 그 사람의 말은 요약에 들어가지 않습니다(봇·화면이 안내).
- 표지는 처음 나온 순서대로 붙입니다. 팀원은 `[M n]`이고, 팀원 메시지 안에서 멘션된 팀 밖 사람은 **번호 없는 `[외부]`** 하나로만 씁니다(여러 사람을 구분하거나 같은 사람을 메시지 사이에서 이어 볼 수 없게). AI는 표지로만 사람을 부르고, 서버가 출력의 표지를 지금 표시 이름·"외부 참여자"로 되돌립니다(`replaceMeetingLabels`, 모델이 번호를 붙여도 번호 없이). 후속 할 일 담당 표지가 멤버면 그 사용자 id를 담당자 후보로 둡니다. 기한은 실제 달력 날짜만 받습니다(`validDueDate`).
- 메시지는 `<transcript>`의 `<m who="[M1]">…</m>`에 넣고 닫는 태그를 무력화하며(`neutralizePromptText`), system 프롬프트가 구획 안 글을 지시로 따르지 않게 합니다.
- 출력 스키마 `{summary, decisions[], follow_ups[{task, owner|null, due|null}], open_questions[]}`, `feature: meeting_summary.draft`, effort `medium`, max_tokens 16000(E-12 초안과 같은 근거). 서버가 요약 2000자, 결정·후속 할 일 20개·500자(후속 할 일 글 300자), 열린 질문 10개로 자르고 중복을 없앱니다.
- 테스트가 가짜 공급자로 받은 글 전체에서 디스코드 id·Peerchive 표시 이름·과제 이름·사용자 id·과제 id가 0건임을 확인합니다.

### 5. 원문 미저장·보존

- **메시지 원문은 저장하지 않습니다**: 내부 API는 본문을 서명 확인 뒤 메모리에서만 풀고, 서버 로그에는 경로·실패 이유만 남기며(ADR 0009), 감사·분석·outbox에는 개수만 들어갑니다. 테스트가 메시지에 심은 표지 문자열을 이 트랜잭션의 **모든 public 테이블**(outbox·감사·분석·nonce·rate limit 포함)과 콘솔 출력에서 찾아 0건임을 확인합니다. 봇도 메시지를 저장하거나 로그로 남기지 않습니다.
- 초안에는 AI가 만든 요약·결정·후속 할 일·열린 질문과 참석 멤버 id·제외한 팀 밖 메시지 수·첨부 수·메시지 수·시간 범위만 있습니다. AI가 메시지 일부를 그대로 요약에 옮길 수는 있으며, 그 글은 팀원 승인 전에는 팀 밖으로 나가지 않습니다.
- 초안은 승인·거절 즉시, 그러지 않아도 만든 지 **7일**(`expires_at`) 뒤 worker 주기 작업 `ai-meeting-drafts`(매시 23분)와 다음 읽기가 지웁니다. 동의 철회·제안 거둠·채널 해제도 그 채널의 초안을 지웁니다.
- 탈퇴 정리: 그 사람의 동의 행과 그 사람이 요청한 승인 전 초안을 지웁니다. 그 사람이 제안한 회의 채널은 팀 설정이라 남깁니다(사용자 행은 지우지 않으므로 외래 키 그대로). 혼자 과제를 지울 때 회의 채널·동의·초안도 함께 지웁니다.
- 감사(`ai_meeting.channel_propose|channel_withdraw|consent|consent_revoke|draft_create|draft_approve|draft_reject`): id와 개수·플래그(`messages`·`decisions`·`followUps`·`excluded`·`drafts`·`tasks`·`edited`·`selfApproved`)만. 분석 `ai_meeting_draft_proposed {messages, decisions, followUps}`·`ai_meeting_draft_resolved {decision, tasks, edited}` + 승인 로그의 `log_saved {source: ai}`, 수집 거부를 따름. 사용량은 E-12의 `ai_usage_daily`(기능 `meeting_summary.draft`).

### 6. 내부 API 본문 상한(이 경로만 256KB)

- 메시지 200개·본문 합계 40,000자는 한글(UTF-8 3바이트)만으로 120KB이고 JSON 틀(메시지마다 작성자 id·시각·첨부 수)과 이스케이프를 더하면 64KB를 넘습니다. 그래서 `createInternalHandler`에 경로별 `maxBodyBytes`를 두고 **회의 요약 경로만 256KB**(`MEETING_SUMMARY_MAX_BODY_BYTES`)로 올립니다. 다른 내부 API는 64KB 그대로입니다.
- 서명 확인 전에 `content-length`와 실제 길이를 이 상한으로 먼저 자르므로, 인증 없는 요청이 쓰는 메모리는 요청당 256KB를 넘지 않습니다. HMAC·시각 차이·nonce 재사용 거부는 그대로입니다(테스트).
- **나눠 보내기(chunking)는 쓰지 않습니다**: 여러 요청으로 나누면 서버가 앞 조각(원문)을 모아 두어야 해 "원문을 저장하지 않음"과 충돌하고, 조각마다 AI를 부르면 비용·일관성이 나빠집니다. 상한은 봇이 직렬화한 크기를 재서 지키고, 서버도 메시지 수·본문 합계를 다시 검증합니다(422).

### 7. 한도

- 부르기 전에(넘으면 공급자 호출 0): 과제마다 하루(UTC) 5번(`rate_limit_buckets`, 과제 id 해시) → E-12의 서버 전체 하루 토큰·사용자마다 하루 호출·서버 전체 하루 호출(`callAi`). 넘으면 봇에 `rate_limited`.
- 승인 대기 초안은 과제마다 3개까지(`drafts_pending`), 메시지 200개·본문 40,000자·메시지 하나 4000자(프롬프트에는 2000자).

## 결과

- 서버에 키가 있고 팀이 동의한 채널이면, 회의 뒤 `/summarize` 한 번으로 결정·후속 할 일 초안을 받고 다른 팀원이 고쳐 승인해 🗣️ 회의 로그와 할 일로 남길 수 있습니다. 승인되지 않은 AI 글은 빌드 로그·공개·검색·기여 장부 어디에도 들어가지 않고, 승인한 글은 `AI 초안`으로 끝까지 표시됩니다. 대화 원문은 남지 않습니다.

## 대안

- **동의를 한 번 받으면 계속 유효(멤버 변화 무시)**: 단순하지만 나중에 들어온 사람의 대화가 동의 없이 요약됩니다. 지금 멤버로 매번 계산합니다.
- **owner 동의만**: §15 "팀이 동의한"과 맞지 않습니다. 전원 동의로 둡니다.
- **봇이 대화를 계속 듣고 저장했다가 요약**: 명령 한 번이 쉬워지지만 원문이 저장됩니다. 명령 때 REST로 읽고 버립니다.
- **나눠 보내기·서버 쪽 조각 모으기**: 64KB 상한을 지키지만 원문 조각을 서버에 둬야 합니다. 이 경로만 상한을 올립니다.
- **디스코드 표시 이름을 그대로 보냄**: 출력이 읽기 쉽지만 팀 밖 사람의 이름까지 외부로 나갑니다. 표지로 보내고 서버가 멤버 이름만 되돌립니다.
- **팀 밖 참여자 메시지를 "외부 참여자 N"으로 보냄**: 회의 맥락은 살지만 Peerchive가 동의를 받을 수 없는 사람의 글이 공급자에게 갑니다. 보내지 않고 개수만 남깁니다. 멘션 표지에 번호를 붙이면 같은 사람을 메시지 사이에서 이어 볼 수 있어 번호 없는 `[외부]`로 둡니다.
- **AI가 참석자를 고름**: 말하지 않은 사람을 넣을 수 있습니다. 참석자는 메시지를 쓴 멤버로 서버가 정합니다.
- **과반수 승인·요청자 단독 승인**: 과반수는 소규모 팀에 무겁고, 단독 승인은 "팀원 승인"의 뜻이 약합니다. 요청자 외 한 사람(쓰기 멤버가 혼자면 본인)으로 둡니다.
- **후속 할 일을 모두 자동으로 할 일로**: 편하지만 원치 않는 할 일이 쌓입니다. 승인 때 항목마다 고릅니다.
