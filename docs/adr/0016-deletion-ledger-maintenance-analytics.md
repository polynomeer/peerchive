- 상태: 채택
- 날짜: 2026-10-26

## 맥락

T-16은 Phase 1 백로그의 마지막 항목입니다(DELIVERY_PLAN §4 "DB+파일 복구, 삭제 ledger 재적용, 개인정보 없는 분석 이벤트"). 관련 설계:

- SYSTEM_DESIGN §1 불변조건 7 "삭제·철회 요구가 있으면 실제 내용도 제거할 수 있음", §6.6 DeletionLedger(target, requested_at, purged_at)와 "DB 삭제는 무조건 cascade하지 않고 공동 기록·동의·철회의 파급을 먼저 계산", §11 "백업에는 삭제 자료가 잠시 남을 수 있음. 복구 시 최신 철회·삭제를 재적용하기 전에는 외부 트래픽을 열지 않음", §14 RPO 24시간·RTO 4시간·관측 목록·운영 스위치.

- 이전 slice가 남긴 자리: 탈퇴 요청은 `users.status = deleted`와 세션 삭제뿐(ADR 0006), 만료 행 정리 TODO(rate limit T-02, 업로드 의도·격리 파일 T-05, nonce·디스코드 코드·📌 요청 T-09), 모든 외래 키는 `no action`(cascade 없음), 공개 철회·동의 철회 규칙(ADR 0012), 게시 판정은 탈퇴·정지 계정의 동의를 무효로 봄(`subject_inactive`).

## 결정

### 탈퇴 정리(purge): 유예 7일 뒤 worker가 계정마다 한 트랜잭션

- 탈퇴 요청 뒤 `PEERCHIVE_DELETION_GRACE_DAYS`(기본 7일)가 지나면 worker 주기 작업 `account-purge`(기본 30분마다)가 정리합니다. 유예는 실수·계정 탈취 대응 시간입니다(되돌리기 화면은 아직 없음, 운영자 수동).
- **지우는 것(그 사람만의 자료)**: 프로필, 세션, 로그인 수단, 그 주소의 매직링크 토큰, 외부 연동(디스코드 id), 디스코드 코드·📌 요청, 주간 체크인(모든 과제), 그 사람이 남긴 유용성 신호, 선배 노트(남이 남긴 신호·검색 문서 포함), 케이스 스터디·포트폴리오 판, 분석 이벤트, 업로드 의도, **혼자만 쓴 과제 전체**.
- **혼자만 쓴 과제** = 다른 사람이 active·left·removed 멤버였던 적이 없는 과제. 로그·revision·근거, 할 일, 마일스톤·스냅샷, 역할 선언·확인, 체크인, 디스코드 연결·알림, 산출물·버전과 **저장소 파일(격리·clean 키)**, 초대·엠바고·플랜 포크 기록, 공개·후보·동의까지 지웁니다. 감사 이벤트는 남기되 project_id를 비웁니다(본문 없음).
- **팀 과제는 기록을 지우지 않습니다.** 그 사람이 쓴 로그·역할 선언·올린 파일·할 일은 팀 이력이고 동료의 확인·근거·리포트가 가리킵니다. 조용히 지우면 팀 기록이 깨지므로 남기고 **가명 처리**합니다: users 행은 남기되 표시 이름 "탈퇴한 사용자", 이메일은 자리표시 주소(`purged+<id>@deleted.invalid`), `purged_at`·`analytics_opt_out = true`. 그 사람이 남의 기록에 쓴 **메모 글**(확인 메모·동의 메모·신고 설명·이의제기 글)은 지웁니다(이의제기 글은 고정 문구로 바꿈, 길이 제약 때문).
- 팀 과제 멤버십은 `removed`, owner였으면 남은 active 멤버(owner·editor → reviewer → viewer, 먼저 들어온 순)에게 넘기고 감사 기록(`project.transfer_ownership`, reason `account_deleted`). active 멤버가 없으면 owner 표시는 가명 사용자로 남습니다. 그 사람이 만든 대기 초대는 취소합니다.
- **공개**: 그 사람이 당사자인 **지금 게시 중인 release**는 동의 철회와 같은 결과로 철회합니다(동의 `revoked`, 공개 `withdrawn`(원인 `consent_revoked`), release `withdrawn`, 열린 후보 `superseded`, `access_epoch` +1, outbox `publication.withdrawn`). 공개 읽기는 요청마다 상태를 확인하므로 커밋 즉시 막히고, worker 정리 handler가 검색 문서·신호·케이스 스터디를 맞춥니다. 팀은 기존 규칙대로 철회한 사람을 뺀 새 후보(exclude-declined)를 만들 수 있고, 열린 후보의 그 사람 동의는 게시 판정이 무효로 봅니다(`subject_inactive`). 새 규칙을 만들지 않았습니다.
- **묘비**: 운영 기록(신고·조치)이나 다른 사람의 플랜 포크가 가리키는 노트·케이스·공개·과제 행은 외래 키 때문에 지울 수 없으므로 내용을 비운 행으로 남깁니다(노트 답 `{}`·withdrawn, 케이스 제목 "삭제된 케이스 스터디"·문장 삭제, 후보 스냅샷·manifest `{}`, 과제 제목 "삭제된 과제"·본문 필드 null). 공개 조회는 published가 아니므로 404입니다. 판정은 미리 계산하지 않고 savepoint 안에서 지워 보고 외래 키 위반(23503)이면 묘비로 바꿉니다(참조 표가 늘어도 안전).
- **파일은 커밋 직전에 지웁니다.** 행을 지운 뒤 같은 트랜잭션 안에서 저장소 파일을 지우고, 파일 삭제가 실패하면 트랜잭션 전체가 되돌아가 다음 주기에 다시 시도합니다. 커밋이 실패하면 행이 남고 파일만 없는 상태가 되는데, 다음 정리가 행을 지웁니다(개인 파일이 남는 쪽보다 낫다고 봄).
- 다시 정리해도 지울 것이 없으면 아무것도 바꾸지 않습니다(idempotent): 이미 묘비인 행은 조건부 update라 개수가 늘지 않습니다.

### 삭제 장부(deletion_ledger): 종류별 개수 + HMAC 대상

- 정리 한 번에 지운 **종류마다 한 행**: `subject_hash`(HMAC-SHA256(`PEERCHIVE_DELETION_PEPPER`, 사용자 id)), `entity_kind`(예: `profile`, `solo_projects`, `artifact_objects`), `count`, `requested_at`(분 단위), `purged_at`, `source`(`purge`/`reapply`). 이름·이메일·제목·id 목록은 없습니다(테스트가 장부 JSON에 사용자·과제 id·이메일·이름·본문 sentinel이 없음을 확인).
- 일반 해시가 아니라 pepper HMAC인 이유: 사용자 id는 UUID라 추측하기 어렵지만, 백업·로그에 같이 남은 id와 장부를 바로 이어 볼 수 없게 합니다. pepper는 장부와 다른 곳(비밀 저장소)에 둡니다.
- **삭제 pepper는 바꾸지 않습니다.** 바꾸면 재적용이 이전 장부를 맞추지 못합니다. production에서 없거나 약하면(32자 미만·자리표시) worker와 재적용 명령이 시작하지 않습니다.

### 복구 뒤 재적용과 점검 모드

- `pnpm ops:reapply-deletions [--ledger-file=<path>] [--dry-run]`: 장부(지금 운영 DB에서 `pnpm ops:export-ledger`로 내보낸 파일, 백업의 `ledger.jsonl`, 또는 대상 DB 자신의 장부)의 subject_hash 집합을 만들고, 대상 DB의 모든 사용자 id를 같은 pepper로 HMAC해 맞는 사람을 **상태와 무관하게** 다시 정리합니다(오래된 백업에서는 그 사람이 active일 수 있음). 파일의 항목 중 대상 장부에 없는 것은 넣어 복구된 DB의 장부도 최신으로 만듭니다. 두 번 돌려도 바뀌는 것이 없습니다. 출력은 개수만입니다.
- **점검 모드** `PEERCHIVE_MAINTENANCE=1`: web의 첫 서버 미들웨어(`00.maintenance`)가 정확히 `/api/v1/health`(쿼리 허용)를 뺀 모든 요청(화면·API·공개 조회·내부 API)을 DB를 건드리지 않고 503(`maintenance`, `Retry-After: 600`, no-store, noindex)으로 막습니다. 빌드된 정적 자산(`/_nuxt/*`, 데이터 없음)은 Nitro가 미들웨어보다 먼저 내줄 수 있습니다. 공개 읽기 운영 스위치(ADR 0012)와 달리 로그인·쓰기도 막습니다. 바꾸려면 재시작합니다(환경 변수는 요청마다 읽지만 배포 환경에서 바꾸는 방법이 재시작뿐).
- **복구 순서**: web·worker 정지 → `ops/restore.sh` → web을 `PEERCHIVE_MAINTENANCE=1`로 시작(헬스 확인만) → `pnpm ops:reapply-deletions --ledger-file=<최신 장부>` → worker 시작 → 점검 모드를 풀고 web 재시작. worker는 점검 모드 변수를 보면 경고만 남깁니다(재적용 전에 worker를 켜지 않는 것은 절차로 지킴).

### 주기 정리 작업

worker가 작업마다 pg-boss 큐 `ops.<이름>`과 cron 일정(Asia/Seoul, 놓친 실행은 한 번, `PEERCHIVE_CRON_<이름>`으로 바꾸거나 `off`)을 둡니다. 모두 조건에 맞는 행만 지워 idempotent하고, 한 문장 `PEERCHIVE_OPS_BATCH_SIZE`(기본 500)행·한 실행 50배치까지만 합니다.

### pilot 분석 이벤트: 허용 목록 props + HMAC 주체 + 수집 거부

- 이름: DELIVERY_PLAN §6의 15개 + `login_succeeded`(활성화 지표의 가입 시점, `newUser`). enum으로 DB에서도 막습니다.
- props: 이벤트마다 허용 목록(`@peerchive/domain` `ANALYTICS_PROP_SPECS`)의 키만, 값은 **닫힌 enum 문자열·참거짓·범위 안 정수**만 받습니다. 자유 문자열 필드가 없으므로 본문·제목·파일 이름·URL·이메일·검색어가 들어갈 자리가 없습니다. 목록 밖 키·값이 하나라도 있으면 이벤트 전체를 버리고 키 이름만 경고합니다. 요약: 태그·출처(`log_saved`), 근거 개수(`evidence_attached` files·links·logs), 체크인 시간 구간·난이도·통계 동의·이유 개수, 확인 상태, 리포트 기간 일수, 후보 수준·고른 개수, 동의 결정, 게시 수준·버전 번호, 철회 원인, 포크로 복사한 개수, 신호 대상·종류, 노트 표시 방식·답 개수, 포트폴리오 판의 대표·역량·스킬 개수.
- 주체: `actor_hash` = HMAC(`PEERCHIVE_ANALYTICS_PEPPER`, 사용자 id), `project_hash` 같은 방식, `hash_key_id` = pepper의 SHA-256 앞 8자. 분석 pepper는 삭제 pepper와 다르고 **바꿀 수 있습니다**(바꾸면 이전 이벤트와 이어지지 않음 — 정기 교체로 장기 추적을 끊는 수단). production에서 없으면 분석을 끕니다(서비스는 그대로).
- 기록 위치: 서비스가 업무 변경과 같은 트랜잭션에서 insert 한 줄(싸고, 업무가 되돌려지면 이벤트도 사라짐). outbox는 쓰지 않았습니다.
- **수집 거부**: 설정 화면(`/onboarding`의 "파일럿 사용 기록")·`PATCH /api/v1/me/preferences {analyticsOptOut}`. 거부하면 이후 이벤트를 만들지 않고 지난 이벤트(지금 pepper 기준)도 지웁니다. 파일럿 동의 문구는 자리표시이며 안내문 확정 뒤 바꿉니다. 탈퇴 정리도 그 사람의 이벤트를 지웁니다.
- **운영자 지표** `GET /api/v1/operator/metrics?from=&to=`(운영자만, 화면 `/operator/metrics`): 이벤트만 읽어 활성화(가입 7일 안 과제 + 로그 3 + 근거 1, 7일이 지난 사람만 분모)·기록 유지(`to` 이전 4주 중 3주 이상)·사례 전환(후보를 만든 과제 중 게시한 과제, 근사)·북극성(포크 + 도움됐어요)·리포트 내보내기·포트폴리오 공유·노트 게시·이벤트별 개수. **5 미만은 null**(분자·분모 중 하나라도 가려지면 비율도 null). 작성 시간은 이벤트로 잴 수 없어 null.

### 관측

`GET /api/v1/health?deep=1`(운영자만: 로그인 안 하면 401, 운영자 아니면 403 `operator_only`, 항상 200 + `status: ok|degraded`): DB 왕복, 저장소 쓰기·읽기·지우기 시험(격리 접두어 일회용 키, 흔적 없음), worker 상태 기록 나이(1분마다 기록, 180초 넘으면 stale), 주기 작업의 마지막 결과, outbox 미전달 수·가장 오래된 나이, pg-boss 실패·dead-letter 수, 유예 + 1일이 지났는데 정리되지 않은 탈퇴 계정 수(삭제 실패 신호), 점검 모드·공개 읽기 스위치 상태. 얕은 `/api/v1/health`는 그대로입니다.

## 결과

- 탈퇴가 "표시만"이 아니라 실제 삭제가 되고, 오래된 백업을 복구해도 재적용으로 다시 지워집니다(복구 연습 스크립트가 매번 확인). 팀 기록은 보존되고 탈퇴자는 "탈퇴한 사용자"로 보입니다.
- 남는 것(알려진 한계): 철회·대체된 **이전 release 스냅샷**(비공개, 공개 조회되지 않음)에는 팀 과제의 그 사람 표시 이름·자료가 남습니다(팀의 exclude-declined가 이 스냅샷을 씀). 운영자는 신고된 release 스냅샷을 볼 수 있습니다. 감사 이벤트·신고·조치 행은 가명 사용자 id를 가리킵니다. 외부 검색 캐시·이미 받은 PDF는 회수하지 못합니다. 백업 안의 자료는 보존 기간(기본 14일)이 지나야 사라집니다.
- 백업과 장부 내보내기 사이(최대 24시간, RPO)에 들어온 탈퇴 요청은 DB를 잃으면 함께 잃습니다(당사자가 다시 요청해야 함). 장부 내보내기를 백업보다 자주 다른 곳에 두면 줄어듭니다.
- 재적용은 모든 사용자 id를 HMAC하므로 사용자 수에 비례합니다(파일럿 규모 문제없음).
- 분석 지표는 이벤트를 메모리로 읽어 계산합니다(파일럿 규모). 커지면 SQL 집계·materialized view로 바꿉니다.

## 대안

- 탈퇴 즉시 cascade 삭제: 팀 이력·동료 확인·공개 동의 판정이 조용히 깨지고(§6.6), 실수·탈취를 되돌릴 시간이 없음.
- 팀 기록도 모두 삭제: 다른 사람의 근거·리포트·공개 사례가 깨짐. 내용 대신 가명 처리를 택함.
- 장부에 사용자 id를 그대로: 복구 뒤 맞추기는 쉽지만 장부 자체가 "누가 탈퇴했는지" 목록이 됨.
- 외부 분석 도구(제품 분석 SaaS): 의존성·데이터 국외 이전·동의 범위 문제. pilot 규모에서는 같은 DB의 표 하나로 충분.
- 이벤트를 outbox로: 이벤트 하나에 큐 왕복이 생기고 이득이 없음(insert 한 줄).
- 점검 모드를 공개 읽기 스위치로 대신: 로그인·쓰기가 열려 있어 재적용 전에 복구된 데이터가 바뀌거나 보임.
