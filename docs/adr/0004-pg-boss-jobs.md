# 0004. 비동기 작업은 pg-boss + outbox

- 상태: 채택
- 날짜: 2026-10-18(구현 2026-10-19, T-05: `apps/worker`, pg-boss 12.36.0, [ADR 0007](0007-file-storage-and-scanning.md))

## 맥락

파일 검사, 공개·철회 전파(검색 색인·캐시·임베딩·집계 정리), AI 작업, PDF 생성은 요청 밖에서 재시도 가능하게 실행해야 합니다(§3, §11, §14). 1인 운영이므로 Redis·Kafka 같은 별도 인프라는 피하고 싶습니다.

## 결정

- 작업 큐는 PostgreSQL 테이블 기반 [pg-boss](https://github.com/timgit/pg-boss)를 씁니다.
- 상태 변경과 후속 작업 기록은 같은 트랜잭션의 outbox 행으로 남기고, 전달기가 pg-boss 작업으로 옮깁니다. 철회는 DB 상태·`access_epoch` 갱신이 먼저이며 파생 데이터 정리가 늦어도 읽기 경로가 상태를 먼저 확인합니다.
- 작업은 idempotent하게 작성하고 retry·backoff·dead-letter를 설정합니다. worker 장애 시 비공개 자료가 공개되는 fallback은 두지 않습니다.
- Phase 0에서는 의존성을 설치하지 않았습니다. `apps/worker`를 만들 때 당시 안정 버전을 정확히 고정하고 상태를 `채택`으로 바꿉니다.

## 결과

- DB 하나로 데이터와 작업 상태를 함께 백업·복구할 수 있습니다.
- 처리량이 커지면 DB 부하가 늘 수 있어, worker backlog를 관측 지표로 둡니다.

## 대안

- BullMQ + Redis: 성숙하지만 인프라가 하나 늘고 트랜잭션 일관성을 별도로 맞춰야 함.
- 클라우드 큐(SQS 등): 공급자 종속, 로컬 개발 복잡도 증가.
- 요청 내 동기 처리: 파일 검사·AI·철회 전파의 지연과 실패 처리를 감당할 수 없음.
