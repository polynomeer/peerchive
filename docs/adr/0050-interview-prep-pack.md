# 0050. 면접 준비 팩: 케이스 문장이 인용한 ⚖️결정·회의 결정·🧱막힘 로그에서 읽을 때마다 만드는 템플릿 예상 질문(근거 kind·key, 없으면 일반 질문 실패·의견 충돌·다시 한다면) + (사용자, 공개, 안정된 질문 키)마다 본인만 보는 답변 메모와 질문 글만 공개하는 선택(`interview_prep_entries`) + 실명 페르소나 대표 케이스가 지금 볼 수 있을 때만 "이 지원자에게 물어보면 좋은 질문" + 지금 만들어지지 않는 질문의 메모는 지우지 않고 본인에게만 "보관된 메모" + 탈퇴 때 모두 삭제, 플래그 없음

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

E-06은 DELIVERY_PLAN §4.4 P1 보완 백로그 항목입니다: "대표 사례의 결정·막힘 인용으로 예상 질문 생성(템플릿, AI 선택), 답변 메모는 본인만, 학생이 고른 질문만 채용자 화면에 “물어보면 좋은 질문”으로 표시". 관련 설계와 앞선 결정:

- PROOFU_EVOLUTION_PLAN §10.5(대표 사례마다 결정·막힘 로그에서 예상 질문 — “왜 실시간 센서 대신 수동 입력을 택했나?”, “가장 크게 실패한 것은?”, “팀 내 의견 충돌은?” — 학생이 답변 메모를 비공개로, 허용하면 채용자 화면에 **“이 지원자에게 물어보면 좋은 질문”**으로 일부), §10.3(같은 공개 버전의 두 보기 — 포트폴리오 요약 보기는 채용자용), §10.4(근거로 이동), §15(AI 없이도 핵심 기능).
- ADR 0014(T-14 케이스 스터디: 게시된 release 하나에 고정, 문장마다 스냅샷 `{releaseVersion, kind, key}` 인용, `generator = 'template'`, 공개 읽기는 요청마다 release 제공 가능 여부 확인), 0015(운영 조치로 가린 항목·케이스 숨김), 0028(S-01 페르소나: 표시명 판에는 대표 케이스 없음, 채용자용은 실명 페르소나), 0026(C-08 익명 스터디 기록은 포트폴리오에 연결하지 않음).
- 스냅샷 로그 키는 같은 공개의 release끼리 같습니다(공개마다 안정된 키, ADR 0012). 케이스 스터디는 release가 바뀌면 "새 버전으로 다시 만들기"로 새 행이 됩니다.

## 결정

### 1. 질문은 저장하지 않고 읽을 때마다 만듦(결정적 템플릿)

- `@peerchive/domain` `generateInterviewQuestions({snapshot, sections, isHidden})`: 케이스 문장(모든 구역)의 인용 중 `log`를 처음 나온 순서대로 보고, 스냅샷에서 그 로그의 태그에 따라 질문을 만듭니다.
  - ⚖️결정: 선택지가 둘 이상이면 “왜 {다른 선택지} 대신 {선택}을 택했나요?”, 아니면 “{선택}을 정할 때 무엇을 가장 중요하게 봤나요?” (키 `decision:<로그 키>`). “지나고 보니”가 있으면 “지금 다시 한다면” 질문 하나 더(`hindsight:<로그 키>`, 회고).
  - 회의 정리(결정 사항 있음): 첫 결정 사항을 두고 의견이 갈렸는지(`meeting:<로그 키>`, 협업·의견 충돌).
  - 🧱막힘: 스냅샷에 그 막힘을 가리키는 💡해결이 있으면 원인을 찾은 과정, 없으면 “기록상 해결되지 않았습니다. 지금이라면”(`stuck:<로그 키>`).
  - 근거 있는 질문은 최대 9개, 그 뒤 일반 질문(출처 없음): `generic:failure`(가장 크게 실패한 것), `generic:conflict`(팀 내 의견 충돌, 팀 과제만), `generic:retro`(다시 한다면).
- 질문 글은 고정 틀 + 스냅샷 글(선택·선택지·증상·회의 결정, 잘라서)뿐이고 사실을 만들어 내지 않습니다. 조사는 받침으로 고르고 한글이 아니면 “을(를)”. 인용하지 않은 로그, 운영 조치로 가린 로그(T-15)는 근거가 되지 않습니다.
- 질문마다 근거 `{kind: 'log', key}`를 싣고, 화면은 그 공개 기록으로 가는 출처 칩을 보여 줍니다. 근거가 없으면 일반 질문으로 표시합니다.
- **저장하지 않는 이유**: 케이스 문장·인용이 바뀌면 다음 요청부터 질문이 바뀌므로 "다시 만들기" 작업·동기화 상태·worker가 필요 없고, 공개 화면이 낡은 질문을 보여 줄 일이 없습니다. 같은 입력이면 같은 질문(같은 키·순서)입니다.
- **AI 자리**: `InterviewQuestionGenerator` 타입과 `INTERVIEW_TEMPLATE_GENERATOR`({name: 'template', generate})를 두고 서버는 그것만 부릅니다(`questionsForCase`). E-12 이후 AI 생성기를 고를 수 있게 하더라도 같은 키 규칙(근거 있는 질문은 스냅샷 로그 하나를 가리킴)·출처 규칙을 지켜야 하며, 공급자가 없으면 템플릿으로 동작합니다. 팩 DTO의 `generator`는 지금 늘 `template`입니다.

### 2. 항목: (사용자, 공개, 질문 키)마다 메모·공개 선택

- `interview_prep_entries`(user_id, publication_id, question_key unique; `question_text`, `note` 1~2000자 또는 null, `shown`, check “메모나 선택 중 하나는 있음”). 메모도 선택도 없어지면 행을 지웁니다.
- **공개(publication) 단위로 묶는 이유**: 질문 키가 공개마다 안정된 로그 키라서, 케이스를 고쳐 인용이 잠시 빠졌다 돌아오거나, 원본이 새 공개 버전으로 바뀌어 케이스를 다시 만들어도 같은 질문이면 같은 메모·선택이 이어집니다. 같은 공개로 만든 직무별 케이스 여럿은 같은 질문에 같은 메모를 공유합니다(같은 기록에 대한 같은 답).
- `question_text`는 마지막으로 저장할 때의 질문 글입니다. 지금 질문 글과 다르면 팩이 `textChanged`로 “메모를 다시 확인하세요”를 보여 줍니다(로그 글은 release마다 다를 수 있음).

### 3. 고아 메모: 지우지 않고 본인에게만 "보관된 메모"

- 지금 그 케이스에서 만들어지지 않는 키의 항목(인용을 뺐거나, 가린 로그이거나, 원본을 볼 수 없게 된 케이스)은 `archived`로 본인에게만 보여 줍니다. **공개 선택은 효력이 없습니다**(공개는 지금 만들어지는 질문과의 교집합만).
- 보관된 항목은 지우기만 됩니다(`note: null, shown: false`). 공개로 고르거나 메모를 새로 쓰면 422 `questionKey: not_current`. 같은 질문이 다시 만들어지면(인용을 되돌림·새 버전) 메모와 선택이 그대로 다시 붙습니다 — 공개 선택도 되살아나므로 화면에 안내합니다.
- 자동 삭제하지 않는 이유: 학생이 쓴 비공개 글을 편집 한 번으로 잃게 하지 않으려는 것입니다. 공개 하나에 100개 한도(409 `limit_reached`)로 무한히 쌓이지 않게 합니다.

### 4. 비공개: 메모는 작성자만

- `GET·PUT /case-studies/:id/interview-prep`는 케이스 작성자만(다른 사람에게는 같은 공개의 팀원이라도 404, 비로그인 401). 메모 글은 감사 기록에도 넣지 않습니다(공개 선택을 바꿀 때만 `interview_prep.shown_toggle` — 케이스 id·질문 키·참거짓).
- 공개 경로(`publicInterviewQuestions`)는 `note` 열을 고르지 않습니다. 공개 프로필 JSON·HTML·OG·인쇄 보기·README 카드·검색 문서·피드 어디에도 메모가 없습니다. 판 미리보기(본인)도 공개 보기와 같아 메모를 싣지 않습니다.

### 5. 공개 표시: 실명 페르소나 대표 케이스가 지금 볼 수 있을 때만

- `buildPortfolioView(..., {askQuestions})`를 실명 페르소나의 공개 프로필과 실명 판 미리보기만 켭니다. 볼 수 있는 대표 케이스(`isPubliclyVisible`: 게시 중 + 고정 release 제공 가능 + 숨김 아님 + 익명 스터디 아님)마다 `askQuestions`(질문 글·종류·근거 칩)를 싣고, 화면은 케이스 카드 아래 “이 지원자에게 물어보면 좋은 질문”으로 보여 줍니다(답변 없음 안내). 인쇄 보기도 같은 컴포넌트라 질문 글이 주소와 함께 나옵니다. README 카드에는 싣지 않습니다.
- 게시 취소·운영 조치 숨김·원본 철회·대체·엠바고는 다음 요청부터 사라집니다(요청마다 같은 판정). 표시명 페르소나는 대표 케이스가 없고 옵션도 꺼서 어떤 경우에도 나오지 않습니다.
- 공개로 고르는 것은 케이스 상태와 무관하게 언제든 할 수 있고, 팩 DTO의 `publiclyVisible`이 지금 보이는지 알려 줍니다.

### 6. 플래그·탈퇴 정리

- 플래그 없음(P1, 기존 공개 경로를 넓히지 않고 학생이 고른 질문 글만 더함, 기본은 아무것도 공개하지 않음).
- 탈퇴 정리(worker): 그 사람의 항목(메모·선택)을 모두 지웁니다(공개 행보다 먼저). 장부 개수 `interview_prep_entries`.

### 상태 코드 요약

| 경로 | 성공 | 오류 |
|---|---|---|
| `GET /case-studies/:id/interview-prep` | 200 팩(questions·archived·available·publiclyVisible) | 401, 404 |
| `PUT /case-studies/:id/interview-prep {questionKey, note?, shown?}` | 200 팩 | 401, 404, 409 `limit_reached`, 422 `questionKey: invalid·not_current`·`note: too_long·invalid`·`_: no_changes`, 429 |

## 결과

- 학생은 케이스 편집 화면 아래 "면접 준비 팩"에서 자기 기록에 근거한 예상 질문을 보고 비공개로 답을 준비하며, 고른 질문만 채용자 화면에 “이 지원자에게 물어보면 좋은 질문”으로 내놓습니다. 채용자는 그 질문의 근거 칩으로 공개 기록에 바로 갑니다.
- migration `0047_interview_prep_pack`(테이블 1개, enum 없음, 빈 DB 처음부터 migrate 확인).
- 테스트: domain 생성 규칙(인용한 결정·회의·막힘만, 일반 질문, 결정성, 가린 항목, 한도, 키·조사·메모 검증), web 통합 `interview-prep.integration.test.ts`(근거 kind·key, 작성자만, 공개 JSON·README 카드·미리보기·검색 문서에 메모 없음, 실명·지금 볼 수 있을 때만 표시, 게시 취소·숨김·철회 후 사라짐, 표시명 0건, 인용 변경 시 보관·복귀·삭제), worker 탈퇴 정리, E2E `e06-interview-prep.spec.ts`(화면에서 메모·선택 → 공개 프로필·인쇄 보기에 질문만, 메모 0건).
- 한계: 질문을 직접 쓰거나 고칠 수 없습니다(템플릿 질문만). 검증·회고 로그는 질문 근거가 되지 않습니다. 같은 공개의 직무별 케이스가 메모·선택을 공유합니다. 보관된 메모는 그 공개로 만든 케이스의 팩에서만 보이므로, 케이스를 하나도 남기지 않으면 볼 길이 없습니다(행은 탈퇴 때 지움). 질문 순서·개수를 학생이 바꿀 수 없습니다.

## 대안

- **질문을 테이블에 저장하고 케이스·release가 바뀔 때 다시 만들기**: 질문 글을 고정할 수 있지만 다시 만들기 시점·worker·낡은 질문 처리가 필요하고, 공개 화면이 케이스 문장과 어긋날 수 있습니다.
- **케이스 스터디 id로 메모를 묶음**: 단순하지만 새 공개 버전으로 케이스를 다시 만들면 메모가 모두 끊깁니다.
- **고아 메모 자동 삭제**: 깔끔하지만 문장 하나를 빼는 편집으로 학생의 비공개 글을 잃게 됩니다.
- **답변 일부도 공개**: 채용자에게 더 많은 정보지만 §10.5는 질문만 보여 주며, 준비한 답을 미리 보이면 면접 질문의 의미가 줄어듭니다.
- **기능 플래그 뒤에 둠**: 기본이 "아무것도 공개하지 않음"이고 공개 범위를 넓히지 않으므로 플래그가 지킬 위험이 없습니다.
