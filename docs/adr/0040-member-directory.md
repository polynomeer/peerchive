# 0040. 동문회·OB 방 멤버 명부: 동의한 멤버만 행(요청마다 `consent: true`) + 항목별 비우기 + 철회·나가기·익명 전환·탈퇴 때 행 즉시 삭제(`withdrawn_at` 없음) + 익명 방에는 명부 없음 + 쪽 최대 20·사용자별 10분 20쪽·내보내기 경로 없음

- 상태: 채택
- 날짜: 2026-11-01

## 맥락

A-03은 DELIVERY_PLAN §4.3 P2 백로그의 세 번째 졸업생 공간 항목입니다: "동의 없는 행 0건, 항목별 비우기, 철회·탈퇴 즉시 삭제, 내보내기 경로(API·CSV·PDF·일괄 조회) 없음, 페이지 크기·조회 rate limit". 수용 시나리오 §5.3 X: "명부에는 공개에 동의한 멤버만, 동의한 항목만 나타납니다. 멤버가 동의를 철회하거나 방을 나가면 즉시 사라집니다. 명부를 CSV·PDF로 내보내거나 한 번에 전부 조회하는 경로가 없고, 짧은 시간에 많은 페이지를 넘기면 rate limit에 걸립니다." §7 GA 게이트는 “A-03 명부 회귀 테스트”를 졸업생 공간 개방 조건으로 둡니다. 관련 설계와 앞선 결정:

- SYSTEM_DESIGN §6.7.2 DirectoryEntry: `space_id, user_id, cohort_label?, current_work?, interests[], contact_method?, consented_at, withdrawn_at?` — 동의한 멤버만 행, 항목별로 비울 수 있음, 철회·탈퇴 시 즉시 행 삭제, 내보내기 API·CSV·PDF·일괄 조회 없음, 페이지당 개수 제한과 조회 rate limit, 방 밖 검색·추천·PersonaActivity에 쓰지 않음. §8.4: 멤버 명부 보기는 같은 방 멤버만 “동의한 멤버의 동의 항목만”, 방장·admin도 같음(내보내기 불가), 운영자는 조치 목적만. 명부는 방 탈퇴 시 삭제.
- ADR 0038(A-01): alumni 템플릿·방별 프로필, 이름 규칙(실명 방 실명 고정, 표시명 방 방별 이름, 익명 방에는 방별 프로필 없음). ADR 0039(A-02): `loadAlumniRoom`(플래그 → 읽을 수 있는 공간 → alumni 방 → active 멤버, 아니면 404)·`roomMemberNames`·나가기 정리. ADR 0037 §1: P2 플래그 `alumni`, 꺼지면 404. ADR 0021·0029: 커뮤니티 구역 표는 공개·social 경로가 읽지 않음 + S-02 속성 테스트.

## 결정

### 1. 표 `directory_entries` (migration `0036_member_directory`)

- PK `(space_id, user_id)`. 열: `cohort_label?`(1–20자), `current_work?`(1–60자), `interests text[] not null default '{}'`(최대 5개, 하나 1–20자 — 원소 길이는 서비스가 확인), `contact_method?`(1–100자), `consented_at`, `updated_at`. 인덱스 `(space_id, consented_at)`(쪽 조회 순서)·`user_id`(탈퇴 정리).
- **`withdrawn_at`은 두지 않습니다.** 설계 초안에는 있었지만 계획은 “철회 시 즉시 삭제”이고, 철회 시각을 남기면 “이 사람이 이 방 명부에 있었다”가 행으로 남습니다. 철회는 행 삭제이므로 이 표의 모든 행은 지금 동의 중인 항목입니다. 다시 동의하면 새 행(새 `consented_at`)입니다.
- **커뮤니티 구역**에 두어 C-05·S-02 경계 검사(스키마 머리말로 표 목록을 읽음)와 social DB 역할 권한 검사가 자동으로 덮습니다. social 역할에는 권한을 주지 않습니다(`peerchive_apply_social_grants`는 표를 이름으로만 허용하므로 다시 정의하지 않음). 새 enum이 없어 `ALTER TYPE ADD VALUE` 문제는 없습니다.
- 기수는 방별 프로필(A-01)의 기수와 **따로** 둡니다. 명부는 별도 동의이므로 방별 프로필의 기수를 자동으로 명부에 싣지 않습니다(방별 프로필은 방 안 글·댓글 표시용, 명부는 동의한 공개 항목).

### 2. 동의: 행을 만드는 요청이 곧 동의

- `PUT /community/spaces/:slug/directory/me {consent: true, cohortLabel?, currentWork?, interests?, contactMethod?}` — 전체 교체. **`consent`가 정확히 `true`가 아니면 422 `consent: required`**(만들 때와 바꿀 때 모두). 화면은 동의 설명 아래 체크 상자를 체크해야 보냅니다. 멤버가 되거나 명부를 보는 것만으로는 행이 생기지 않습니다(테스트가 확인).
- 모든 항목은 선택이고 빈 값·`null`·보내지 않음은 비움(관심사는 빈 배열)입니다. 모두 비워도 유효합니다(“이름만 올림”).
- 연락 방법은 **자유 글**(한 줄, 100자)이고 형식을 검사하지 않습니다. 화면이 “이 방 멤버 모두에게 보입니다. 전화번호·개인 메일 같은 민감한 정보는 적지 않는 것을 권합니다”라고 경고합니다. 메신저 아이디·링크·“방 오픈채팅으로” 같은 다양한 형식을 받으려는 선택입니다.
- 관심사는 대소문자를 무시하고 같은 값을 하나로 합칩니다. 입력 검사는 방별 프로필과 같은 한 줄 규칙(NFC·공백 하나로·제어 문자·줄바꿈 거부)입니다.
- 저장 한도 사용자·시간당 30번(429). 보관·제한된 방 409 `space_not_active`, 커뮤니티 쓰기 제한(C-06) 중이면 403 `write_restricted`(연락 방법·하는 일은 다른 멤버에게 보이는 글이므로).

### 3. 누가 어디서: alumni 방 멤버만, 익명 방에는 없음

- 모든 경로는 플래그 뒤이고 `loadAlumniRoom`(alumni 템플릿 사용자 방의 **active 멤버만**, 아니면 404 — 운영자도 멤버가 아니면 404)을 거칩니다. 일반 방 404.
- **익명 방에는 명부가 없습니다**(보기·동의 409 `directory_unavailable`). 이름 없는 명부는 쓸모가 없고, 이름을 숨긴 채 기수·하는 일·관심사·연락 방법을 모으면 소규모 방에서 익명이 깨집니다(ADR 0038에서 익명 방에 방별 프로필·배지를 두지 않은 것과 같은 이유). 효력이 생긴 예약 전환(`nameModeNow`)도 같게 봅니다.
- 방이 익명으로 바뀌면 worker의 이름 표시 방식 적용(`applyNameModeChange`)이 같은 트랜잭션에서 그 방의 명부 행을 모두 지웁니다(되돌려도 살아나지 않음 — 다시 동의해야 함). 적용 전이라도 효력 시각이 지나면 API는 409입니다.
- 철회(`DELETE …/directory/me`)는 보관된 방·익명 방에서도, 쓰기 제한 중에도 됩니다(멱등, 플래그 꺼짐·멤버 아님은 404).

### 4. 이름

- 방별 프로필 규칙(A-01·`roomMemberNames`)을 그대로 씁니다: **실명 방은 실명**(`users.real_name`, 없으면 `실명 미입력`), **표시명 방은 방별 프로필 이름**(없으면 `방별 이름 없음`). 표시명 페르소나 이름·계정 표시 이름·핸들은 읽지 않습니다(ADR 0030).
- 이름은 읽을 때의 값입니다. 명부 행에 이름을 저장하지 않습니다.
- 응답에는 사람 id·핸들·프로필 링크가 없고, 명부 항목 id도 없습니다(PK가 (방, 사람)이라 가리킬 id가 필요 없음). 내 항목은 `mine: true`로만 표시합니다.

### 5. 내보내기 경로 없음: 쪽 조회 + rate limit

- 조회는 `GET /community/spaces/:slug/directory?page=&pageSize=` 하나뿐입니다. 동의한 active 멤버(active 계정)의 항목을 **동의한 순서**(`consented_at`, `user_id`)로 한 쪽씩 돌려줍니다.
  - `pageSize`는 1~20(기본 20), 20을 넘으면 422 `too_large`. `page`는 1~500. **그 밖의 조회 값(`all`·`limit`·`format`·`export` 등)은 422 `unknown`** — “전부 가져오기”나 다른 형식이 없다는 것을 계약으로 분명히 합니다.
  - 전체 수는 돌려주지 않고 `hasNext`만 줍니다(마지막 쪽을 계산해 건너뛰는 도구를 만들기 어렵게, 그리고 필요 없는 집계를 내지 않으려고).
- **쪽을 볼 때마다 사용자별 rate limit**(`directory_page_view`, 모든 방 합쳐 **10분에 20쪽**, 넘으면 429). 트랜잭션 밖에서 세어 429로 끝나도 카운터가 남습니다. 접근 검사(404·409)와 조회 값 검사(422)를 먼저 해서 그런 요청은 세지 않습니다. 20쪽 × 20명 = 10분에 400명까지라 보통 규모의 방은 사람이 넘기며 읽기에 충분하고, 기계적으로 빠르게 넘기면 걸립니다(§5.3 X). 화면은 429에 “10분쯤 뒤 다시 보세요”를 보여 줍니다.
- 화면은 저장·철회 뒤 쪽을 다시 받지 않고 보이는 목록에서 내 항목만 바꿉니다(조회 한도를 쓰지 않게).
- 방장·운영진·운영자에게도 내보내기·일괄 조회는 없습니다(§8.4 “내보내기 불가”). 운영자 화면에 명부를 붙이지 않았습니다.
- 테스트가 `server/api` 아래 라우트 목록을 읽어 명부 경로가 정확히 3개(`directory/index.get`·`me.put`·`me.delete`)이고 csv·pdf·export·download·bulk·all이 없음을, `directoryEntries`를 참조하는 서버 코드가 명부 모듈뿐이고 worker는 삭제만(탈퇴·익명 전환) 하는지 확인합니다.

### 6. 경계: 방 밖에는 0건

- 명부는 커뮤니티 모듈(`server/modules/community/member-directory.ts`)만 읽고 씁니다. 공개 프로필·README 카드·활동 목록(PersonaActivity)·피드·추천·검색·운영 화면은 이 표를 읽지 않고, social DB 역할은 권한이 없습니다.
- S-02 속성 기반 테스트(`identity-boundary.integration.test.ts`)의 무작위 세계에서 익명이 아닌 alumni 방 멤버가 고유 표식의 기수·하는 일·관심사·연락 방법으로 동의하고, 모든 공개·소셜 출력·피드·추천에 그 값이 0건인지, 공개 검색 API와 `search_documents`에도 없는지 봅니다. social 역할 테스트는 `directory_entries`가 커뮤니티 표 목록에 있고 `SET ROLE`로 읽으면 거부되는지 봅니다. 별도 난수(시드 ^ 0xa03)를 써서 기존 세계는 바뀌지 않습니다.

### 7. 감사 기록

- 동의·바꾸기 `community.directory_consent {created, filled}`(새 동의인지·채운 항목 수), 철회 `community.directory_withdraw {cause: 'self'}`. **값(기수·하는 일·관심사·연락 방법)은 남기지 않습니다.** 동의 사실 자체는 “언제 동의했는가”를 확인할 근거로 남깁니다(행은 철회 때 지워지므로).
- 나가기·내보내기에 따른 삭제는 기존 `community.member_leave`·`member_remove` 기록으로 충분해 따로 남기지 않습니다. 명부 조회는 남기지 않습니다(누가 누구를 봤는지 기록하지 않음). 분석 이벤트는 더하지 않았습니다.

### 8. 삭제

| 일 | 명부 행 |
|---|---|
| 동의 철회(`DELETE …/directory/me`) | 바로 삭제(멱등) |
| 방 나가기(`leaveSpace`)·내보내기(`removeMember`) | 같은 트랜잭션에서 삭제(플래그와 무관) |
| 방이 익명으로 바뀜(worker) | 그 방 전체 삭제 |
| 탈퇴 정리(worker purge) | 그 사람의 모든 방 행 삭제(삭제 장부 `directory_entries`, 개수만) |
| 플래그 끄기·방 보관 | 남김(다시 켜면 보임, 보관된 방은 읽기·철회만) |

### 9. 화면

- `/community/s/:slug`: alumni 방(익명 아님)의 active 멤버에게 “멤버 명부” 링크.
- `/community/directory/:slug`: 동의 설명(동의한 멤버·항목만, 방 멤버 모두에게 보임, 방 밖에는 안 나감, 언제든 비우기·철회, 나가면 삭제, 내보내기 없음), 항목 입력(연락 방법 아래 경고), 동의 체크 상자, “동의하고 명부에 올리기/바꾸기”·“동의 철회”, 명부 목록과 이전·다음 쪽. Nuxt 중첩 라우트를 피하려고 방별 프로필·모임 화면처럼 별도 경로입니다(같은 `/community/**` 가드·noindex).

| 경로 | 성공 | 오류 |
|---|---|---|
| 모든 새 경로 | – | 플래그 꺼짐 404, 401 |
| `GET /community/spaces/:slug/directory?page=&pageSize=` | 200 | 404(멤버 아님·alumni 아님), 409 `directory_unavailable`, 422 `page`·`pageSize: invalid\|too_large`·그 밖의 값 `unknown`, 429 |

## 결과

- 명부에는 동의한 멤버의 동의한 항목만 있고, 철회·나가기·익명 전환·탈퇴로 바로 사라집니다. 명부를 통째로 가져가는 경로가 없고, 빠르게 넘기면 rate limit에 걸립니다(§5.3 X). GA 게이트의 “A-03 명부 회귀 테스트”는 `member-directory.integration.test.ts`와 S-02 속성 테스트입니다.
- 한계: rate limit은 사람이 천천히 넘기며 옮겨 적는 것까지 막지는 못합니다(방 멤버에게 보이는 정보의 본질적 한계 — 그래서 연락 방법 경고와 항목별 비우기를 둠). 고정 창 rate limit이라 창 경계에서 최대 2배까지 허용될 수 있습니다(기존 `hitRateLimit`과 같음). 연락 방법 자유 글의 오남용(스팸 링크)은 명부 항목이 아직 신고 대상이 아니므로 방 운영진의 내보내기·글 신고로 대응합니다.

## 대안

- **`withdrawn_at`을 두고 소프트 삭제**: 다시 동의할 때 값을 되살릴 수 있지만 철회한 사람의 정보와 “명부에 있었다”는 사실이 남습니다. 계획대로 즉시 삭제했습니다.
- **항목별 동의 플래그(필드마다 공개 여부)**: 값을 비우는 것과 같은 효과에 상태만 늘어납니다. “적으면 공개, 비우면 비공개”로 단순하게 두었습니다.
- **익명 방에서 이름 없이 명부**: 이름 없는 명부는 연락 수단으로 쓸모가 없고, 기수·관심사 조합이 익명을 깨뜨립니다. 막았습니다.
- **방별 프로필의 기수를 명부에 자동으로**: 방별 프로필은 명부 동의와 별개이므로 자동으로 싣지 않습니다.
- **커서 기반 조회**: 오프셋보다 안정적이지만 쪽 번호가 없으면 “n쪽” 탐색이 어렵고, rate limit이 실제 방어선이라 차이가 작습니다. 쪽 번호 상한(500)을 두었습니다.
- **방(공간)별 rate limit**: 여러 방에 들어가 각각 긁는 것을 막지 못합니다. 사용자별로 셉니다.
- **전체 수 표시**: 편하지만 필요 없는 집계이고 마지막 쪽 계산을 돕습니다. `hasNext`만 줍니다.
