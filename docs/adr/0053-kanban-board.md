# 0053. 칸반 보드 보기: 리스트와 같은 할 일 데이터를 상태별 열로 보여 주는 보기(이 기기에 기억) + 드래그·키보드(Shift + 방향키)·카드 "옮기기" 메뉴가 같은 자리 계산(`planTaskMove`)을 거쳐 같은 요청 하나 + 열 사이 이동은 상태 변경(`PATCH`·`/complete`)에 선택 `position`(한 트랜잭션, 같은 권한·version·한도) + 같은 열 안은 기존 순서 변경 API + 완료 열이면 리스트와 같은 완료 프롬프트, migration·의존성·플래그 없음

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

E-09는 DELIVERY_PLAN §4.4 P1 보완 백로그 항목입니다: "상태별 열 보드, 드래그와 같은 결과를 내는 키보드·버튼 대안, 리스트 보기와 같은 권한·순서 데이터, 완료 시 로그 전환 프롬프트 유지". 제품 기획 §6.6은 칸반을 버리지 않고 '할 일' 보기로 남기며, MVP는 리스트 보기와 상태 변경 메뉴를 우선하고 "보드(드래그) 보기는 P1이며 드래그에는 키보드·버튼 대안을 둡니다"라고 정했습니다. 2019 ProofU의 Board/List/Card(원본 `frontend/`, 보존 대상이라 고치지 않음)가 v2에서 살아남는 형태입니다.

- T-07(할 일): 상태 `todo`·`doing`·`done`, (프로젝트, 상태) 목록마다 1부터 빈틈없는 `position`, 상태를 바꾸면 새 목록 맨 뒤. 순서 변경 `PUT /api/v1/projects/:id/tasks/order {status, taskIds}`는 한 상태 목록 전체의 순열만 받음(422 `mismatch`·`duplicate`). 관리는 active owner/editor, 수정·완료는 `expectedVersion`(409 `version_conflict`). 완료 `POST /api/v1/tasks/:id/complete`가 프롬프트를 돌려줌.
- 시나리오 H(키보드·모바일): 리스트 보기는 드래그 없이 상태 메뉴와 ▲▼로 모두 조작합니다.
- 기존 API만으로 열 사이의 특정 자리로 옮기려면 상태 변경(맨 뒤) + 순서 변경 두 번을 보내야 해서, 두 번째가 실패하면 반쯤 옮겨진 상태가 남습니다.

## 결정

### 1. 데이터·API: 리스트와 같은 행, 상태 변경에 자리만 더함

- 새 테이블·열 없음(migration 없음). 보드는 리스트와 같은 `GET /api/v1/projects/:id/tasks` 응답을 상태별로 묶어 그립니다.
- **같은 열 안 이동**은 리스트 ▲▼와 같은 `PUT …/tasks/order`(전체 순열, version을 올리지 않음)를 그대로 씁니다.
- **열 사이 이동**은 상태 변경에 선택 `position`(새 상태 목록에서 1부터 센 자리, 정수 1~500)을 붙여 한 요청·한 트랜잭션으로 보냅니다.
  - `PATCH /api/v1/tasks/:id {expectedVersion, status, position?}`, 완료 열이면 `POST /api/v1/tasks/:id/complete {expectedVersion, position?}`.
  - 서버는 지금과 같이 새 목록 맨 뒤로 옮기고 원래 목록을 당긴 뒤, 같은 트랜잭션에서 새 목록을 `insertTaskAt`(목록 길이 + 1을 넘으면 맨 뒤)으로 다시 매깁니다. 자리를 생략하면 지금과 똑같이 맨 뒤입니다(리스트 보기는 그대로).
  - 상태가 바뀌지 않는 요청(생략·같은 상태)의 `position`은 422 `{position: 'status_required'}`, 정수가 아니거나 범위 밖이면 422 `{position: 'invalid'}`. 같은 열 안 이동은 순서 변경 API 하나로만 합니다(규칙을 두 갈래로 나누지 않음).
  - 이미 완료한 할 일에 `/complete`를 다시 보내면(재전송) 지금처럼 아무것도 바꾸지 않고 `position`도 무시합니다.
- 권한·version·열린 할 일 한도·감사 이벤트는 자리 없는 상태 변경과 같습니다(viewer·reviewer 403, 비멤버 404, 낡은 version 409, 감사는 `task.update`·`task.complete` 그대로 — 자리는 남기지 않음). 프로젝트 행을 잠근 트랜잭션이라 순서·한도 판정이 다른 쓰기와 엇갈리지 않습니다.

### 2. 자리 계산은 domain 한 곳

`@peerchive/domain` tasks에 순수 함수를 둡니다. 드래그·키보드·버튼이 모두 같은 함수를 거쳐 같은 요청을 냅니다.

- `planTaskMove(columns, taskId, {status, index})` → `none` | `reorder {status, taskIds}`(같은 열, 전체 순열) | `status {status, position}`(다른 열).
- `boardStep(columns, taskId, left|right|up|down)`: 위·아래는 열 안 한 칸, 왼쪽·오른쪽은 옆 열의 같은 줄(그 열이 짧으면 맨 끝), 끝이면 null.
- `dropTarget(columns, taskId, status, beforeId)`: 드래그를 놓은 열과 바로 뒤에 올 카드(없으면 맨 끝, 자기 자신 앞이면 제자리).
- `insertTaskAt(ids, taskId, position)`: 서버의 자리 지정과 화면의 순열 계산이 같은 규칙을 씁니다.

### 3. 화면

- 과제 화면 할 일 섹션에 "리스트 보기"·"보드 보기" 전환(`aria-pressed`). 고른 보기는 이 기기에 기억합니다(`localStorage` `peerchive:tasks-view`, 읽기·쓰기 모두 try/catch, 실패하면 리스트). 계정 설정·서버 저장은 하지 않습니다.
- 보드(`TaskBoard.vue`): 상태마다 열(제목에 개수), 카드에 제목·담당자·마감일(지났으면 "마감 지남")·빌드 로그 연결. 상태는 색이 아니라 열 제목 글자로 보여 줍니다.
- 옮기는 방법 세 가지(관리 권한이 있을 때만):
  1. **드래그**: 브라우저 기본 HTML5 끌어 놓기(새 의존성 없음). 카드를 다른 카드의 위쪽 절반에 놓으면 그 카드 앞, 아래쪽이나 열의 빈 곳이면 그 뒤·맨 끝. 놓을 열과 자리를 테두리·선으로 표시합니다.
  2. **키보드**: 카드(`tabindex=0`)에 포커스를 두고 Shift + ←/→(옆 열), Shift + ↑/↓(열 안). 카드 안의 버튼·링크에 포커스가 있을 때는 가로채지 않습니다. 안내 문구를 `aria-describedby`로 카드에 연결합니다.
  3. **버튼**: 카드의 "옮기기"(`aria-expanded`) → "← 왼쪽 열로"·"오른쪽 열로 →"·"↑ 위로"·"↓ 아래로"(끝이면 비활성, Esc로 닫고 "옮기기"로 포커스).
- 결과 안내 "‘제목’을(를) 진행 중 열 2번째로 옮겼습니다."는 할 일 섹션의 role=status(늘 DOM에 있고 비면 숨김)로 읽히고, 오류는 role=alert입니다. 옮긴 뒤 포커스는 그 카드로 돌아옵니다. 열 사이 이동 뒤에는 다른 할 일의 자리도 바뀌므로 목록을 다시 불러옵니다. 실패하면(409·422 등) 리스트와 같은 안내 후 최신 목록을 불러옵니다.
- **완료 열로 옮기면** `/complete`를 부르고, 응답에 프롬프트가 있으면 리스트와 같은 `TaskPrompt`("막힌 적 있었나요? 결정할 게 있었나요?")를 보드 아래에 띄워 질문에 포커스를 옮깁니다. 남기지 않고 닫아도 완료는 그대로이고 포커스는 카드로 돌아옵니다.
- 수정·삭제·빠른 추가 폼은 리스트 보기(빠른 추가는 두 보기 공통)에 그대로 둡니다. 보드는 옮기기만 합니다.
- 좁은 화면: 열은 `flex: 1 0 15rem`, 보드만 `overflow-x: auto`(가로 스크롤 스냅)이고 페이지는 넘치지 않습니다. 스크롤 영역은 `role=region`·이름·`tabindex=0`으로 키보드 스크롤과 포커스 표시가 됩니다. 터치 기기에서 HTML5 드래그가 안 되는 브라우저는 버튼·키보드 대안을 씁니다.

## 결과

- 보드와 리스트는 같은 행·같은 순서 데이터를 보여 주고, 어느 보기에서 옮겨도 다른 보기에 그대로 나타납니다. 드래그·키보드·버튼은 같은 요청을 내므로 결과가 같습니다.
- 열 사이 이동이 한 요청이라 반쯤 옮겨진 상태가 남지 않습니다. 기존 클라이언트(자리 없음)는 바뀌지 않습니다.
- 테스트: domain 단위 `tasks.test.ts`(`insertTaskAt`·`locateTask`·`planTaskMove`·`boardStep`·`dropTarget`, 드래그로 놓은 자리와 버튼 한 칸 이동이 같은 요청인지), web 통합 `tasks.integration.test.ts`(열 사이 이동 + 자리·범위 밖은 맨 뒤·`/complete` 자리와 프롬프트·재전송은 자리 무시·완료 되돌리며 자리 지정·422 `status_required`·`invalid`·409·viewer 403·비멤버 404·같은 열은 순서 변경), e2e `e09-kanban-board.spec.ts`(보기 기억, 버튼·Shift + 방향키 이동 → 안내·포커스·API·리스트 보기 순서 일치, 완료 열 → 완료 프롬프트, 페이지 가로 스크롤 없음; 데스크톱에서 Playwright `dragTo` 드래그), `a11y-and-layout.spec.ts`에 보드 보기 화면 추가.
- 한계: 터치 드래그(포인터 이벤트로 직접 구현)는 하지 않았습니다. 여러 카드를 한 번에 옮기기, 열 접기, 사용자 정의 열(상태 추가)은 없습니다. 보기 기억은 기기마다입니다. 다른 멤버가 옮긴 결과는 다시 불러올 때 보입니다(실시간 갱신 없음).

## 대안

- **열 사이 이동을 상태 변경 + 순서 변경 두 요청으로**: 서버를 바꾸지 않지만 두 번째 요청이 실패하면 카드가 맨 뒤에 남고, 그 사이 다른 멤버의 변경과 엇갈리기 쉽습니다.
- **새 이동 API(`POST /tasks/:id/move {status, position}`)**: 의미는 분명하지만 완료 프롬프트·version·한도 판정을 `/complete`·`PATCH`와 두 갈래로 유지해야 합니다.
- **같은 열 안에서도 `position`을 받음**: 순서 변경 API와 규칙이 겹치고, 리스트 ▲▼와 다른 요청이 생겨 "같은 순서 데이터" 조건을 확인하기 어려워집니다.
- **드래그 라이브러리(SortableJS·vuedraggable 등)**: 터치 드래그를 얻지만 의존성이 늘고, 키보드·버튼 대안과 같은 자리 계산을 공유하려면 결국 감싸야 합니다.
- **보기 선택을 서버(사용자 설정)에 저장**: 기기 사이에 이어지지만 화면 취향 하나에 API·migration이 생깁니다.
- **방향키만(Shift 없이)으로 옮기기**: 카드 사이 이동·페이지 스크롤과 겹쳐 실수로 옮기기 쉽습니다. Alt + 방향키는 일부 브라우저의 뒤로 가기와 겹칩니다.
