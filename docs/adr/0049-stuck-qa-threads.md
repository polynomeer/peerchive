# 0049. 막힘 Q&A 스레드: 기본 꺼짐 P1 플래그 `stuckQa` + 공개된 🧱 막힘 카드(공개·로그 키)마다 로그 작성자가 켜는 질문 허용(`stuck_qa_cards`, 과목 연결 공개만) + 과목 학교 인증 계정만 질문·답변 + 스레드 단위 `질문자`·`익명N`(같은 스레드 같은 번호, 스레드마다 따로)과 로그 작성자 `작성자` 고정 + "도움됐어요"는 정렬에만(개수·개인 점수 없음) + 답변자가 답변마다 고르는 "후배 기여" + 신고·숨김(`stuck_qa_post`·`hide_stuck_qa_post`)·신고에 묶인 운영자 작성자 확인·큐레이터 1차 검토 + 공개 철회·엠바고·가린 로그면 요청마다 404

- 상태: 채택
- 날짜: 2026-11-02

## 맥락

E-04는 DELIVERY_PLAN §4.4 P1 보완 백로그의 네 번째 항목입니다: "공개된 🧱 로그 작성자가 질문 허용을 켠 경우만 질문, 스레드 단위 `질문자`·`익명N` 번호와 로그 작성자 `작성자` 고정, “도움됐어요”는 카드 정렬에만(개인 점수 없음), 익명 답변의 ‘후배 기여’ 포함 여부는 답변자 선택, 신고·숨김, 공개 철회 시 스레드도 비공개". 로드맵(§3)상 단계 4 후보라 구현은 하되 pilot 근거가 필요한 개방은 기본 꺼짐 플래그 뒤에 둡니다(§4.4 머리말). 관련 설계와 앞선 결정:

- PROOFU_EVOLUTION_PLAN §8.5(공개된 🧱 막힘 로그에 작성자가 허용하면 질문, 원리·접근 위주, 대리 완성·답 판매 금지, "도움됐어요"는 카드 유용성 정렬에만, 스레드 단위 익명 표시, 로그 작성자는 익명이어도 `작성자`, 운영자는 신고 처리를 위해 실제 작성자를 앎, 익명 답변의 후배 기여 포함은 선택), §8.6(과목 허브 작성은 학교 인증 계정만, 막힘 Q&A 답변 포함).
- 본문 §8.5는 "작성자가 선택"이라 쓰지만 DELIVERY_PLAN E-04 행은 "답변자 선택"입니다. 실행 계획을 따라 **답변자가 답변마다** 고릅니다(답변을 쓴 사람이 곧 그 답변의 작성자라 두 문장이 같은 뜻으로도 읽힘).
- ADR 0011·0012(공개 읽기는 저장된 release 스냅샷만, 요청마다 상태 확인, 철회 즉시 404), 0013(과목 허브·유용성 신호 — 항목별 개수만, 작성자 합계 없음), 0015(신고·운영 조치·이의제기), 0018(학교 메일 인증·`canWriteToCourseHub`), 0021·0022(C-04 스레드 익명 번호 `thread_aliases`, 커뮤니티 테이블은 공개·소셜 경로에서 읽지 않음), 0023(작성자 확인은 사유·기록을 남김), 0025(C-09 `course_qa_items` — 질문 하나 + 채택 답 하나의 복사본), 0047(E-02 허브 단계적 개방 — 사례 페이지는 허브가 "준비 중"이어도 열림), 0048(E-03 큐레이터 1차 검토).

## 결정

### 1. 별도 테이블(과목 허브 구역), `course_qa_items`는 그대로

- C-09 막힘 Q&A(`course_qa_items`)는 커뮤니티 질문 + 채택 답 하나를 두 사람 동의로 **복사한** 아카이브 행이고, 이번 스레드는 공개된 막힘 카드에 직접 달리는 여러 글의 대화입니다. 모양(한 행 ↔ 여러 글·번호·도움됐어요)과 수명(복사본 ↔ 카드 공개 상태에 매임)이 달라 늘리지 않고 새 테이블 다섯 개를 만듭니다. C-09 행·화면·검색은 바꾸지 않습니다.
- 커뮤니티 `thread_aliases`(C-04)의 모양을 따르지만 **커뮤니티 테이블·모듈을 쓰지 않습니다**: 사례 페이지·허브는 공개 경로라 C-05 경계(공개 읽기 경로는 커뮤니티 코드·테이블 0건)를 지켜야 합니다. 테이블은 schema.ts의 새 구역 "막힘 Q&A 스레드"(커뮤니티 구역 밖)에 있고, 규칙은 `@peerchive/domain` `stuck-qa.ts`(런타임 의존성 없음)에 따로 둡니다.
- `stuck_qa_cards`(공개 id + 스냅샷 로그 키 unique, `author_id`·`questions_allowed`), `stuck_qa_threads`(카드·`asker_id`·`last_post_at`), `stuck_qa_aliases`((스레드, 사람)·(스레드, 번호) unique), `stuck_qa_posts`(종류 question/answer — 스레드마다 질문 하나 부분 unique, `by_log_author`·`alias_no`, 본문 1~2000자, `count_as_contribution`(답변만), 상태 published/withdrawn/hidden), `stuck_qa_helpful`((글, 사람) unique).

### 2. 카드와 "지금 보임" 판정: 요청마다, 행은 지우지 않음

- 카드 = 지금 게시 중인 release 스냅샷의 🧱 막힘 로그(`loadServedRelease` + `extractStuckItems`). 이 판정이 공개·release 게시 상태, 지금 release, 엠바고, 운영 조치로 가린 항목(`hide_item`)을 모두 봅니다. 키는 공개마다 안정되므로 새 버전을 게시해도 같은 카드입니다.
- **공개가 철회·제한·대체되어 카드가 지금 release에 없거나, 엠바고 중이거나, 로그가 가려지면** 카드·스레드·글 읽기와 질문·답변·도움됐어요·질문 허용 바꾸기·신고가 모두 404입니다. worker 정리를 기다리지 않고 행도 지우지 않습니다(다시 게시하면 돌아옴). 엠바고 중인 과제는 release가 제공되지 않으므로 스레드도 열리지 않습니다.
- 스레드는 질문 글이 published일 때만 보입니다(질문을 지우거나 숨기면 스레드 전체가 404, 카드 목록에서도 빠짐).
- 허브가 E-02로 "준비 중"이어도 사례 페이지는 열려 있으므로 스레드도 사례 페이지(`/p/:slug`)에서 들어갑니다. 허브 목록·검색에는 싣지 않습니다(§결과 한계).

### 3. 질문 허용: 그 막힘 로그를 쓴 사람만, 과목 연결 공개만

- 로그 작성자 = 지금 release의 `refs.logs[키].authorId`(공개 응답에 없는 비공개 참조). 요청마다 이 값으로 정하므로 `stuck_qa_cards.author_id`는 켠 사람 기록일 뿐입니다.
- `PUT /stuck-qa/cards/:slug/:itemKey {questionsAllowed}`: 로그 작성자이고 active여야 합니다(아니면 403 `not_log_author`). 켤 때 공개에 과목 연결이 없으면 409 `course_not_linked`(질문·답변은 과목 학교 인증이 필요하므로). 기본 꺼짐. 바뀌었을 때만 감사 `stuck_qa.questions_toggle`(카드 id, `questionsAllowed` 참거짓).
- **끄면** 새 질문·새 답변 모두 409 `questions_closed`, 기존 스레드는 읽기만 됩니다("질문 허용"을 대화 전체의 열고 닫음으로 봄).

### 4. 쓰기 자격: 과목 허브 작성 규칙 그대로

- 질문(스레드 열기)·답변은 로그인 + `writeDecision`(= `hubWriteDecision`: active + 그 공개의 정본 과목 학교의 active 학교 메일 인증, C-01·ADR 0018, `PEERCHIVE_HUB_REQUIRE_AFFILIATION`). 인증이 없으면 403 `hub_write_not_allowed` + `requirement: 'school_affiliation'`·`schoolId`(화면이 인증 페이지로 안내). 로그 작성자도 같은 규칙입니다(졸업생 인증 이력 유지, §8.6).
- 로그 작성자는 자기 카드에 질문을 열 수 없습니다(422 `card: own_card`). 본문은 앞뒤 공백을 지운 1~2000자(422 `body: required|too_long`). 사용자별 시간당 스레드 10회·글 30회(429).
- 도움됐어요는 쓰기가 아니므로 로그인만(학교 인증 불필요, T-13 신호와 같음). 시간당 300회.

### 5. 스레드 단위 익명 번호

- 질문한 사람 0(`질문자`), 그 밖의 사람은 그 스레드에 처음 쓴 순서대로 1, 2, …(`익명N`). 같은 스레드에서 같은 사람은 같은 번호, 스레드가 다르면 번호를 공유하지 않습니다. 지운·숨긴 글의 번호도 다시 쓰지 않습니다.
- **로그 작성자는 번호 행이 없고 항상 `작성자`**(`by_log_author = true`, `alias_no` 없음 — check로 강제). 쓸 때 정한 표시를 글 행에 남겨 나중에 release가 바뀌어도 표시가 흔들리지 않습니다.
- 답변을 쓸 때 스레드 행을 `FOR UPDATE`로 잠가 번호 순서를 정합니다(unique가 마지막 방어선).
- 이름은 어디에도 나오지 않습니다(모두 익명, 실명·표시명 선택지 없음 — §8.5 "기초적인 질문을 부담 없이"). 공개 DTO에는 사람 id·번호 행 id·handle이 없고, `mine`(보는 사람 자신의 글)과 `helpedByMe`만 보는 사람에게 맞춰 실립니다.

### 6. "도움됐어요"는 정렬에만

- 게시 중인 남의 **답변**에만(자기 글 422 `post: own_post`, 질문 422 `post: not_answer`). `PUT·DELETE /stuck-qa/posts/:id/helpful` → `{helpedByMe}`.
- 쓰는 곳: 카드 안 스레드 순서(게시 중인 답변이 받은 합 → 최근 글 → id), 스레드 안 답변 순서(질문 먼저, 받은 수 → 먼저 쓴 순 → id). **개수는 어떤 응답(공개·본인·운영자·큐레이터)에도 싣지 않고** 작성자별로 합산하지 않습니다. T-13 유용성 신호(`usefulness_signals`, 개수를 보여 줌)와 일부러 분리했습니다.
- 허브의 막힘 카드 정렬(T-13 `rankStuckItems`)에는 넣지 않았습니다: 플래그가 꺼져 있을 때와 허브 순서가 달라지지 않게 하고, pilot에서 쓰임을 본 뒤 정합니다.

### 7. 포트폴리오 "후배 기여": 답변자가 답변마다

- 답변을 쓸 때 `countAsContribution`(기본 false)을 고르고 `PATCH /stuck-qa/posts/:id`로 바꿉니다(자기 답변만, 아니면 404). 질문은 대상이 아닙니다(check).
- 공개 프로필(실명 페르소나만)의 `juniorContribution.stuckQaAnswers` = 켠 게시 중인 답변 중 **지금 보이는 것**(질문 게시 중 + 공개 제공 가능 + 로그가 지금 release에 있고 가려지지 않음)의 개수. 스레드·과목·도움됐어요 수는 싣지 않습니다. 플래그가 꺼져 있으면 0. 표시명 프로필에는 0(ADR 0028).
- 공개 프로필 경로가 이 계산 때문에 선배 노트·운영 안내 모듈(그리고 그 너머의 커뮤니티 어댑터)을 import하지 않도록 `stuck-qa-portfolio.ts`로 나눴습니다(S-02 경계 lint).

### 8. 지우기·신고·숨김·작성자 확인·큐레이터

- `DELETE /stuck-qa/posts/:id`(204): 자기 글을 언제든(카드가 닫히거나 공개가 내려가도). 본문을 비우고(`withdrawn`, 후배 기여 끔) 번호·자리는 남깁니다. 남의 글 404.
- 신고 대상 `stuck_qa_post` `{stuckQaPostId}`: 지금 보이는 스레드의 게시 중인 글만(플래그 꺼짐 404). 신고 행은 글 id만 가리킵니다(`reports.stuck_qa_post_id`, 내용 복사 없음). 조치 `hide_stuck_qa_post`(published → hidden, 되돌리면 hidden → published — 그사이 지웠으면 그대로). 질문을 숨기면 스레드 전체가 안 보입니다. 당사자는 글쓴이(안내·이의제기, 안내 경로는 스레드 화면).
- 운영자 신고 상세: 글의 표시·본문·상태·질문 미리보기·사례 slug만(작성자 없음). **작성자 확인** `POST /operator/stuck-qa/posts/:id/author-lookup {reportId}`: 운영자만(403 `operator_only`), 그 글을 가리키는 신고가 있어야 합니다(상태 무관, 아니면 404). 감사 `stuck_qa.author_lookup`(글 id + metadata `reportId`만). 응답에만 내부 id·handle·계정 상태·로그 작성자로 쓴 글인지가 있습니다. 플래그와 무관하게 동작합니다(이미 받은 신고 처리). ADR 0023처럼 별도 사유 기록 표를 두지 않고 신고에 묶은 것은, 신고 없는 임의 확인을 막는 것이 핵심이고 사유는 신고·처리 메모가 남기기 때문입니다.
- 큐레이터 1차 검토(E-03): `CURATOR_REVIEW_TARGETS`에 `stuck_qa_post`를 더했습니다. 과목은 카드 공개의 지금 release 과목. 큐레이터는 지금 보이는 글의 표시·본문만 봅니다(작성자 없음).

### 9. 플래그와 탈퇴 정리

- `PEERCHIVE_FEATURE_STUCK_QA`(P1 영역 `stuckQa`, `PEERCHIVE_FEATURE_P2`를 따르지 않음, 기본 꺼짐). 꺼지면 모든 경로·새 신고 404, 사례 페이지의 "막힘 Q&A" 링크 숨김, 포트폴리오 개수 0. 이미 받은 신고의 운영자 처리·작성자 확인은 됩니다.
- 탈퇴 정리(worker): 그 사람의 글은 본문을 비워 `withdrawn`(번호·자리 유지), 도움됐어요 행 삭제, 그 사람이 켠 질문 허용은 끄고 `author_id`를 비웁니다. 번호 행·스레드의 `asker_id`는 가명 처리된 users를 가리킨 채 남습니다(스레드의 다른 번호가 바뀌지 않게).

## 결과

- 막힘 로그를 쓴 학생이 원하면 후배가 그 카드에 익명으로 묻고, 인증한 선배·작성자가 답합니다. 공개를 내리면 대화도 즉시 닫히고, 도움됐어요는 순서만 바꾸며 누구의 점수도 되지 않습니다.
- 화면: 사례 페이지 "막힘 Q&A"(플래그가 켜졌을 때 🧱 기록마다 링크), `/stuck-qa/cards/:slug/:itemKey`(작성자의 질문 받기 켜기·끄기, 질문하기, 스레드 목록), `/stuck-qa/threads/:id`(글·답하기·도움됐어요·후배 기여·지우기·신고), 운영자 신고 상세의 글 + 작성자 확인, 큐레이터 1차 검토, 공개 프로필 "후배 기여"의 답변 수. 모두 noindex(robots 기본 막음).
- migration `0046_stuck_qa_threads`(테이블 5개, enum 2개 새로 만듦, `report_target_type`·`moderation_action_kind`에 값 하나씩 `ADD VALUE` — 같은 migration의 check는 `::text`로 비교, 새로 만든 enum은 부분 index에서 리터럴 그대로(`::text` 캐스트는 index 조건에서 IMMUTABLE이 아니라 거부됨), 빈 DB 처음부터 migrate 확인).
- 테스트: web 통합 `stuck-qa.integration.test.ts`(플래그 꺼짐 404, 허용 게이트·인증·감사, 철회·엠바고 404, 번호 규칙·DTO에 id 없음, 도움됐어요 정렬만, 후배 기여 선택, 신고·숨김·안내·작성자 확인·큐레이터, 소스 경계), domain 규칙·플래그, worker 탈퇴 정리, E2E `e04-stuck-qa.spec.ts`(플래그 꺼진 기본 서버에서 404·링크 없음).
- 한계: 허브 목록·검색·알림에는 스레드가 나오지 않습니다(사례 페이지에서만 들어감). 새 글 알림이 없습니다. 글을 고칠 수 없습니다(지우고 다시 씀). 답변 채택이 없습니다. C-09처럼 커뮤니티 질문을 스레드로 옮기는 길은 없습니다. 도움됐어요 개수를 아무에게도 보여 주지 않으므로 작성자도 반응을 모릅니다. 로그 작성자가 탈퇴하거나 release가 바뀌어 작성자가 달라지면 이미 쓴 글의 `작성자` 표시는 그대로입니다.

## 대안

- **`course_qa_items`를 늘려 스레드로 씀**: 테이블은 줄지만 C-09 행은 두 사람 동의로 얼린 복사본이라 상태·철회·검색 규칙이 다르고, 글 여러 개·번호를 담으려면 사실상 새 모델입니다.
- **커뮤니티 `thread_aliases`·글 테이블 재사용**: 번호 규칙은 같지만 사례 페이지·허브가 커뮤니티 테이블을 읽게 되어 C-05·S-02 경계(공개·소셜 경로 커뮤니티 0건)를 깹니다.
- **도움됐어요를 `usefulness_signals`의 새 대상 종류로**: 기존 집계·정리 handler를 쓰지만 그 표는 개수를 보여 주는 것이 전제라 "정렬에만"을 지키려면 예외가 늘어납니다.
- **도움됐어요 개수를 글마다 보여 줌**: 답변 신뢰도 판단에 도움이 되지만 §8.5 "정렬에만"과 어긋나고, 익명 스레드에서 번호별 점수처럼 읽힙니다.
- **질문 허용을 꺼도 기존 스레드에 답변 허용**: 이미 열린 대화는 이어지지만 작성자가 대화를 멈출 방법이 공개 철회뿐이 됩니다.
- **실명·표시명 선택지**: 신뢰도가 오르지만 §8.5의 "부담 없는 기초 질문"과 맞지 않고, 표시명이 다른 글과 이어져 스레드 단위 익명의 목적을 흐립니다.
- **작성자 확인에 사유 기록 표(ADR 0023 방식)**: 확인마다 사유가 남지만 지금은 신고 없는 확인을 막는 것으로 충분하고 표 하나가 늘어납니다. 신고 외 확인이 필요해지면 그때 더합니다.
