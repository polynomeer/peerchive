# Peerchive 실행 계획과 검증 기준

Peerchive(피어카이브)는 2019년 대학교 학부 졸업작품 **ProofU**에서 이어지는 프로젝트의 새 이름입니다. 아래 일정·지표·기준은 확정 계획이나 이미 수행한 조사 결과가 아니라 검증할 제안입니다.

## 1. 전제

- 개발자 1명이 주 20~30시간, 사용자 조사·운영 협력자 1명이 주 3~5시간 참여하고, 첫 학생 코호트(한 학교, 과목 2~3개)에 접근할 수 있다고 가정합니다.
- 실제 투입이 주 10시간이면 달력 시간이 약 2.5~3배 필요합니다. 이 경우 [제품 기획 §16](../PROOFU_EVOLUTION_PLAN.md#16-mvp-범위)의 축소안을 적용합니다.
- 일정은 한국 학사 일정(3월·9월 개강, 6월·12월 종강, 상·하반기 공채)에 맞춥니다. 탐색 수요는 개강 첫 2주, 사례 공개는 종강 직후, 포트폴리오 공유는 공채 시즌에 몰릴 것으로 예상합니다.
- 기존 원본을 실행 가능하게 만드는 데 먼저 시간을 쓰지 않습니다. 수동 실험으로 가치를 확인하면서 새 앱의 가장 작은 수직 흐름을 만듭니다.
- 예산·시간이 부족해도 권한 검사·파일 격리·공개 철회·복구는 생략하지 않고 기능 범위를 줄입니다. 상용 출시 수준의 정책·운영·접근성·기관 검토는 pilot 이후 별도 범위입니다.

## 2. 개발 전 검증 실험

코드를 작성하기 전에 노션·디스코드·정적 페이지·스프레드시트로 진행합니다. 과제 파일을 강제로 받거나 비공개 자료를 연구 목적으로 공개하지 않습니다.

### 2.1 인터뷰

| 대상 | 인원 | 핵심 질문 |
|---|---|---|
| 재학생 | 8~12명 | 마지막 조별과제에서 누가 무엇을 했는지 어떻게 증명했나? 족보를 받아 본 적 있나, 무엇이 가장 유용했나? 진행 중 판단·실패·검증을 어디에 남겼나? 포트폴리오를 만들 때 무엇을 다시 했나? 어디까지 공개하고 싶고 누구의 동의가 필요한가? 팀 채널은 무엇을 쓰나? 에브리타임 등에서 스터디 모집·과제 질문을 하나, 그 대화가 기록으로 남지 않아 아쉬웠던 적이 있나? |
| 채용 검토 경험자 | 4~6명 | 학생 사례 3개를 90초씩 보고 역할·근거·면접 질문을 설명. 기업이 플랫폼을 쓸 것이라는 확약을 인터뷰에서 추론하지 않음 |
| 교수·조교·멘토 | 2~3명 | 실제 공개 조건과 걱정, 학기 후 공개(엠바고)의 수용성, 기여 리포트의 동료평가 활용 가능성 |

| E4 | 채용자 비교 | 같은 학생의 GitHub 링크 vs 케이스 카드 + 역량×근거를 검토자 5명에게 제시 | 4명 이상이 주요 역할과 근거를 정확히 설명하고 더 구체적인 면접 질문 작성 | 요약 순서·개인/팀 분리 개선 |
| E5 | 엠바고·공개 수용성 | 교수·조교와 학생에게 공개 수준·엠바고 규칙 설명 | 교원 다수가 “학기 후 공개라면 허용 가능”, 동의와 조건을 갖춘 사례 5개 이상 확보 | 공개 범위를 개념·요약 수준으로 제한, 공개 허용 동아리·개인 프로젝트로 pilot |
| E6 | 졸업생 공급 | 2026-2학기 종강 무렵 졸업생·고학년에게 선배 노트·막힘 카드 요청 | 과목당 선배 노트 10개, 막힘 20개 | 대상 과목 축소, 운영자가 인터뷰 후 대필(작성자 승인) |

E0 기록 실험은 절반은 자유 기록, 절반은 태그형 빌드 로그로 시작해 장애 요인을 찾습니다. 작은 표본이므로 통계적 확증보다 장애 요인 발견이 목적입니다. 측정 방법은 모집 전에 고정하고 결과에 맞춰 기준을 몰래 바꾸지 않습니다.

학생이 실제 제출 자료를 공개하기 어렵다는 결과가 나와도 프로젝트를 버릴 이유는 아닙니다. 제출 후 공개 가능한 프로젝트, 공개 목적의 동아리 결과, 개인 재구현 과제, 선배 노트로 공급 범위를 조정합니다.

### 4.1 P1 캠퍼스 커뮤니티 백로그

[제품 기획 §8.9](../PROOFU_EVOLUTION_PLAN.md#89-캠퍼스-커뮤니티-방과-페이지-p1)의 커뮤니티를 MVP의 아카이브 흐름이 검증된 뒤(G3) pilot 학교 한 곳에서 엽니다. 데이터 모델·권한·열람 범위는 [시스템 설계 §6.7·§8.1·§8.2](SYSTEM_DESIGN.md#67-캠퍼스-커뮤니티-p1)를 따릅니다. 범위는 제품 기획 §16의 P1 행(공식 페이지 1개, 사용자 방, 모집·스터디 방, 스레드 익명 번호, 신고·임시 숨김, 질문 → 막힘 로그 옮기기)이며 투표·많이 공감한 글·공식 학과 페이지 확대·익명 글 실명 경고는 P2입니다.

| ID | 작업 | 의존 | 완료 기준 |

## 5. 수용 시나리오

**A. GitHub 없이 개인 과제 기록**
이메일로 가입해 private 과제를 만들고 PDF와 한 줄 로그를 남깁니다. 재접속 시 자료와 저장 상태가 유지되고, 공개 전에는 익명·다른 사용자·검색 API에서 보이지 않습니다. GitHub 연결을 요구하는 빈 화면이 없어야 합니다.

**B. 디스코드에서 막힘 기록**
팀원이 디스코드에서 `/log 막힘 CORS 에러`를 입력하면 해당 프로젝트에 🧱 로그가 한 번만 생성됩니다. 같은 요청이 재전송돼도 중복되지 않습니다. 다른 팀원이 남의 메시지에 📌을 달면 작성자에게 승인 요청이 가고, 승인 전에는 로그가 생기지 않습니다.

**C. 팀원이 기여를 확인**
A가 로그·산출물을 근거로 역할을 선언하고 B가 확인합니다. A가 내용이나 근거를 수정하면 이전 확인은 현재 선언에 유효하다고 표시되지 않습니다. owner도 A의 선언을 편집할 수 없습니다. 동료평가 리포트에는 확인 상태가 구분되어 나타납니다.

**D. 엠바고와 공동 자료 공개**
학기 진행 중인 과목의 과제는 게시 요청이 서버에서 거부됩니다. 학기 종료 후 owner가 후보를 만들었으나 한 명이 동의하지 않았거나 파일이 검사 중이면 게시가 실패합니다. 동의 직후 게시 전 탈퇴·철회·내용 변경이 일어나도 서버 재검사가 막습니다. 작업 공간의 다른 로그는 공개 응답에 포함되지 않습니다.

**E. 철회와 파생 데이터**
공개된 공동 파일의 동의가 철회되면 새 공개 조회와 파일 접근을 즉시 차단하고, 포트폴리오·케이스·검색·과목 집계에서 제외합니다. 짧은 URL TTL 동안의 잔여 접근을 테스트하고, 이미 받은 사본은 회수할 수 없음을 안내합니다. worker가 실패해도 공개 읽기가 먼저 차단되어야 합니다.

**F. 후배의 과목 탐색과 플랜 포크**
비로그인 방문자가 과목 페이지에서 공개 사례·막힘·선배 노트를 봅니다. 워크로드 분포는 기여자가 5명 미만이면 표시되지 않습니다. 로그인한 후배가 계획을 포크하면 마일스톤·체크리스트·시간 배분·참고 자료만 복사되고, 산출물·로그 본문·막힘 해결 내용은 복사되지 않습니다.

**G. 사후 작성**
졸업생이 지난 과제를 사후 작성 모드로 만들면 모든 항목과 공개 화면에 `사후 작성`이 표시되고, 자기 기입 날짜와 기록 시각이 구분됩니다.

**H. 초보 학생의 기록과 접근성**
모바일에서 파일만 먼저 올리고 나중에 설명을 완성할 수 있습니다. 저장 실패 시 내용이 사라지지 않고 재시도가 표시됩니다. 키보드로 모든 작업을 할 수 있고, 상태는 색상·아이콘 외 텍스트로도 이해할 수 있습니다. 할 일 순서는 드래그 없이 바꿀 수 있습니다.

**I. 취업용 읽기**
익명 검토자가 로그인 없이 공개 프로필을 열고 90초 안에 대표 과제의 문제·개인 역할·근거를 찾습니다. 연락처는 학생이 허용한 내용만 보입니다. 비공개 학교 정보·이메일·팀 피드백·체크인이 페이지 HTML·JSON·Open Graph·인쇄물에 포함되지 않습니다.

### 5.1 커뮤니티 수용 시나리오 (P1)

**J. 공식 학교 페이지 열람 범위**
pilot 학교 메일로 인증한 학생은 공식 학교 페이지를 읽고 익명으로 씁니다. 비로그인 사용자, 다른 학교 인증 사용자, 인증이 취소된 사용자는 같은 URL에서 404를 받습니다. 검색엔진 크롤러 시뮬레이션과 외부 링크 미리보기에 본문이 나타나지 않고, 공개 검색·과목 페이지에도 커뮤니티 글이 섞이지 않습니다.

**K. 익명 작성자 보호**
익명 글에 같은 작성자가 댓글을 달면 `글쓴이`로, 다른 참여자는 처음 쓴 순서대로 `익명1`·`익명2`로 표시되고 그 번호가 스레드 안에서 유지됩니다. 같은 사람이 다른 스레드에 쓴 글과는 번호·키로 연결되지 않습니다. 방장·모더레이터의 API 응답과 화면에도 작성자 식별자가 없습니다. 익명 글은 작성자의 공개 프로필·포트폴리오·활동 집계에 나타나지 않습니다.

**L. 이름 표시 방식 변경**
방장이 실명 방을 익명으로 바꾸면 멤버 전원에게 알림이 가고 7일 뒤에 적용됩니다. 그 전에 쓴 실명 글은 실명으로, 이후 글은 익명으로 표시됩니다. 반대로 익명 방을 실명으로 바꿔도 이전 익명 글의 작성자는 드러나지 않습니다. 변경 이력은 방 설정에서 확인할 수 있습니다.

**M. 신고·임시 숨김·이용 제한**
사용자 방의 글에 서로 다른 인증 사용자 3명이 신고하면 글이 즉시 임시 숨김되고 검토 큐에 올라갑니다. 같은 사람이 여러 번 신고해도 누적되지 않습니다. 방장은 익명 작성자를 알 수 없으므로 제재를 요청하고, 운영자가 사유를 남긴 뒤 작성자를 확인해 경고나 쓰기 제한을 내립니다. 이 확인은 감사 기록에 남고, 쓰기 제한을 받은 사용자도 자기 과제 공간·포트폴리오는 그대로 씁니다.

**N. 스터디 모집에서 기록까지**
공식 페이지 모집 게시판에 스터디 모집 글을 올리면 지원자 정보는 모집자에게만 보이고 순위가 없습니다. 모집을 마감하면 표시명 기본의 스터디 방이 생기고 지원자가 초대됩니다. 스터디 방에서 주차별 빌드 로그를 남기고, 끝날 때 멤버 동의를 받아 공개 사례로 발행합니다. 익명 스터디 방의 기록은 포트폴리오에 연결할 수 없습니다.

**O. 질문을 막힘 로그로 옮기기**
질문 게시판의 과제 질문에 답변이 채택되면 질문자가 “막힘 로그로 옮기기”를 요청합니다. 질문자와 채택 답변자가 모두 동의하고 이름 표시 방식을 다시 고른 뒤에만 복사본이 막힘 로그로 만들어지고, 원 글은 커뮤니티의 열람 범위를 유지합니다. 한 명이라도 동의하지 않으면 아무것도 복사되지 않습니다.

**P. 소규모 익명 방과 사칭 방지**
멤버 9명인 익명 방에서는 글 시각이 ‘오늘·이번 주’로만 보이고, 방을 만들 때 신원 추정 위험 안내가 나옵니다. 사용자 방 이름에 `공식`·`학생회`를 넣으면 생성이 거부되고, `공식` 배지는 운영자가 연 공간에만 붙습니다.

### 5.2 공개 프로필·팔로우 수용 시나리오 (P1)

**Q. 익명 글이 프로필로 새지 않음**
팔로워가 많은 표시명 `@devjimin`의 주인이 공식 학교 페이지에 익명 글을, (P2) 토픽에 소속 표시 익명 글을 씁니다. 그 글은 `@devjimin`과 실명 프로필의 활동 목록·팔로우 피드·추천·검색·OG·PDF 어디에도 나타나지 않고, 응답 JSON에 글 ID나 작성 시각도 없습니다. 방장이 방을 실명으로 바꾼 뒤에도 이전 익명 글은 프로필에 나타나지 않습니다. 같은 글을 아카이브로 옮기며 표시명을 고르면 복사본만 `@devjimin`에 나타나고, 원 글과의 연결은 보이지 않습니다.

**R. 표시명과 실명의 분리**
연결이 꺼진 상태에서 표시명 프로필과 실명 프로필의 HTML·JSON·OG·PDF·팔로우 목록·추천 어디에도 상대 프로필 정보가 없습니다. 사용자가 연결을 켜면 양쪽에 서로의 링크가 보이고, 다시 끄면 다음 요청부터 사라지며 토글 이력은 감사 기록에만 남습니다. 표시명으로 다른 사람을 팔로우해도 상대의 팔로워 목록에는 표시명만 보입니다.

**S. 공개 범위가 공개 절차를 우회하지 않음**
계정의 모든 항목을 `전체 공개`로 바꿔도 팀 동의가 끝나지 않은 공개 후보·비공개 과제 공간·엠바고 중인 과제 제목은 프로필에 나타나지 않습니다. 과제 수행 목록에는 사용자가 고른 과제의 과목·학기·제목만 보이고, 다른 멤버 이름과 로그는 없습니다. 공개 사례를 철회하면 다음 요청부터 프로필 목록과 팔로워 피드에서 빠집니다.

**T. 비공개 계정과 팔로우**
비공개 계정에 팔로우 요청을 보내면 승인 전에는 기본 정보만 보이고, 승인 뒤 `승인한 팔로워` 범위의 과제 목록·글이 보입니다. 팔로워를 삭제해도 상대에게 알림이 가지 않습니다. 비공개에서 공개로 바꿀 때 대기 중인 요청은 자동 승인되지 않고 본인에게 확인을 묻습니다. 팔로워 수 표시를 끄면 공개 응답에 숫자가 없습니다.

**U. 차단**
A가 표시명 프로필에서 B를 차단하면 B는 그 프로필을 404로 받고 서로의 팔로우가 삭제되며 알림은 가지 않습니다. A의 실명 프로필은 A가 “모든 프로필에서 차단”을 고를 때만 숨겨지고, 이때 연결 추정 경고가 나옵니다. 공식 학교 페이지의 익명 글은 차단과 관계없이 그대로 보입니다.

**V. 소셜 링크 확인**
GitHub 프로필에 Peerchive 프로필 링크를 넣고 확인을 요청하면 `확인됨`이 붙습니다. 링크를 지우면 다음 재확인에서 `lost`로 바뀝니다. 사설 IP·내부 주소로 redirect되는 URL은 수집 worker가 접속하지 않고 거부합니다.

### 5.3 졸업생·토픽·기관 수용 시나리오 (P2)

**W. 동문회·OB 방**
동아리 OB 방에서 멤버는 `12기 김지민`이라는 방별 프로필과 `OB` 배지로 보이고, 이 이름은 방 밖 공개 프로필·검색·피드에 나타나지 않습니다. 운영진이 홈커밍 일정을 올리면 멤버가 참석/불참/미정으로 응답하고 응답자 목록은 멤버에게만 보입니다. 운영진 공지에는 읽음 수만 표시되고 누가 읽었는지는 보이지 않습니다.

**X. 멤버 명부 동의**
명부에는 공개에 동의한 멤버만, 동의한 항목만 나타납니다. 멤버가 동의를 철회하거나 방을 나가면 즉시 사라집니다. 명부를 CSV·PDF로 내보내거나 한 번에 전부 조회하는 경로가 없고, 짧은 시간에 많은 페이지를 넘기면 rate limit에 걸립니다.

**Y. 소속 표시 임계값**
인증 회원이 30명인 부트캠프의 수료생이 `취준` 토픽에 글을 쓰면 `부트캠프 수료생`으로 표시되고, 넓혀졌다는 사실은 작성자에게만 안내됩니다. 인증 졸업생이 60명 이상인 대학의 졸업생은 `○○대 · 졸업생`으로 표시됩니다. 작성자가 `표시 안 함`을 고르면 소속이 붙지 않습니다. 이후 회원 수가 늘거나 소속이 바뀌어도 이미 쓴 글의 표시는 그대로이며, 학과·기수는 어떤 경우에도 표시되지 않습니다.

**Z. 기관 인증 수단과 기관 운영진**
만료되었거나 사용 한도를 넘은 초대 코드는 거부됩니다. 기관이 참여하지 않는 기수는 같은 기수 멤버 2명의 승인으로 인증되며, 기수 승인으로만 인증된 멤버의 승인은 세지 않습니다. 수료증 확인은 결정 직후 파일이 삭제되고 삭제 기록이 남습니다. 기관 운영진은 기관 페이지의 익명·소속 표시 익명 글 작성자를 알 수 없고, 소속 사용자의 프로필·과제 공간을 기관 단위로 조회할 수 없습니다.

## 6. 측정 계획

**북극성 지표:** 학기 말에 공개된 과제·선배 노트 중 **후배가 계획을 포크하거나 ‘도움됐어요’를 남긴 수** (pilot 학기 목표 가설 15건).

작성자 측 핵심 지표는 **기간 중 의미 있는 로그를 남기고 기여 근거를 포트폴리오에 연결한 학생 수**입니다. 활동량을 늘리는 대신 기록의 유용성을 확인합니다.

| 지표 | 정의 | pilot 판단 초안 |
|---|---|---|
| 활성화 | 가입 7일 이내 과제 생성 + 로그 3개 + 근거 하나 | 초대 학생의 50~60% |
| 기록 유지 | 활성 학생이 4주 중 3주 이상 기록한 비율 | 40%, 시험 기간 영향 별도 확인 |
| 학기 중 가치 | 기여 리포트를 동료평가·발표에 실제로 쓴 팀 | 30% |
| 사례 전환 | 공개 허용이 확인된 종료 과제 중 공개(요약 이상) 비율 | 30~40% |
| 도움 받은 탐색 | 과목 페이지 방문 후 막힘·선배 노트에 ‘도움됐어요’ 또는 포크한 재학생 비율 | 30% |
| 공급 전환 | 도움 받은 학생 중 학기 말 노트·막힘을 직접 남긴 비율 | 20% |
| 포트폴리오 활용 | 공개 사례를 대표 기여로 연결하고 실제로 공유한 학생 | 10명 이상(파일럿), 20명(단계 3) |
| 이해도 | 모의 검토자가 역할·결과·근거를 정확히 설명한 비율 | 80% |
| 작성 부담 | 로그 1회 실제 작성 시간과 중단 이유 | 중앙값 5분 이하 |
| 운영 안전 | 비공개 누출·잘못된 공개·삭제 실패 | 중대한 미해결 건이 있으면 확대 중단 |
| 비용 | 활성 학생당 저장량·전송량·worker·AI 비용·운영 인력 시간 | 다음 범위 산정에 반영 |

최소 분석 이벤트: `project_created`, `log_saved`(tag·source), `evidence_attached`, `milestone_snapshot_set`, `checkin_submitted`, `claim_endorsed`, `report_exported`, `candidate_prepared`, `consent_completed`, `publication_published`, `publication_withdrawn`, `plan_forked`, `usefulness_marked`, `senior_note_published`, `portfolio_shared`. 과제 본문·파일 내용·검색 원문·연락처는 이벤트에 담지 않습니다. pilot 동의·보존 기간·분석 접근권한은 별도로 안내합니다.

공개 조회수·좋아요·커밋 수를 개인 역량 점수로 쓰지 않습니다. 작은 표본의 비율을 전체 대학생 시장에 일반화하지 않으며, 취업률 개선은 초기 pilot으로 입증할 수 없는 별도 장기 연구 질문입니다.

### 6.1 커뮤니티 지표 (P1)

커뮤니티의 성공 기준은 체류 시간이 아니라 **커뮤니티에서 오간 질문·스터디가 아카이브 기록으로 이어지는가**입니다. 제품 기획 §19의 “커뮤니티 → 기록 전환이 거의 없으면 모집·스터디 방만 남김”을 아래 지표로 판단합니다.

| 지표 | 정의 | pilot 한 학기 판단 초안 |
|---|---|---|
| **커뮤니티 → 막힘 로그 전환** (핵심) | 질문 게시판의 기술·과제 질문 중 막힘 로그·막힘 Q&A로 옮겨진 비율과 건수 | 질문의 10% 이상 또는 20건 이상. 5% 미만이면 “거의 없음” |
| **커뮤니티 → 스터디 기록 전환** (핵심) | 마감된 스터디 모집 중 스터디 방에서 빌드 로그를 3주 이상 남긴 비율 | 30% 이상. 10% 미만이면 스터디 기록 대신 모집만 유지 |
| 스터디 공개 전환 | 기록을 남긴 스터디 중 학기 말 공개 사례·선배 노트로 이어진 비율 | 20% |
| 모집 성사 | 모집 글 중 마감되어 스터디 방·과제 공간이 만들어진 비율 | 40% |
| 아카이브 유입 | 커뮤니티 사용자 중 과목 허브·자기 과제 공간을 처음 연 비율 | 30% |
| 재방문 | 학교 인증 사용자 중 학기 중 주 1회 이상 방문한 비율(시험 기간 별도) | 30% |
| 신고율·처리 시간 | 글 1,000건당 신고 수, 자동 숨김 후 검토 완료까지 시간 중앙값 | 검토 중앙값 24시간 이내 |
| 운영 부담 | 운영자·모더레이터의 주간 신고 검토 시간 | 제품 기획 §19 질문 10의 가용 시간 이내 |

### 6.2 공개 프로필·팔로우와 졸업생·기관 지표 (P1·P2)

공개 프로필·팔로우의 성공 기준은 팔로워 수가 아니라 **팔로우가 기록을 읽고 남기는 행동으로 이어지는가**이고, 졸업생·기관 확장의 기준은 **선배 노트·공개 사례 공급이 늘어나는가**입니다. 제품 기획 §19의 정체성 포지션·표시명·팔로워 수·소속 표시·졸업생 공간 결정의 변경 조건을 아래 지표로 판단합니다.

| 지표 | 정의 | 판단 초안 |
|---|---|---|
| **정체성 누출** (필수) | 프로필·피드·팔로우·추천·검색·OG·PDF에서 0~1단계 글이 발견되거나 연결 비공개 페르소나가 함께 노출된 건수 | 0건. 1건이라도 있으면 피드·프로필 기능 중단 후 원인 해결 |
| **팔로우 → 기록 활용** (핵심, P1) | 팔로우 피드에서 공개 사례·선배 노트를 열고 ‘도움됐어요’·포크를 남긴 사용자 비율 | 피드 사용자의 15%. 5% 미만이면 피드를 프로필 구독 알림 수준으로 축소 |
| 피드 구성 | 피드 노출 항목 중 기록(사례·선배 노트·스터디 기록)의 비율 | 50% 이상. 사진 위주 프로필 글이 과반이면 미디어 비중 조정 |
| 익명 외 활동 비중 (P1) | 커뮤니티 글 중 표시명·실명(2~3단계)으로 쓴 비율과 익명 라운지 밖 공간의 활동 | 익명 라운지 외 활동이 거의 없으면(10% 미만) 제품 기획 §19에 따라 익명 공간 비중 재검토 |
| 표시명 사용 | 공개 프로필 보유자 중 표시명 페르소나를 만든 비율, 연결을 켠 비율 | 관찰 지표(목표 없음) |
| 표시명 사칭·평판 세탁 | 표시명 프로필 대상 사칭·기만 신고 건수와 확정 건수 | 확정 건이 반복되면 §19에 따라 표시명 프로필에 기관 인증 배지 필수화 |
| 팔로워 수 표시 선택 | 팔로워 수 표시를 켠 사용자 비율, 크리에이터 인터뷰 결과 | §19 변경 조건(크리에이터 유입에 중요) 판단 근거 |
| 소셜 링크 유입 | 확인된 소셜 링크를 단 사용자 수와 외부 링크 경유 방문 | 관찰 지표 |
| 차단·뮤트·팔로워 삭제 | 활성 팔로우 관계 1,000건당 발생 수 | 급증 시 추천·노출 방식 점검 |
| **졸업생 → 선배 노트 공급** (핵심, P2) | 동문회·OB 방·토픽 참여 졸업생 중 학기 내 선배 노트·수료 회고를 남긴 비율과 건수 | 10% 또는 30건 이상이면 §19에 따라 졸업생 공간을 P1로 앞당기는 근거 |
| 토픽 → 선배 노트 전환 (P2) | 직무 토픽의 답변 중 선배 노트로 옮겨진 비율 | 5% |
| 동문 방 활성 (P2) | 월 1회 이상 일정·공지가 있는 동문 방 비율, 일정당 참석 응답률 | 40%, 30% |
| 명부 동의율 (P2) | 동문 방 멤버 중 명부에 동의한 비율 | 관찰 지표(낮아도 강제하지 않음) |
| 소속 표시 상향 비율 (P2) | 토픽 글 중 임계값 때문에 넓혀진 비율 | 과반이면 pilot 규모에 맞춰 임계값 재검토(§19) |
| 기관 인증 (P2) | 인증 수단별 건수·처리 시간, 사칭으로 판정된 인증 수 | 수료증 확인 처리 중앙값 3일 이내, 사칭 확정 시 승인 경로 점검 |
| 기관 확장 공급 (P2) | 기관 기수 방에서 시작된 공개 사례·포트폴리오 수 | 기관 단위 판매 가설(제품 기획 §17)의 근거 |

분석 이벤트: `persona_created`(kind), `identity_link_toggled`, `visibility_changed`(item_kind·audience), `project_listed`, `follow_requested`, `follow_approved`, `follower_removed`, `block_created`(scope), `mute_created`, `feed_item_opened`(source_type), `social_link_verified`, (P2) `alumni_room_created`, `event_created`, `rsvp_submitted`, `directory_consent_changed`, `topic_post_created`(label_scope_applied·broadened), `affiliation_verified`(method), `completion_retro_published`. 0~1단계 글 이벤트에는 사용자 키를 붙이지 않고, 차단·뮤트·팔로워 삭제 이벤트에는 상대방 키를 담지 않습니다. 팔로워 수·피드 노출 수를 개인 지표나 순위로 쓰지 않습니다.

## 8. 콜드 스타트와 성장

공급 단위를 사례보다 작게 쪼개 초기 콘텐츠를 빠르게 모읍니다.

| 공급 단위 | 작성 시간 가설 | 초기 목표(과목 하나 기준) |
|---|---|---|
| 선배 노트 | 10분 | 10개 |
| 막힘 카드(사후) | 5분/개 | 20개 |
| 사후 작성 사례 | 30분 | 3~5개 |
| 진행 중 사례 | 학기 내내 | pilot 팀 5~10개 |

- **순서:** 2026-12 졸업생 캠페인 → 2027-03 개강 때 과목 페이지 공개(재학생 유입) → 학기 중 기록 → 2027-06 종강 후 공개 → 하반기 공채 시즌 포트폴리오 공유 → 공유 링크로 다음 유입.

- 초기 공개 콘텐츠에는 실패·제약이 있는 사례도 포함해, 전시가 잘 되는 학생만 혜택을 보는 구조를 피합니다.
- **ProofU 첫 사례:** 오너가 사후 작성 모드로 ProofU 자체를 첫 공개 사례로 올립니다(2019년 커밋은 재구성 기록임을 표시).

### 9.1 커뮤니티 운영 위험 (P1)

커뮤니티는 아카이브보다 운영 부담이 훨씬 큰 기능입니다. 1인 개발·소수 운영 구조에서 감당할 수 있는 범위만 엽니다.

| 위험 | 초기 신호 | 대응 |
|---|---|---|
| 신고 검토가 운영 여력 초과 | 검토 대기 증가, 처리 시간 중앙값 24시간 초과, 주간 검토 시간이 가용 시간 초과 | 자동 임시 숨김 유지, 모더레이터 1차 검토, 사용자 방 정원·신규 개설 제한, 익명 방 선택을 인증 방장·정원 제한으로 좁힘(제품 기획 §19), 그래도 넘치면 공식 페이지 쓰기 일시 중지 |
| 익명 괴롭힘·신상 공개 | 특정 개인 실명·연락처 언급, 같은 대상 반복 신고 | 실명 비방·신상 공개 금지 규칙, 익명 쪽지 없음, 단계별 이용 제한, 실명·연락처 문자열 경고(P2) 앞당김 검토 |
| 모더레이터 확보 실패 | pilot 학교에서 모더레이터 지원자 2명 미만 | 운영자가 직접 맡을 수 있는 공식 페이지 1개로 한정, 사용자 방은 방장 책임 + 운영자 신고 처리 |
| 운영자 작성자 확인의 남용·불신 | 신고와 연결되지 않은 조회, 사용자 문의 | 조회 권한을 신고 처리 역할로 제한, 사유·신고 ID 필수, 감사 기록 정기 점검, 글쓰기 화면 고지 |
| 소규모 익명 방의 신원 추정 | 작은 익명 방에서 “누군지 안다” 신고 | 10명 미만 방 시각 버킷, 생성 시 안내, 필요 시 소규모 방의 익명 선택 제한 |
| 학교·학과 사칭 | `공식`·학생회 유사 이름, 학과 페이지 외부인 | 예약어 거부, `공식` 배지 분리, 학과 모더레이터의 외부인 쓰기 제한, 반복 시 학과 학생회 확인 검토(학번 수집 없음) |
| 답안 공유·학업 부정 | 같은 학기 과목 연결 방에서 코드·답안 공유 신고 | 과목 연결 방 엠바고 정책, 신고 사유 분류, 계획·개념 질문은 허용 |
| 게시 중단·법적 요청 | 권리 침해 주장, 수사 협조 요청 | 법률 검토를 거친 별도 절차를 GC 전에 확정, 처리 기록 보존 |
| 아카이브의 입구가 아니라 대체물이 됨 | 글 수는 늘지만 §6.1 전환 지표가 낮음 | 질문 게시판에서 “막힘 로그로 옮기기” 노출 강화, 전환이 계속 낮으면 모집·스터디 방만 남기고 자유 게시판 축소 |
| 기존 커뮤니티와 경쟁해 빈 공간 | 에브리타임에 이미 있는 대화만 반복, 방문 감소 | 스터디 모집·과제 질문처럼 기록으로 이어지는 용도에 집중, 빈 공식 페이지를 미리 만들지 않음. 개설 요청이 너무 적으면 pilot 학교 한 곳만 운영자가 먼저 개설(제품 기획 §19) |

### 9.2 공개 프로필·팔로우와 졸업생·기관 확장 위험 (P1·P2)

| 위험 | 초기 신호 | 대응 |
|---|---|---|
| 익명 글과 프로필의 결합 | 회귀 테스트·신고로 0~1단계 글이 프로필·피드에서 발견, 작성 시각·문체로 “이 표시명이 쓴 익명 글”이라는 추정 신고 | 정체성 누출 0건 원칙(§6.2), 발견 즉시 피드·프로필 기능 중단, S-02 경계(모듈 lint·DB 권한·속성 테스트) 강화, 소규모 공간 시각 버킷 확대 |
| 차단·공개 범위로 페르소나 연결 추정 | “두 프로필이 같은 사람인 것 같다” 문의·신고 | 차단 기본 범위를 해당 페르소나로 유지, `all_personas`·`same_institution` 선택 시 안내, 연결 관련 응답 차이를 회귀 테스트로 점검 |
| 표시명 사칭·평판 세탁 | 다른 사람·기관을 흉내 낸 표시명, 신고 후 새 표시명으로 재등장 | 사칭 신고 사유, 표시명 변경 빈도 제한, 제재는 계정 단위로 적용, 반복되면 표시명 프로필 기관 인증 배지 필수화(제품 기획 §19) |
| 팔로워 경쟁·과시 피드화 | 팔로워 수 공개 비율 급증, 사진 위주 프로필 글이 피드 과반 | 인기 순위 없음, 팔로워 수 정렬·추천 가중치 금지, 피드에서 기록 우선, 프로필 글 미디어 수 제한 |
| 공개 범위 설정 오해 | 사용자가 “전체 공개했는데 사례가 안 보인다”·“비공개인데 링크로 보인다” 문의 | 설정 화면에 공개 절차·공개 URL과의 관계를 미리보기로 표시, 비공개 계정 전환 시 이미 공개된 release는 별도 철회가 필요함을 안내 |
| 소셜 링크 확인의 악용 | 내부 주소 접속 시도, 확인됨을 인물 검증으로 오해 | 링크 수집 worker의 SSRF 방어, 재확인 주기·횟수 제한, `확인됨` 설명 문구 |
| 소규모 소속 표시로 익명 붕괴 | 작은 기관·기수에서 “누군지 안다” 신고 | 임계값 50 유지 또는 상향, 학과·기수 미표시, 신고 시 해당 소속 표시를 넓은 범주로 일괄 전환 |
| 멤버 명부의 수집·스팸 | 명부 조회 급증, 명부 연락처로 홍보·스팸 신고 | 동의 항목만, 내보내기 없음, rate limit, 신고 시 방장 내보내기·운영자 제재 |
| 가짜 기수·기관 인증 사칭 | 승인 연쇄로 인증된 계정 증가, 같은 승인자의 대량 승인 | 승인자는 비승인 수단 인증자만, 승인 수 2명, 승인자 기록, 사칭 확정 시 승인 자격 제한 |
| 기관 운영진의 감시 도구화 | 기관이 소속 사용자 활동 조회·익명 작성자 확인을 요구 | 기관 단위 사용자 조회 API 없음, 작성자 확인은 운영자 신고 처리 역할만, 기관 계약에 명시(G4) |
| 기관 평판 분쟁 | 수료 회고가 사실상 평가·비방으로 쓰임, 기관의 삭제 요구 | 별점·연봉 없음, 구조화된 회고 서식, 실명 비방 금지 규칙, 게시 중단 요청 절차(GC) 적용 |
| 졸업생 공간이 친목에 머묾 | 동문 방 활동은 있으나 §6.2 공급 지표가 낮음 | 동문 방에서 선배 노트 요청·수료 회고 서식 노출, 계속 낮으면 P2 범위를 일정·명부로 축소 |
| 동문 방 운영 부담·저장 비용 | 앨범·영상 저장량 증가, 신고 증가 | 방별 저장 한도, 영상은 외부 링크 우선, 비용 산정(§10)에 반영 |

## 10. 운영 비용 산정 방식

호스팅 업체·지역·용량·가격을 선택하지 않았으므로 월 비용을 확정 숫자로 제시하지 않습니다. 공급자 선택 시 당시 공식 가격으로 다시 산정합니다.

- 고정: 웹·worker·봇 실행, PostgreSQL, 모니터링, 인증·메일
- 변동: 저장량, 다운로드 전송량, 검사·썸네일·PDF 작업, AI 토큰, 외부 API 호출
- 사람: 공개 상담, 신고·분쟁, 인터뷰, 파일·DB 복구, 배포 관리, 커뮤니티 신고 검토·모더레이터 지원(P1, 주간 시간을 따로 기록)

초기 50명 × 500MB는 최대 약 25GB 원본 가정이며 파생 파일·버전·백업·전송량은 추가입니다. 동영상은 외부 링크 우선, 학생당 한도와 전체 예산 경보를 둡니다. 예산이 부족하면 AI·GitHub 자동 연결·정교한 PDF·의미 검색부터 줄이고, 비공개 권한·파일 격리·공개 철회·복구는 유지합니다.

## 11. Git·아카이브·문서 운영

- 원본 `frontend/`, `backend/`, `docs/history-map.json`, `docs/archive-cleanup.json`은 보존합니다. 원본 수정이 필요한 별도 요청이 있으면 변경과 검증 기준을 명시적으로 기록합니다.
- 신규 구현은 기능별 브랜치(예: `peerchive/<기능>`)에서 진행하고, 신규 `apps/`·`packages/`에 자체 테스트·migration·운영 문서를 둡니다. master 이력을 다시 쓰거나 백업 브랜치를 변경하지 않습니다.
- 각 구현 단위는 문제·사용자 행동·완료 기준·권한 영향·테스트를 PR에 기록합니다. README에는 기능을 ‘제안 / 개발 중 / 사용 가능’으로 구분해 표시합니다.
- 실험 결과에 따라 이 문서를 갱신하고, 주요 결정은 ADR로 남깁니다.
- 2019년 커밋 18개는 2020년 업로드 코드를 재구성한 기록이며 실제 당시 개발 로그가 아닙니다. 신규 서비스는 그 기록을 실시간 개발 증빙이나 기여 인증으로 표시하지 않습니다. [원본 이력 백업](https://github.com/polynomeer/peerchive/tree/backup/pre-reconstruction-20261013)은 유지합니다.

## 12. 바로 할 일 (2026-10-19부터 2주)

1. 인터뷰 질문지(§2.1)를 확정하고 재학생·채용 검토자·교원 후보를 모집합니다.
2. 노션 빌드 로그 템플릿(태그·마일스톤·체크인 폼)과 디스코드 채널 구조를 만들고 E0 파일럿 팀 2~3개를 모집합니다.
3. 첫 과목 2~3개를 정하고 졸업생 5명에게 선배 노트·막힘·사후 작성(E2)을 요청합니다.
4. 과목 페이지·공개 사례·공개 프로필의 정적 목업을 만들어 E1·E4에 씁니다.
5. ProofU 원본 화면 캡처와 이력 자료로 첫 사례의 2019 마일스톤 스냅샷을 준비합니다.
6. Nuxt + PostgreSQL + Drizzle + pg-boss 스켈레톤과 CI(원본 보존 검증 포함)를 기술 실험으로 구성하고 ADR을 남깁니다.

이 순서는 ‘좋아 보이는 사이트’를 먼저 만드는 것보다 어떤 기록이 학생에게 실제로 유용한지 확인하기 위한 것입니다. 학생 모집·연락, 외부 서비스 가입·배포는 이 문서 작업에 포함되지 않습니다.
