# Peerchive 실행 계획과 검증 기준

**한국어** | [English](DELIVERY_PLAN.en.md)

작성일: 2026-10-18 · 상태: 통합 제안

[제품 기획](../PROOFU_EVOLUTION_PLAN.md) · [시스템 설계](SYSTEM_DESIGN.md)

Peerchive(피어카이브)는 2019년 대학교 학부 졸업작품 **ProofU**에서 이어지는 프로젝트의 새 이름입니다. 아래 일정·지표·기준은 확정 계획이나 이미 수행한 조사 결과가 아니라 검증할 제안입니다.

## 1. 전제

- 개발자 1명이 주 20~30시간, 사용자 조사·운영 협력자 1명이 주 3~5시간 참여하고, 첫 학생 코호트(한 학교, 과목 2~3개)에 접근할 수 있다고 가정합니다.
- 실제 투입이 주 10시간이면 달력 시간이 약 2.5~3배 필요합니다. 이 경우 [제품 기획 §16](../PROOFU_EVOLUTION_PLAN.md#16-mvp-범위)의 축소안을 적용합니다.
- 일정은 한국 학사 일정(3월·9월 개강, 6월·12월 종강, 상·하반기 공채)에 맞춥니다. 탐색 수요는 개강 첫 2주, 사례 공개는 종강 직후, 포트폴리오 공유는 공채 시즌에 몰릴 것으로 예상합니다.
- 기존 원본을 실행 가능하게 만드는 데 먼저 시간을 쓰지 않습니다. 수동 실험으로 가치를 확인하면서 새 앱의 가장 작은 수직 흐름을 만듭니다.
- 예산·시간이 부족해도 권한 검사·파일 격리·공개 철회·복구는 생략하지 않고 기능 범위를 줄입니다. 상용 출시 수준의 정책·운영·접근성·기관 검토는 pilot 이후 별도 범위입니다.

## 2. 개발 전 검증 실험

코드를 작성하기 전에 노션·디스코드·정적 페이지·스프레드시트로 진행합니다. 과제 파일을 강제로 받거나 비공개 자료를 연구 목적으로 공개하지 않습니다.

### 2.1 인터뷰

| 대상 | 인원 | 핵심 질문 |
|---|---|---|
| 재학생 | 8~12명 | 마지막 조별과제에서 누가 무엇을 했는지 어떻게 증명했나? 족보를 받아 본 적 있나, 무엇이 가장 유용했나? 진행 중 판단·실패·검증을 어디에 남겼나? 포트폴리오를 만들 때 무엇을 다시 했나? 어디까지 공개하고 싶고 누구의 동의가 필요한가? 팀 채널은 무엇을 쓰나? |
| 채용 검토 경험자 | 4~6명 | 학생 사례 3개를 90초씩 보고 역할·근거·면접 질문을 설명. 기업이 플랫폼을 쓸 것이라는 확약을 인터뷰에서 추론하지 않음 |
| 교수·조교·멘토 | 2~3명 | 실제 공개 조건과 걱정, 학기 후 공개(엠바고)의 수용성, 기여 리포트의 동료평가 활용 가능성 |

### 2.2 실험

| ID | 실험 | 방법 | 진행 조건 초안 | 미충족 시 |
|---|---|---|---|---|
| E0 | 수동 운영 | 2~3팀이 4주간 노션 빌드 로그 템플릿 + 디스코드 채널로 과제 진행, 주간 체크인은 폼, 기여 요약은 운영자가 수동 작성 | 팀 절반 이상이 4주 중 3주 이상 기록, 기록 작성 중앙값 5분 이내 | 태그 축소, 파일·체크인 중심 흐름, 봇 우선순위 상향 |

| E3 | 사례 정리 | 동의한 완성 과제 3~5개를 ‘문제 / 본인 기여 / 핵심 결정 / 확인 방법 / 결과 / 한계 / 출처’ 서식으로 정리, 단순 결과물 링크와 비교 | 포트폴리오 작성 시간 단축, 읽는 사람의 이해도 향상 | 서식 순서·항목 조정 |
| E4 | 채용자 비교 | 같은 학생의 GitHub 링크 vs 케이스 카드 + 역량×근거를 검토자 5명에게 제시 | 4명 이상이 주요 역할과 근거를 정확히 설명하고 더 구체적인 면접 질문 작성 | 요약 순서·개인/팀 분리 개선 |
| E5 | 엠바고·공개 수용성 | 교수·조교와 학생에게 공개 수준·엠바고 규칙 설명 | 교원 다수가 “학기 후 공개라면 허용 가능”, 동의와 조건을 갖춘 사례 5개 이상 확보 | 공개 범위를 개념·요약 수준으로 제한, 공개 허용 동아리·개인 프로젝트로 pilot |
| E6 | 졸업생 공급 | 2026-2학기 종강 무렵 졸업생·고학년에게 선배 노트·막힘 카드 요청 | 과목당 선배 노트 10개, 막힘 20개 | 대상 과목 축소, 운영자가 인터뷰 후 대필(작성자 승인) |

E0 기록 실험은 절반은 자유 기록, 절반은 태그형 빌드 로그로 시작해 장애 요인을 찾습니다. 작은 표본이므로 통계적 확증보다 장애 요인 발견이 목적입니다. 측정 방법은 모집 전에 고정하고 결과에 맞춰 기준을 몰래 바꾸지 않습니다.

학생이 실제 제출 자료를 공개하기 어렵다는 결과가 나와도 프로젝트를 버릴 이유는 아닙니다. 제출 후 공개 가능한 프로젝트, 공개 목적의 동아리 결과, 개인 재구현 과제, 선배 노트로 공급 범위를 조정합니다.

## 5. 수용 시나리오

**A. GitHub 없이 개인 과제 기록**
이메일로 가입해 private 과제를 만들고 PDF와 한 줄 로그를 남깁니다. 재접속 시 자료와 저장 상태가 유지되고, 공개 전에는 익명·다른 사용자·검색 API에서 보이지 않습니다. GitHub 연결을 요구하는 빈 화면이 없어야 합니다.

**B. 디스코드에서 막힘 기록**
팀원이 디스코드에서 `/log 막힘 CORS 에러`를 입력하면 해당 프로젝트에 🧱 로그가 한 번만 생성됩니다. 같은 요청이 재전송돼도 중복되지 않습니다. 다른 팀원이 남의 메시지에 📌을 달면 작성자에게 승인 요청이 가고, 승인 전에는 로그가 생기지 않습니다.

**C. 팀원이 기여를 확인**
A가 로그·산출물을 근거로 역할을 선언하고 B가 확인합니다. A가 내용이나 근거를 수정하면 이전 확인은 현재 선언에 유효하다고 표시되지 않습니다. owner도 A의 선언을 편집할 수 없습니다. 동료평가 리포트에는 확인 상태가 구분되어 나타납니다.

**D. 엠바고와 공동 자료 공개**
학기 진행 중인 과목의 과제는 게시 요청이 서버에서 거부됩니다. 학기 종료 후 owner가 후보를 만들었으나 한 명이 동의하지 않았거나 파일이 검사 중이면 게시가 실패합니다. 동의 직후 게시 전 탈퇴·철회·내용 변경이 일어나도 서버 재검사가 막습니다. 작업 공간의 다른 로그는 공개 응답에 포함되지 않습니다.

**E. 철회와 파생 데이터**
공개된 공동 파일의 동의가 철회되면 새 공개 조회와 파일 접근을 즉시 차단하고, 포트폴리오·케이스·검색·과목 집계에서 제외합니다. 짧은 URL TTL 동안의 잔여 접근을 테스트하고, 이미 받은 사본은 회수할 수 없음을 안내합니다. worker가 실패해도 공개 읽기가 먼저 차단되어야 합니다.

**F. 후배의 과목 탐색과 플랜 포크**
비로그인 방문자가 과목 페이지에서 공개 사례·막힘·선배 노트를 봅니다. 워크로드 분포는 기여자가 5명 미만이면 표시되지 않습니다. 로그인한 후배가 계획을 포크하면 마일스톤·체크리스트·시간 배분·참고 자료만 복사되고, 산출물·로그 본문·막힘 해결 내용은 복사되지 않습니다.

**G. 사후 작성**
졸업생이 지난 과제를 사후 작성 모드로 만들면 모든 항목과 공개 화면에 `사후 작성`이 표시되고, 자기 기입 날짜와 기록 시각이 구분됩니다.

**H. 초보 학생의 기록과 접근성**
모바일에서 파일만 먼저 올리고 나중에 설명을 완성할 수 있습니다. 저장 실패 시 내용이 사라지지 않고 재시도가 표시됩니다. 키보드로 모든 작업을 할 수 있고, 상태는 색상·아이콘 외 텍스트로도 이해할 수 있습니다. 할 일 순서는 드래그 없이 바꿀 수 있습니다.

**I. 취업용 읽기**
익명 검토자가 로그인 없이 공개 프로필을 열고 90초 안에 대표 과제의 문제·개인 역할·근거를 찾습니다. 연락처는 학생이 허용한 내용만 보입니다. 비공개 학교 정보·이메일·팀 피드백·체크인이 페이지 HTML·JSON·Open Graph·인쇄물에 포함되지 않습니다.

## 6. 측정 계획

**북극성 지표:** 학기 말에 공개된 과제·선배 노트 중 **후배가 계획을 포크하거나 ‘도움됐어요’를 남긴 수** (pilot 학기 목표 가설 15건).

작성자 측 핵심 지표는 **기간 중 의미 있는 로그를 남기고 기여 근거를 포트폴리오에 연결한 학생 수**입니다. 활동량을 늘리는 대신 기록의 유용성을 확인합니다.

| 지표 | 정의 | pilot 판단 초안 |
|---|---|---|
| 활성화 | 가입 7일 이내 과제 생성 + 로그 3개 + 근거 하나 | 초대 학생의 50~60% |
| 기록 유지 | 활성 학생이 4주 중 3주 이상 기록한 비율 | 40%, 시험 기간 영향 별도 확인 |
| 학기 중 가치 | 기여 리포트를 동료평가·발표에 실제로 쓴 팀 | 30% |
| 사례 전환 | 공개 허용이 확인된 종료 과제 중 공개(요약 이상) 비율 | 30~40% |
| 도움 받은 탐색 | 과목 페이지 방문 후 막힘·선배 노트에 ‘도움됐어요’ 또는 포크한 재학생 비율 | 30% |
| 공급 전환 | 도움 받은 학생 중 학기 말 노트·막힘을 직접 남긴 비율 | 20% |
| 포트폴리오 활용 | 공개 사례를 대표 기여로 연결하고 실제로 공유한 학생 | 10명 이상(파일럿), 20명(단계 3) |
| 이해도 | 모의 검토자가 역할·결과·근거를 정확히 설명한 비율 | 80% |
| 작성 부담 | 로그 1회 실제 작성 시간과 중단 이유 | 중앙값 5분 이하 |
| 운영 안전 | 비공개 누출·잘못된 공개·삭제 실패 | 중대한 미해결 건이 있으면 확대 중단 |
| 비용 | 활성 학생당 저장량·전송량·worker·AI 비용·운영 인력 시간 | 다음 범위 산정에 반영 |

최소 분석 이벤트: `project_created`, `log_saved`(tag·source), `evidence_attached`, `milestone_snapshot_set`, `checkin_submitted`, `claim_endorsed`, `report_exported`, `candidate_prepared`, `consent_completed`, `publication_published`, `publication_withdrawn`, `plan_forked`, `usefulness_marked`, `senior_note_published`, `portfolio_shared`. 과제 본문·파일 내용·검색 원문·연락처는 이벤트에 담지 않습니다. pilot 동의·보존 기간·분석 접근권한은 별도로 안내합니다.

공개 조회수·좋아요·커밋 수를 개인 역량 점수로 쓰지 않습니다. 작은 표본의 비율을 전체 대학생 시장에 일반화하지 않으며, 취업률 개선은 초기 pilot으로 입증할 수 없는 별도 장기 연구 질문입니다.

## 8. 콜드 스타트와 성장

공급 단위를 사례보다 작게 쪼개 초기 콘텐츠를 빠르게 모읍니다.

| 공급 단위 | 작성 시간 가설 | 초기 목표(과목 하나 기준) |
|---|---|---|
| 선배 노트 | 10분 | 10개 |
| 막힘 카드(사후) | 5분/개 | 20개 |
| 사후 작성 사례 | 30분 | 3~5개 |
| 진행 중 사례 | 학기 내내 | pilot 팀 5~10개 |

- **순서:** 2026-12 졸업생 캠페인 → 2027-03 개강 때 과목 페이지 공개(재학생 유입) → 학기 중 기록 → 2027-06 종강 후 공개 → 하반기 공채 시즌 포트폴리오 공유 → 공유 링크로 다음 유입.
- **채널:** 학과 학생회, 개발·디자인 동아리, 캡스톤 발표회, 졸업작품전. 대학 메일 인증을 입장 조건으로 강제하지 않습니다.
- **밀도:** 학교 전체가 아니라 과목 2~3개에 집중합니다. 검색 결과가 적으면 인기 피드 대신 과목별·유형별 모음을 보여 주고, “다른 학교에서는”(개념 태그)으로 보완합니다.
- 초기 공개 콘텐츠에는 실패·제약이 있는 사례도 포함해, 전시가 잘 되는 학생만 혜택을 보는 구조를 피합니다.
- **ProofU 첫 사례:** 오너가 사후 작성 모드로 ProofU 자체를 첫 공개 사례로 올립니다(2019년 커밋은 재구성 기록임을 표시).

## 10. 운영 비용 산정 방식

호스팅 업체·지역·용량·가격을 선택하지 않았으므로 월 비용을 확정 숫자로 제시하지 않습니다. 공급자 선택 시 당시 공식 가격으로 다시 산정합니다.

- 고정: 웹·worker·봇 실행, PostgreSQL, 모니터링, 인증·메일
- 변동: 저장량, 다운로드 전송량, 검사·썸네일·PDF 작업, AI 토큰, 외부 API 호출
- 사람: 공개 상담, 신고·분쟁, 인터뷰, 파일·DB 복구, 배포 관리

초기 50명 × 500MB는 최대 약 25GB 원본 가정이며 파생 파일·버전·백업·전송량은 추가입니다. 동영상은 외부 링크 우선, 학생당 한도와 전체 예산 경보를 둡니다. 예산이 부족하면 AI·GitHub 자동 연결·정교한 PDF·의미 검색부터 줄이고, 비공개 권한·파일 격리·공개 철회·복구는 유지합니다.

## 11. Git·아카이브·문서 운영

- 원본 `frontend/`, `backend/`, `docs/history-map.json`, `docs/archive-cleanup.json`은 보존합니다. 원본 수정이 필요한 별도 요청이 있으면 변경과 검증 기준을 명시적으로 기록합니다.
- 신규 구현은 기능별 브랜치(예: `peerchive/<기능>`)에서 진행하고, 신규 `apps/`·`packages/`에 자체 테스트·migration·운영 문서를 둡니다. master 이력을 다시 쓰거나 백업 브랜치를 변경하지 않습니다.
- 각 구현 단위는 문제·사용자 행동·완료 기준·권한 영향·테스트를 PR에 기록합니다. README에는 기능을 ‘제안 / 개발 중 / 사용 가능’으로 구분해 표시합니다.
- 실험 결과에 따라 이 문서를 갱신하고, 주요 결정은 ADR로 남깁니다.
- 2019년 커밋 18개는 2020년 업로드 코드를 재구성한 기록이며 실제 당시 개발 로그가 아닙니다. 신규 서비스는 그 기록을 실시간 개발 증빙이나 기여 인증으로 표시하지 않습니다. [원본 이력 백업](https://github.com/polynomeer/peerchive/tree/backup/pre-reconstruction-20261013)은 유지합니다.

## 12. 바로 할 일 (2026-10-19부터 2주)

1. 인터뷰 질문지(§2.1)를 확정하고 재학생·채용 검토자·교원 후보를 모집합니다.
2. 노션 빌드 로그 템플릿(태그·마일스톤·체크인 폼)과 디스코드 채널 구조를 만들고 E0 파일럿 팀 2~3개를 모집합니다.
3. 첫 과목 2~3개를 정하고 졸업생 5명에게 선배 노트·막힘·사후 작성(E2)을 요청합니다.
4. 과목 페이지·공개 사례·공개 프로필의 정적 목업을 만들어 E1·E4에 씁니다.
5. ProofU 원본 화면 캡처와 이력 자료로 첫 사례의 2019 마일스톤 스냅샷을 준비합니다.
6. Nuxt + PostgreSQL + Drizzle + pg-boss 스켈레톤과 CI(원본 보존 검증 포함)를 기술 실험으로 구성하고 ADR을 남깁니다.

이 순서는 ‘좋아 보이는 사이트’를 먼저 만드는 것보다 어떤 기록이 학생에게 실제로 유용한지 확인하기 위한 것입니다. 학생 모집·연락, 외부 서비스 가입·배포는 이 문서 작업에 포함되지 않습니다.
