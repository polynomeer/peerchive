# Peerchive 고도화 실행 계획과 검증 기준

작성일: 2026-10-13 · 상태: 제안

Peerchive(피어카이브)는 2019년 대학교 학부 졸업작품 **ProofU**에서 이어지는 프로젝트의 새 이름입니다. *Peer + Archive*를 결합해 학생들이 서로의 과제·프로젝트 경험에서 배우는 공개 아카이브라는 목적을 담았습니다. 별도의 커리어 관리 프로젝트 `proofu`와 구분하기 위해 이름을 변경했습니다. 현재 저장소 주소 `proofu-univ`와 문서 파일 경로는 유지하며, 보존된 코드는 기존 ProofU의 구현입니다.

[제품 기획](../PROOFU_EVOLUTION_PLAN.md) · [시스템 설계](SYSTEM_DESIGN.md)

## 1. 시간과 인력에 대한 전제

아래는 개발자 1명이 주 25~30시간, 사용자 조사·운영 협력자 1명이 주 3~5시간 참여하고 첫 학생 코호트에 접근할 수 있다는 가정의 **16주 MVP·pilot 계획**입니다. 확정 일정이나 이미 수행한 조사 결과가 아닙니다. 코호트 확보와 공개 정책 검토는 개발과 별개로 지연될 수 있습니다.

기존 서비스를 실행 가능하게 만드는 데 모든 시간을 먼저 쓰지 않습니다. 새 경험이 필요한지 수동 실험으로 확인하고, 동시에 새로운 앱 기반의 가장 작은 공개 흐름을 만듭니다. 새 기술·파일 변환·동의 기능의 불확실성이 커서 단계별로 다음 단계 착수를 판단합니다.

실제 투입 시간이 주 10시간이면 최소 약 2.5~3배의 달력 시간이 필요할 수 있습니다. 상용 출시 수준의 정책·운영·접근성·기관 검토는 pilot 이후 별도 범위입니다. 파일 공유·게시 권한의 위험 때문에 예산이 부족해도 권한 검사를 생략하지 않고 기능 범위를 줄입니다.

## 2. 개발 전에 할 수 있는 수동 실험

### 2.1 원래 문제를 다시 확인하기

학생 8~12명에게 최근 과제를 시작한 순간부터 끝낸 뒤 정리한 순간까지 실제 자료를 보며 인터뷰합니다. 과제 파일을 강제로 받거나 비공개 자료를 연구 목적으로 공개하지 않습니다. 질문은 다음과 같습니다.

- 어떤 과제에서 어떤 도움을 누구에게 구했고, 실제로 유용했던 것은 무엇인가?
- 참고 자료를 봤지만 적용하지 못한 이유와 제출 규칙의 제약은 무엇인가?
- 진행 중 판단·실패·검증을 어디에 남겼는가? 팀의 결과 중 본인 역할은 어떻게 설명하는가?
- 포트폴리오를 만든 적이 있다면 얼마의 시간과 어떤 재작업이 필요했는가?
- 어디까지 공개하고 싶고, 누구의 동의가 필요한가? 무엇 때문에 공개를 꺼리는가?

채용 검토 경험자 4~6명에게 학생 사례 3개를 90초씩 보여 주고 역할·근거·면접 질문을 설명하게 합니다. 기업이 이 플랫폼을 사용할 것이라는 확약을 인터뷰에서 추론하지 않습니다. 교수·멘토 2~3명에게 실제 공개 조건과 걱정을 확인합니다.

### 2.2 사례 정리 실험

동의한 완성 과제 3~5개를 기존 자료로 수동 정리합니다. ‘문제 / 본인 기여 / 중요한 판단 / 확인 방법 / 결과 / 한계 / 출처’ 서식과 단순 결과물 링크를 비교합니다. 같은 학생 자료를 사용해 포트폴리오 작성 시간과 읽는 사람의 이해 차이를 봅니다.

다음 4주 동안 8~12명의 학생이 주 1~2회 기록하는 실험을 합니다. 절반은 자유 기록, 절반은 세 항목 질문형으로 시작하고 작은 표본임을 고려해 통계적 확증보다 장애 요인을 찾습니다. 근거를 첨부하는 데 시간이 너무 걸리면 링크·파일부터 저장하도록 바꿉니다.

### 2.3 처음 판단할 기준

다음 값은 작은 pilot에서 방향을 판단할 가설 기준입니다. 모집 전 측정 방법을 고정하고 결과에 맞춰 기준을 몰래 바꾸지 않습니다.

| 가설 | 진행 조건 초안 | 조건을 충족하지 못하면 |
|---|---|---|
| 공개 사례가 과제 시작에 도움 | 학생 8명 중 5명 이상이 참고 사례에서 자신의 다음 행동을 구체적으로 제안 | 탐색을 줄이고 개인 기록·포트폴리오에 집중 |
| 짧은 기록이 지속 가능 | 참여자 절반 이상이 4주 중 3주에 기록, 기록 작성 중앙값 5분 이내 | 입력 항목 축소, 파일 중심 흐름, 자동 수집 필요성 검토 |
| 기여 설명이 이해를 도움 | 검토자 5명 중 4명이 주요 역할과 연결된 근거를 정확히 설명 | 요약 정보 순서와 개인/팀 분리를 먼저 개선 |
| 공개 가능 사례 확보 | 명시적 동의와 조건 확인을 갖춘 사례 5개 이상 확보 | 해당 수업 배포를 보류하고 공개 허용 동아리·개인 프로젝트로 pilot |

학생이 실제 제출 자료를 공개하기 어렵다면 프로젝트를 버릴 이유는 아닙니다. 제출 이후 공개 가능한 프로젝트, 공개 목적의 동아리 결과, 개인 재구현 과제로 초기 공급 범위를 조정합니다.

## 3. 단계별 로드맵

| 기간 | 목표와 구현 | 산출물 | 다음 단계 진입 기준 |
|---|---|---|---|
| 1~2주 | 인터뷰·자료 정리, 핵심 화면 프로토타입, Nuxt/DB/파일 작은 기술 실험 | 조사 요약, 수동 사례, 가설 판단, 기술 결정 기록 | 학생 기록·포트폴리오 가치 확인 또는 좁힌 가치 확정 |
| 3~4주 | 새 앱 기반, 인증, 프로필, 프로젝트와 멤버 권한 | 재현 가능한 로컬 환경·CI, private 공간 | 두 사용자 간 조회 차단 테스트 통과 |
| 5~7주 | 과정 기록·revision, 첨부 링크·파일 격리, 개인 기여 | 비공개 기록 흐름, 검사 worker, 기여 근거 | 작성·수정·재접속 보존, 다른 팀 접근 차단 |
| 8~10주 | 공개 후보·동의·발행·철회, 공개 사례 DTO | 공개 전시의 전체 흐름, 권한·철회 테스트 | 공개 누출·철회 회귀 테스트 통과 |
| 11~12주 | 대표 사례 선택·프로필 전시, 최소 탐색·신고·인쇄 | 포트폴리오 공유 가능한 MVP | 학생 1명이 과제→사례→포트폴리오까지 진행 |
| 13~16주 | 학생 20~50명·팀 5~10개 제한 pilot, 조사·수정·복구 연습 | 지표·인터뷰 결과, 장애 기록, 다음 범위 결정 | 가치·운영 부담·공개 조건을 종합한 계속/축소/전환 판단 |

상세 구현은 시간순으로 전체 계층을 따로 완성하는 방식보다 **수직 기능 단위**로 진행합니다. 예를 들어 과제 생성 화면·API·DB·권한 테스트를 함께 완료하고 다음 기능으로 갑니다. 파일 검사·권한 모델·공개 후보는 pilot 직전에 임시 처리하지 않습니다.

P1은 pilot 통과 후 별도 6~10주 범위로 산정합니다. 칸반, 리뷰, GitHub 자동 연결, 제한 공유, PDF 개선 중 실험에서 가장 큰 장애를 해결하는 1~2개만 선택합니다. P2 기업·기관 기능은 그 이후 인터뷰와 반복 사용 증거가 있어야 시작합니다.

## 4. 구현 백로그와 의존관계

| ID | 작업 | 의존 | 완료 기준 |
|---|---|---|---|
| P-01 | 사용자 조사와 사례 템플릿 | 없음 | 기록 방식·공개 장애·채용 검토 요구를 실제 사례로 정리 |
| T-01 | 개발 환경·DB migration·CI | 없음 | 새 앱 런타임 고정, 기본 deploy 재현, 아카이브 검사 병행 |
| T-02 | 세션·공개/비공개 프로필 | T-01 | 계정 상태·세션 만료·CSRF·공개 DTO 테스트 |
| T-03 | 과제·초대·프로젝트 권한 | T-02 | 초대 만료·탈퇴·owner 변경·다른 팀 접근 테스트 |
| T-04 | 과정 기록·revision | T-03 | 작성자 권한·저장 실패·낡은 버전 충돌 처리 |
| T-05 | 파일 업로드·격리·검사 | T-03 | clean 이전 열람·공개 불가, 한도·오류·중복 요청 처리 |
| T-06 | 개인 기여·팀원 확인 | T-04, T-05 | 주장 수정 시 확인 무효화, 타인 주장 수정 차단 |
| T-07 | 공개 후보·동의·미리보기 | T-04~06 | 선택 버전만 DTO 구성, manifest 변경 시 동의 재검토 |
| T-08 | 발행·철회·파생 자료 차단 | T-07 | 트랜잭션 재검사, 철회 직후 익명 조회 차단 |
| T-09 | 포트폴리오·개인 프로필 | T-08 | 본인 기여 선택, 철회된 사례 자동 차단 |
| T-10 | 탐색·신고·관리 조치 | T-08 | public 상태만 검색, 조치·이의제기·audit 기록 |
| T-11 | 운영 runbook·복구·pilot 계측 | T-01~10 | DB+파일 복구, 삭제 ledger 재적용, 개인정보 없는 분석 |
| P-02 | pilot 평가와 범위 조정 | P-01, T-11 | 사용·공개·이해도·운영 비용 근거로 다음 단계 결정 |

개발 착수 순서는 T-01 → T-02/T-03 → T-04 → T-05/T-06 → T-07/T-08 → T-09/T-10입니다. 이는 작업 의존관계이며 병렬 에이전트나 인력 투입을 이미 확정한 계획이 아닙니다.

## 5. 기능별 사용자 시나리오와 수용 테스트

### 시나리오 A: GitHub 없이 개인 과제 기록

학생이 이메일로 가입해 private 과제를 만들고 PDF와 한 줄 기록을 남깁니다. 재접속 시 자료와 저장 상태가 유지되고 공개 준비를 누르기 전에는 익명·다른 사용자·검색 API에서 보이지 않습니다. GitHub 연결을 요구하는 빈 화면이 없어야 합니다.

### 시나리오 B: 팀원이 기여를 확인

팀원 A가 기록과 산출물을 연결해 역할을 주장하고 B가 확인합니다. A가 내용이나 근거를 수정하면 이전 확인은 현재 주장에 대해 유효하다고 표시되지 않습니다. owner도 A의 개인 주장을 임의 편집할 수 없어야 합니다.

### 시나리오 C: 공동 자료 공개

owner가 공개 후보를 만들었으나 한 명이 동의하지 않았거나 파일이 검사 중이면 게시가 실패합니다. 모든 조건이 충족된 뒤에만 공개 release가 생기고 작업 공간의 다른 메모는 공개 응답에 포함되지 않습니다. 동의 직후 게시 전 탈퇴·철회·내용 변경이 일어나도 서버 재검사가 막아야 합니다.

### 시나리오 D: 철회와 파생 포트폴리오

공개된 공동 파일의 동의가 철회되면 새 공개 조회와 파일 접근을 즉시 차단합니다. 관련 포트폴리오·검색·PDF 생성에서도 자료가 제외됩니다. 이미 받은 사본의 회수 불가능성은 안내하며 짧은 URL TTL 동안의 잔여 접근도 테스트합니다. worker가 실패해도 공개 읽기는 먼저 차단되어야 합니다.

### 시나리오 E: 초보 학생의 기록과 접근성

모바일에서 파일만 먼저 추가하고 돌아와 설명을 완성할 수 있습니다. 저장 실패 시 내용이 사라지지 않고 재시도가 표시됩니다. 키보드로 모든 작업을 수행하고 상태는 색상·아이콘 외 텍스트로 이해할 수 있어야 합니다. 칸반을 추가할 때 드래그 없이 순서를 변경할 수 있어야 합니다.

### 시나리오 F: 취업용 읽기

익명 검토자가 로그인 없이 공개 프로필을 열고 90초 안에 대표 과제의 문제·개인 역할·근거를 찾습니다. 연락처는 학생이 허용한 내용만 보입니다. 비공개 학교 정보·이메일·팀 피드백이 페이지 HTML, JSON, Open Graph, 인쇄물에 포함되지 않아야 합니다.

## 6. 측정 계획

초기 핵심 지표는 **기간 중 의미 있는 과정 기록을 남기고 기여 근거를 포트폴리오에 연결한 학생 수**입니다. 활동량만 늘리는 대신 완성한 기록의 유용성을 확인합니다.

| 지표 | 정의 | pilot 판단 초안 |
|---|---|---|
| 활성화 | 가입 후 7일 이내 과제·첫 기록·근거 하나를 생성한 비율 | 초대한 학생 중 50% 목표 가설 |
| 기록 유지 | 활성화 학생이 4주 중 3주 이상 기록한 비율 | 40% 목표 가설, 시험 기간 영향 별도 확인 |
| 사례 전환 | 완료 과제 중 명시적 공개가 가능하고 사례로 발행된 비율 | 분모는 공개 허용 확인된 과제만; 30% 목표 가설 |
| 포트폴리오 활용 | 공개 사례를 대표 기여로 연결하고 실제로 공유한 학생 수 | 10명 이상을 첫 유용성 신호로 제안 |
| 이해도 | 검토자가 역할·결과·근거를 정확히 설명한 비율 | 모의 검토자 80% 목표 가설 |
| 작성 부담 | 기록 1회 실제 작성 시간과 중단 이유 | 중앙값 5분 이하 목표 가설 |
| 운영 안전 | 비공개 누출·잘못된 공개·삭제 실패 | 중대한 미해결 건이 있으면 확대 중단 |
| 비용 | 활성 학생당 저장량·전송량·worker 시간·운영 인력 시간 | 실제 비용을 다음 범위 산정에 반영 |

`project_created`, `entry_saved`, `evidence_attached`, `candidate_prepared`, `consent_completed`, `publication_published`, `publication_withdrawn`, `portfolio_shared`를 최소 이벤트로 제안합니다. 과제 본문·파일 내용·검색 원문·연락처는 분석 이벤트에 담지 않습니다. pilot 동의, 보존 기간, 분석 접근권한은 별도 안내합니다.

공개 조회수·좋아요·커밋 수를 개인 역량 점수로 사용하지 않습니다. 인터뷰와 사례 품질 검토를 함께 보고, 작은 표본의 비율을 전체 대학생 시장에 일반화하지 않습니다. 취업률 개선은 초기 pilot으로 입증할 수 없고 장기 추적·비교와 참여자 동의가 필요한 별도 연구 질문입니다.

## 7. 출시와 확대의 게이트

| 게이트 | 필수 확인 | 실패 시 |
|---|---|---|
| G0: 방향 | 실제 학생 자료로 기록·포트폴리오 가설 검증 | 제품 범위 조정 후 개발 축소 |
| G1: private alpha | 권한·저장·파일 격리·계정 상태 테스트 | 외부 공개 기능을 열지 않음 |
| G2: 제한 public pilot | 공개 동의·철회·파생 차단·신고·복구 동작 | public 기능 차단, 문제 해결 후 재검증 |
| G3: 다음 코호트 | 기록 부담·학생 가치·공개 정책·운영 비용 검토 | 사용 목적이나 모집 범위 조정 |
| G4: 기업·기관 확장 | 동의한 사용자 공급, 반복 검토 수요, 연락·데이터 정책 확인 | 공개 프로필 링크 수준 유지 |

기능 완료와 운영 준비를 구분합니다. public 출시 전에 신고 처리 담당자, 접근 권한, 대응 시간, 계정·자료 삭제 절차, 파일 백업, 복구 순서를 확인합니다. 실제 법무·학교 규정 검토를 문서에 적었다는 이유만으로 완료 처리하지 않습니다.

## 8. 위험과 대응

| 위험 | 초기에 확인할 신호 | 대응 |
|---|---|---|

| 기록 피로 | 1~2회 입력 뒤 이탈·첨부 누락 | 짧은 입력, 파일 먼저, 필수 유형 축소 |
| 포트폴리오 과장 | 역할 주장과 근거 불일치·팀원 분쟁 | 기여 상태 구분·수정 버전·철회·이의제기 |

| 실적 있는 학생만 참여 | 사례가 일부 숙련자에게만 몰림 | 실패·작은 과제 서식, 민감 정보 선택, 멘토 피드백 |

## 9. 운영 비용과 예산 산정 방식

호스팅 업체·지역·저장 용량·가격을 선택하지 않았으므로 검증되지 않은 월 비용을 확정 숫자로 제시하지 않습니다. 공급자 선택 시 현재 공식 가격으로 아래 항목을 다시 산정합니다.

- 고정 비용: 웹·worker 실행, PostgreSQL, 모니터링, 인증·메일 제공.
- 변동 비용: 저장량, 다운로드 전송량, 검사·미리보기·PDF 작업, 외부 API 호출.
- 사람 비용: 자료 공개 상담, 신고·분쟁, 학생 인터뷰, 파일·DB 복구, 배포 관리.

초기 50명 × 저장 한도 500MB는 최대 약 25GB의 원본 데이터 가정입니다. 파생 파일·버전·백업·전송량은 추가이며 실제 사용량과 다릅니다. 동영상은 외부 링크 우선으로 두고 학생당 한도·전체 예산 경보를 설정합니다.

예산이 부족하면 GitHub 자동 연결·정교한 PDF·검색 추천·채팅부터 줄입니다. 비공개 권한·파일 격리·공개 철회·복구는 pilot의 기본 조건으로 유지합니다.

## 10. Git·아카이브·문서 운영

이번 문서만 현재 저장소에 커밋합니다. 신규 구현은 향후 `codex/peerchive-evolution-<기능>` 등의 브랜치에서 후속 커밋으로 진행하는 방안을 제안합니다. 기존 master의 이력을 다시 쓰거나 백업 브랜치를 변경할 이유가 없습니다.

현대화 구현 시 `frontend/`, `backend/`, `docs/history-map.json`, `docs/archive-cleanup.json`을 보존합니다. 원본 자료를 수정해야 하는 별도 요청이 있으면 해당 변경과 검증 기준을 명시적으로 기록합니다. 신규 `apps/`·`packages/`에는 자체 테스트·migration·운영 문서를 둡니다.

각 구현 단위는 문제·사용자 행동·완료 기준·권한 영향·테스트를 PR에 기록합니다. 기능 구현 여부는 README에 ‘제안 / 개발 중 / 사용 가능’을 구분해 표시합니다. 이 설계안은 실제 조사·실험 결과에 따라 ADR과 변경 이유를 남기며 갱신합니다.

2019년 커밋 18개는 2020년 업로드 코드를 재구성한 기록이며 실제 당시 개발 로그가 아닙니다. 신규 서비스는 그 기록을 실시간 개발 증빙이나 본인 기여 인증으로 표시하지 않습니다. [원본 이력 백업](https://github.com/polynomeer/proofu-univ/tree/backup/pre-reconstruction-20261013)은 유지합니다.

## 11. 다음 착수 작업

다음 작업은 실제 서비스 전체 구현보다 작은 검증 단위로 시작하는 것이 좋습니다.

1. 최근 과제 자료와 공개 가능한 완성 과제를 3~5개 선정합니다. 사용·공개 동의를 먼저 확인합니다.
2. 대표 과제 하나를 제안 서식으로 수동 편집하고 학생·채용 검토자에게 읽게 합니다.
3. 짧은 기록 작성과 개인 기여 표시, 공개 미리보기의 화면 흐름을 테스트합니다.
4. 확인된 흐름에 맞춰 기술 기반과 private 과제·첫 기록까지 하나의 수직 기능으로 구현합니다.
5. 권한·공개·철회 게이트를 통과한 뒤 제한 pilot을 시작합니다.

이 순서는 ‘좋아 보이는 사이트’를 먼저 만드는 것보다 어떤 기록이 학생에게 실제로 유용한지 확인하기 위한 제안입니다. 프로토타입과 실제 앱 구현, 학생 모집·연락, 외부 서비스 가입·배포는 이번 문서 작업에 포함되지 않습니다.
